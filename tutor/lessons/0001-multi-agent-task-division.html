Lesson 1 · 15 minutes

How a team of AI agents divides up a complex task

By the end of this lesson you can sketch an orchestrator-worker split for a complex software task (what the lead does, what each subagent is told, what comes back) and say whether the split is worth its cost.

Objective O1: how a team of AI agents divides up a complex task About 15 minutes
Why this matters for you

You already work with single agents and tool calling. Splitting work across several agents is the next step toward deploying agents for larger jobs, and it is also the step where a bad split quietly burns a lot of tokens.

One agent has one context window, the text it can hold in view at once, and it works one step at a time. A team breaks a big task apart: a lead agent plans, worker agents run in parallel, and the lead combines what they return. This lesson shows how to write that split, and when it costs more than it returns.

Predict first 1 min

Here is the running task for the whole lesson. A repository has 40 modules that all call version 1 of a payments API, and every one must move to version 2. You could hand it to one agent that works through the modules in order, or to a lead agent that gives ten workers four modules each, all running at the same time.

Before reading on, decide what you expect and say it to yourself in one line. Would the ten-worker version be about ten times cheaper in tokens, about the same, or more expensive than the single agent? Would it finish ten times sooner?

Commit to a number for cost and one for speed; a guess you have made is easier to correct than a vague feeling. "When splitting pays" gives the evidence, and the worked example reuses this migration.

The orchestrator-worker shape 2 min

The common design is called orchestrator-worker: one lead agent receives the task, and it plans the work, starts several subagents (workers with their own context windows) and then synthesizes what they send back into one answer. Anthropic describes exactly this shape in the system behind its Research feature, where the lead agent develops a strategy, spawns subagents that search in parallel, and gathers the results (Anthropic Engineering).

So the lead has three verbs: it plans, it spawns, and it synthesizes. Planning decides which pieces of the task are independent enough to hand out. Spawning starts a worker for each piece. Synthesizing means the lead reads the returned results, resolves conflicts between them and produces the single final output. Notice that the lead does the thinking about the whole, while each worker sees only its piece.

Roles can also be split by job instead of by topic. The same system uses a separate CitationAgent that processes the finished report and attributes each claim to a source; it researches nothing, so a team can hold specialists as well as copies of one worker.

A common mix-up

Parallel does not mean unordered. Any step that needs another step's output still has to wait for it; the worked example shows one in the migration.

Check yourself

Which three verbs describe what the lead agent does?

Show the answer

Plan, spawn, synthesize. Searching and writing belong to workers, and the lead's value is the view of the whole task.

What each subagent is told 2 min

A worker knows only what the lead writes into its task message, so the message is the whole interface. Anthropic found that each subagent needs four things: an objective, an output format, guidance on the tools and sources to use, and clear task boundaries (Anthropic Engineering). Call this the four-part brief.

The reason is what happens without it. In the same system, short instructions led to subagents duplicating work or leaving gaps: in one example, one subagent explored the 2021 chip crisis while two others duplicated work on 2025 supply chains, so the team covered the same ground twice and missed the rest. The boundary part is what stops two workers from editing the same thing.

Here is the contrast in the payments migration. The vague version is one line: update the payments code. A complete version, for the worker that owns modules 11 to 20, reads as follows.

  • Objective: move modules 11 to 20 from the v1 payments client to the v2 client.
  • Output format: a list of files changed plus open questions, under 200 words.
  • Tools: read, edit and grep only; no network access; do not touch tests.
  • Boundary: stop at the module boundary and do not touch the shared config.
A common mix-up

A short delegation feels enough because a capable worker will figure it out. But it cannot see the other workers or the earlier chat, so the gaps and overlaps appear exactly where you were vague.

Check yourself

A lead tells a worker: "Migrate modules 11-20 to the v2 client and edit whatever you need." The worker also rewrites the shared config, which another worker was changing. Which part of the brief was missing?

Show the answer

The task boundary. The objective was clear; "whatever you need" left the edge of the task undefined, which is how overlap starts.

Subagents in Claude Code 1.5 min

Claude Code builds this in. Each regular subagent runs in its own context window with a custom system prompt, specific tool access and independent permissions, and it does not see your conversation history; when it finishes, only its summary returns to the main conversation (Claude Code docs). A forked subagent is the exception, since it inherits the parent conversation, but the default is a fresh start.

The summary return keeps the main context clean. A subagent is defined in a Markdown file with frontmatter, the settings block at the top. Only name and description are required, and Claude uses the description to decide when to delegate, so write it as the situation the subagent is for. Each subagent also spends its own tokens, which matters in the cost section below.

---
name: v2-module-worker
description: Migrates one group of modules from the payments v1 client to v2.
tools: Read, Edit, Grep
---
Migrate only the modules you are given. Return files changed and open questions.
Check yourself

Why can't a regular subagent see the earlier chat?

Show the answer

It starts in its own fresh context. Only what the lead writes into the task message is there, so the brief has to carry everything the worker needs.

How many agents 1.5 min

The lead should size the effort to the task, because the number of workers is a cost decision and not a goal. Anthropic's research system embeds scaling rules in its prompts so the lead does not over-invest in simple queries, and gives rough tiers (Anthropic Engineering). The numbers come from research work, so for coding treat them as illustrative.

TaskTeamEffort each
Simple fact-finding1 agent3-10 tool calls
Direct comparison2-4 subagents10-15 calls each
Complex research10+ subagentsClearly divided responsibilities
A common mix-up

"More workers is always better" is tempting because parallel work sounds faster. A question with one simple answer, such as the version of a library, needs one agent and a few lookups; ten workers would just return ten copies of the same line at ten times the setup.

Check yourself

You need to compare two logging libraries on four criteria. Which tier fits best?

Show the answer

Two to four subagents. A comparison is more than a lookup but far short of a research project, so the middle tier fits.

When splitting pays 2 min

Back to your guess from the start. Anthropic reports that a single agent typically uses about 4 times the tokens of a chat, and a multi-agent system about 15 times (Anthropic Engineering). So ten workers are not ten times cheaper; they cost far more than one agent, because each reads its own context and instructions. The same post says token usage alone explained 80% of the variance in performance on their evaluation, which is why the extra tokens can buy better results.

Speed is where the parallel part pays: Anthropic says parallel subagents and tool calls cut research time by up to 90% on complex queries. Their Claude Opus 4 lead with Claude Sonnet 4 workers also beat single-agent Opus 4 by 90.2% on their internal research eval. Both are their measurements on research tasks, not general laws, and coding has less to parallelize, so expect less than ten times sooner.

A task fits a split when it passes this checklist.

  • It parallelizes: the pieces do not need each other's output.
  • It exceeds one context window.
  • It needs many tools.
  • The value of the result covers the extra cost.

It fits poorly when everyone needs the same shared context or when there are many dependencies. The article notes that most coding tasks have fewer truly parallelizable pieces than research. It also describes the coordination limit concretely: the lead runs subagents synchronously, waiting for each batch to finish, it cannot steer a worker mid-task, and workers cannot coordinate with each other. So a batch is only as fast as its slowest worker, and anything two workers must agree on has to be settled by the lead before they start.

Check yourself

Which task is the better fit for a split: reviewing 30 independent services for a known security flaw, or refactoring one tightly connected class?

Show the answer

The 30 services. They are independent, so they run in parallel, while the connected class is the shared-context, many-dependencies case.

Worked example 2 min

Apply all of this to the payments migration. The split below uses 40 modules in 4 groups of 10, one lead, four module workers, one read-only explorer and one test-runner that also reviews. These counts are my design for this task, not figures from the sources.

Worked example

Migrate a payments API from v1 to v2 across a repository of 40 modules.

  1. The explorer runs first, read-only, mapping which modules call the v1 client and how. It returns a summary, so the lead gets the map without reading 40 modules itself.
  2. The lead writes the shared v2 client wrapper before any worker starts, because every module worker depends on it. This is the one sequential dependency, and it is the lead's job because a wrapper written four times would differ four ways.
  3. The lead spawns the four workers in parallel, each with a four-part brief like the one above, one per group of 10 modules. The lead waits for the whole batch, and workers cannot talk to each other, which is why the shared wrapper came first.
  4. The test-runner runs the suite and reports failures by module, so a failure goes back to the one worker responsible.
  5. The lead synthesizes: it merges the worker summaries and test report into one changeset description and lists open questions.

Count the cost as an illustration, not a measurement. One agent reads each module once. Here the explorer, the four workers and the test-runner each also load their own instructions and context, so seven agents mean at least seven such loads on top of the module reading, and the 15 times figure shows how large the total can get. What you buy is four workers finishing together instead of one after another, and a lead window that never holds all 40 modules.

Only the middle step runs in parallel. The explorer, the wrapper and the test run are sequential, which is the dependency point from the shape section in practice.

Predict before you look

The tests fail in modules 23 and 31. Before opening the answer, decide which agents should act next and what the lead must give them.

Show the answer

The workers for modules 21-30 and 31-40 are restarted, or new ones spawned, each with a new brief naming the failing module and the failure text from the test report. They start fresh, so the old brief alone is not enough. The other two workers are not touched.

Your turn 2 min

A new task: add audit logging to 12 services, for example a record-lookup service that must log who read which patient record. First decide whether to split at all, then complete the briefs and the sequential step.

Decide first

Run the four-point checklist on this task in one line each. Then run it on a second task: changing one database schema that all 12 services read. Which one would you split, and which would you give to a single agent?

Show the answer

Audit logging passes: 12 services are mostly independent, so they parallelize, and they exceed comfortable single-window reading. The schema change fails: every service depends on the same change, so workers would need shared context and cannot coordinate. Give it to one agent, or have the lead make the schema change first and split only the follow-up edits.

Faded practice
  1. Lead: plan the split and decide the log format. Done for you.
  2. Lead: spawn workers after the shared step. Done for you.
  3. Lead: synthesize the worker summaries into one report. Done for you.
  4. Sequential step: you fill in what must be done once before any worker starts, and by whom.
  5. Worker brief: you fill in the objective, output format, tools and boundary for one worker.
  6. Team size: you fill in how many workers, and why not more.
  7. Check: you fill in one way the lead will find out that a worker overlapped with another, and what it does then.

Write your answers before opening the solution.

Show a solution

Sequential step: the lead writes one shared audit-log helper and its format first, since all 12 services call it and four versions would drift apart. Brief for a worker owning services 1-4: objective, add audit logging to services 1-4 using the helper; format, files changed plus open questions, under 200 words; tools, read, edit and grep, no network, do not touch tests; boundary, stop at these four services and leave the helper unchanged. Team size: three workers with four services each is reasonable, plus a test-runner. Twelve workers would multiply tokens for tiny jobs. Overlap check: the lead compares the lists of changed files in the summaries, and any file named twice goes back to one owner.

Summary 1 min

  • A lead plans, spawns and synthesizes; workers run in their own fresh contexts and return summaries.
  • Each brief has an objective, an output format, tools and a boundary, or work gets duplicated and left undone.
  • Splitting costs about 15 times chat in tokens, so it pays only for parallel, large, valuable work, and most coding has less of it.

Check your opening guess against this: ten workers cost far more than one agent, and they save time only on the middle, parallel step.

Say it in your own words: for a task of your own, what would the lead do first, and what is the one step you would keep sequential?
