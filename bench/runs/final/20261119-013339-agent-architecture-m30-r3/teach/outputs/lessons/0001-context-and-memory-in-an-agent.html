Context and memory in an agent

By the end of this lesson you can sketch what the makerspace assistant keeps in its context, what it saves between sessions, and how it finds the right manual page, with a reason for each choice.

Objective O3: context, memory and retrieval About 30 minutes
Why this matters for you

The makerspace assistant has to answer from long machine manuals and remember each student's training status from one visit to the next. Both jobs run into the same limit: the model sees only the text in front of it, and that text has a size and a price.

The big picture 1 min

On every call, the model sees only the text in front of it. That text has a size limit, and you pay for it. So the design question is not "what does the model know?" but three smaller ones: what text goes in on each step, what gets written down for next time, and what is fetched only when it is needed.

Those questions give three places text can live, each with its own job. The window holds what the model reads right now. Saved notes live outside the window and survive between sessions. Retrieval pulls one piece of a large store, such as a single manual page, into the window at the moment it is useful. The rest of the lesson takes them one at a time, with numbers, and ends with you sketching all three for the assistant.

Warm-up 2 min

Last time you traced one request through the agent loop. Before reading on, answer from memory; a wrong guess here is useful, because this lesson builds directly on it.

Recall

Take the request "Is the laser cutter free Friday?" with a check_calendar tool available. Who actually runs check_calendar: the model or your program? And how many times is the model called from the question to the final answer?

Check your answer

Your program runs it. The model only writes a request, something like "call check_calendar for Friday", as text; the program reads that, runs the real function and sends the result back as new text. The model is called twice: once to produce the tool request, and once, with the calendar result now included, to write the final answer.

Every call is a separate trip, and the model starts each trip knowing only what the program sends it. The next sections are about what that is and how big it gets.

If you said the model ran the tool, that is the most common slip: the model produces text, and everything that touches the world is your code. If you said one call, count again: a call ends once the model has asked for the tool, so the answer that uses the result needs a second call.

Tokens and the context window 3 min

A language model does not read letters or whole words. It reads tokens, chunks of text that are often a word or a piece of a word. Here is one sentence from an imagined laser cutter manual, split the way a tokenizer might split it. The exact cuts depend on the model, so treat this as approximate.

Max|imum| cutting| thickness| for| acrylic| is| 6| mm|.

That is about ten tokens for an eight-word sentence. Short common words are usually one token, and long or unusual ones split into several. Tokens are the unit that limits the model and that you are billed in, so from here on we count in tokens, not words.

The context window is all the text the model can refer to when it writes its next token, and that includes the text it has already written in its own reply (Context windows, Claude docs). The docs describe it as the model's "working memory", and they stress that it is not the same thing as the large body of text the model was trained on. Training shaped the model's patterns once, before you ever used it. The window is what is on the desk for this call, and it is gone when the call ends.

A rough way to feel the scale: a page of manual text with tables and part numbers might be a thousand tokens or more, which is why the example later in this lesson uses 1,500 for one manual page. The figure is invented for teaching; real counts depend on the text and the model.

Two consequences follow. First, a fact that is in your manual but not in the window is invisible to the model, however much the manual matters to you. Second, the window has a ceiling, and it differs by model; the docs list sizes up to 1M tokens for some models and 200k for others, so never design around a single number. Everything we count below has to fit under whichever ceiling you have, and everything we count is also a cost.

Check yourself

The model has written 300 tokens of a reply so far. Do those 300 tokens count toward the context window?

Show the answer

Yes. The window covers everything the model can refer to, including its own reply. A long answer both uses room and, on the next step, gets re-sent as part of the history, as the next section shows.

Everything counts, every step re-sends 3 min

What exactly goes into a call? The docs say everything in the request counts toward the window: the system prompt, every message including tool results, the tool definitions, and the output (Context windows, Claude docs). For the makerspace assistant that means four kinds of text:

  • the system prompt, your standing instructions ("you are the makerspace assistant, be careful about safety");
  • the tool definitions, the descriptions of search_manual, check_calendar and the rest, which the model must read every time to know what it may call;
  • the history: the user's messages, the model's earlier outputs and every tool result so far;
  • the new message for this step, then the model's output on top.

The system prompt and tool definitions are a fixed cost: you pay for them on every single call, before the user has said anything useful. The history is the part that grows.

It grows because each turn sends the full history again. The docs describe it as accumulation: previous turns are preserved completely, and the model's output from one turn becomes input on the next (Context windows, Claude docs). So the input of step N is the whole conversation up to step N, not just the latest message. Figure 1 shows the four steps of the example in the next section, with the size of each call's input split into fixed prefix, model outputs and tool results.

A common mix-up

"The model remembers what happened in earlier steps." It is tempting because the conversation feels continuous. But the model keeps nothing between calls; step 3 only "remembers" step 1 because your program pasted step 1's text into step 3's input again. Drop that text from the input and, as far as the model is concerned, it never happened.

Check yourself

Predict before the numbers come: in a loop where step 3's model output is a tool request and its result comes back, is step 4's input bigger than, smaller than or equal to step 3's?

Show the answer

Bigger. Step 4's input is step 3's input plus everything step 3 added: the model's output and the tool result. Unless your program trims something, input only grows over a loop.

Worked example: the four-step loop 3 min

Now the arithmetic. The assistant has three tools: search_manual, check_calendar and book_slot. The request is: "Book the laser cutter Friday, and check its manual for the maximum material thickness." The numbers are invented but plausible, and they are all in tokens.

Worked example

The fixed prefix. The system prompt is 800 tokens, the tool definitions are 700 and the user's message is 60. Every call starts with 800 + 700 + 60 = 1,560 tokens.

  1. Step 1. Input is 1,560. The model outputs 60 tokens, a request to call search_manual. The program runs it and gets back a manual page of 1,500 tokens.
  2. Step 2. Input is the prefix plus step 1's output plus the page: 1,560 + 60 + 1,500 = 3,120. The model outputs 70 tokens (check_calendar). The result is 400 tokens.
  3. Step 3. Input is 3,120 + 70 + 400 = 3,590. The model outputs 60 tokens (book_slot). The result is 100 tokens.
  4. Step 4. Input is 3,590 + 60 + 100 = 3,750. The model outputs the final answer, 120 tokens.

Add the four inputs: 1,560 + 3,120 + 3,590 + 3,750 = 12,020 tokens billed as input. The outputs add to 60 + 70 + 60 + 120 = 310. By the end, the whole conversation is 3,750 + 120 = 3,870 tokens. So you paid for input about 12,020 / 3,870, or 3.1 times, the size of the final conversation. The loop does not cost its final size; it costs the sum of every intermediate size.

As an illustration only, not a real rate: at $1 per million input tokens, 12,020 tokens is about $0.012. That is nothing for one request, and it is a lot for a makerspace assistant answering hundreds of requests a day with ten-step loops, where the sum grows faster than the step count.

Notice where the growth comes from. The biggest jump is step 2, right after the biggest result: 1,560 becomes 3,120 on the back of one manual page. That 1,500-token page entered at step 1's result and is paid for again at steps 2, 3 and 4. A big tool result is not paid for once; it is paid for on every step that follows it.

Context rot and curating 3 min

Windows are large, so why not leave everything in and stop worrying? Because of cost, which you just counted, and because more context is not automatically better. The docs say that as the token count grows, accuracy and recall degrade, a phenomenon they call context rot (Context windows, Claude docs). Anthropic's engineering article makes the same point and frames context as a finite "attention budget": every new token depletes it by some amount, and recall of any one detail decreases as the total grows (Effective context engineering for AI agents). Its explanation, in plain terms: every token has to be related to every other token, so more tokens spread the model's attention thinner, and models also see fewer very long sequences in training.

A common mix-up

"With a window this big, I never need to curate." It is tempting because a bigger window sounds like a bigger safety margin. But the limit is not the only problem: a window can be well under its ceiling and still hold so much stale text that the one useful line is harder for the model to use, while you pay for all of it on every step. The goal is the smallest set of text that still lets the model do the next step.

There are two levers, with different costs. The lightest is clearing old tool results: once the model has used a tool's output, remove that output from later calls. The article calls this one of the safest, lightest-touch forms of compaction (Effective context engineering for AI agents), and the docs list it under context editing. The heavier lever is compaction: when the conversation nears the limit, have the model summarize it and start a new window containing that summary (Effective context engineering for AI agents). Compaction can lose detail, because a summary is shorter than what it replaces; clearing loses only what you chose to clear. Which lever when: start with the simplest thing that works. Clear big, finished tool results first; compact only when the conversation itself, not one result, is what has grown long.

Here is clearing applied to the four-step loop. This is our design for the example, not something the docs prescribe. Step 2's call is the last one that needs the manual page. After it, the program replaces the 1,500-token page with an 80-token note, such as: "Manual page for the laser cutter read; maximum thickness noted in the earlier answer; re-fetch with search_manual if needed."

Worked example: clearing
  1. Step 2's input is unchanged at 3,120, because it already contained the page; the clearing happens after it.
  2. Step 3's input is the prefix, step 1's output, the note, then step 2's output and result: 1,560 + 60 + 80 + 70 + 400 = 2,170, instead of 3,590.
  3. Step 4's input: 2,170 + 60 + 100 = 2,330, instead of 3,750.
  4. That saves 1,420 tokens on each later step (3,590 − 2,170 and 3,750 − 2,330).

What did we lose? The page text itself. If the user next asks "and what about steel?", the model can no longer read the answer off the page; it has to notice the cue in the note and call search_manual again. That is the trade: you spend one extra tool call only if the page is needed again, instead of paying 1,500 tokens on every step in case it is.

Memory between sessions 3 min

Everything so far lives inside one session. Now the other half of the mission: the assistant has to know on Tuesday that a student passed laser cutter training last Thursday. The window cannot do that, because a new session starts with only what the program puts into it. Nothing from last week is there unless your code put it there.

A common mix-up

"The model remembers me between sessions." It is tempting because chat products sometimes seem to. But the model itself carries nothing over: each session begins from a blank window. When an assistant does appear to remember, a program saved something and loaded it back in.

The fix the engineering article describes is note-taking: the agent writes notes that are persisted to memory outside of the context window, and can pull them back in later (Effective context engineering for AI agents). Examples there include a to-do list or a notes file, much like the NOTES.md in this workspace. For our assistant, a small structured record per student is enough. Here is an invented example, stored in a file or database, not in the window:

{"student": "s-1042", "laser_cutter": "trained", "3d_printer": "not trained"}

The flow has two moments. At the end of a visit, the program writes the record: when a staff member marks the laser cutter training complete, the program updates laser_cutter to "trained" and saves the file. At the start of the next session, the program reads the record for the student who just logged in and puts one line into the window, perhaps in the system prompt or as a first message. That line is about 20 tokens, so remembering costs almost nothing compared with the 1,500-token page.

A caution on what to save: only what a later session will need. A student's training status passes that test; the 300 tokens of small talk before it do not. Saving less keeps the reload cheap, and the same attention-budget reasoning from the last section applies to what you load at the start.

Notice that the model is not the one remembering. It can help by deciding what to note, but the storing and reloading are ordinary program code, like reading JSON in your class project. Structure matters because the program reads the record back later and needs fields it can rely on.

Check yourself

A student passes band saw training. What does the program write, and when?

Show the answer

The program updates one field in the student's record, saved outside the window, and next session loads that short line back in. The model's memory of the chat does not survive; the whole transcript would be a wasteful way to keep one fact.

Finding the right page 4 min

The last problem: the manuals are far bigger than you want in the window. One machine's manual might be 40 pages, and the assistant covers many machines. Pasting every manual into the system prompt would make every call enormous (see the arithmetic in the worked example) and invite context rot. So the assistant must find one page and load only that.

A common mix-up

"Retrieval means the model searches its training for the answer." It is tempting because the model seems to just know things. But, as in the lesson on the agent loop, the model only writes text. Retrieval is a search that runs in a tool over your files, and the result enters the window as an ordinary tool result. If the manual is not retrievable, the model cannot see it.

The engineering article describes two ways to arrange this (Effective context engineering for AI agents). In pre-retrieval, a search over your documents, typically embedding-based, runs before the model is called, and the matching text is placed in the window up front. In just-in-time retrieval, the agent keeps lightweight identifiers, such as file paths, stored queries or links, and loads the real data with tools only when it needs it. The article also describes a hybrid: some data is loaded up front for speed, and the rest is fetched on demand at the agent's discretion.

How does a search find the right page? First you split each manual into sections, give each a stable id and index them; the ids come from your own splitting, for example from the manual's headings. Then search_manual(query) returns the best one or two sections. Keyword matching finds exact strings well, such as a part number like "LC-40", but misses paraphrases. Embedding matching compares meaning, so "how thick can I cut?" finds the "thickness limits" section, but it can blur exact codes. Many systems combine both. Just-in-time retrieval has a cost the article names: runtime exploration is slower than pre-retrieval, and the model needs clear tool descriptions to use the search well.

For the assistant, a just-in-time design looks like this. The window holds the system prompt and, for the machine being discussed, a pointer such as manuals/laser-cutter.md plus a section id like thickness-limits. When the user asks about thickness, the model calls search_manual or a read tool with that pointer, and the program returns the section, perhaps 1,500 tokens. A pointer is about 15 tokens. Figure 2 puts the three places side by side.

One more tool for large jobs, in a single sentence: a sub-agent can do the digging in its own separate window and hand back only a condensed summary, often 1,000 to 2,000 tokens (Effective context engineering for AI agents); multi-agent designs are a later lesson.

Why not always pre-retrieve? A search before the call guesses what will be needed, and if the guess is wrong you have paid for text the model never uses. Why not always go just-in-time? Each fetch is an extra tool call, which means an extra step and an extra re-send of the history. Which side wins depends on how predictable the question is, and that is a design decision, not a rule.

Check yourself

In the just-in-time design, which of these does the assistant keep in the window at the start of a conversation about the laser cutter?

Show the answer

The file path and section id. They are tiny, and the model passes them to a tool when it needs the real text. Putting in the whole manual is expensive, and assuming the model already knows it confuses training with your own files.

Faded practice and the sketch 7 min

Now apply all three ideas to a new request: "Book the band saw." This time the assistant starts by calling read_student_record, because band saw use requires training, then reads the band saw manual, then books. The prefix is again 1,560 tokens.

Part A: the arithmetic

Shown for you
  1. Step 1. Input 1,560. Output 50 (calls read_student_record). Result 120.
  2. Step 2. Input 1,560 + 50 + 120 = 1,730. Output 60 (reads the manual). Result 1,200.
Your turn
  1. Step 3. Input is 1,730 + 60 + ___ = ___. The output is 80 and the result is 100.
  2. Step 4. Input is ___ (the final answer follows, so no result).
  3. Total input billed across the four steps: ___.
  4. Optional: after step 2 you swap the 1,200-token manual page for an 80-token note. What is step 4's input now?
Show a solution

Step 3's input is 1,730 + 60 + 1,200 = 2,990 (the first blank is the 1,200-token manual page). Step 4's input is 2,990 + 80 + 100 = 3,170. The total is 1,560 + 1,730 + 2,990 + 3,170 = 9,450.

For the optional part: step 3's input becomes 1,730 + 60 + 80 = 1,870, and step 4's becomes 1,870 + 80 + 100 = 2,050. The saving on step 4 is 3,170 − 2,050 = 1,120, which is the 1,200-token page minus the 80-token note.

Part B: choose a retrieval style

Your turn

A student asks, "What is the band saw's blade speed?" Choose pre-retrieval or just-in-time and give one reason. Then compare input cost: pre-retrieving three candidate manual pages of 1,500 tokens each adds ___ tokens to the first call. A just-in-time fetch adds one 1,500-token result plus one extra step. Roughly how many extra tokens does that extra step re-send, if the history before it is 1,730? Finally: the conversation has 20 finished steps, and one 1,200-token result is the bulk of it. Clear or compact?

Show a solution

The question is narrow and the right page is easy to name, so just-in-time fits: you pay for one page, not a guess of three. Pre-retrieving three pages adds 3 × 1,500 = 4,500 tokens to the first call, and the model reads two pages it does not need. The just-in-time fetch adds 1,500 plus one more call that re-sends the 1,730-token history, so about 1,730 extra input tokens for the step itself. Even so, 1,500 + 1,730 is below 4,500. If the question were vague, such as "which machine should I use?", the guess would be harder and the balance could flip. For the last case, clear: one bulky finished result is what has grown, so replace it with a short note and keep the rest.

Part C: the sketch

The task

On paper, draw three lists for the makerspace assistant: in the window, saved outside the window and retrieved on demand. Put at least two items in each and write one reason for each item, in a clause. Use these items to start, and add your own: system prompt, tool definitions, a student's training status, the full band saw manual, a section id for the band saw manual, a completed tool result you no longer need, the booking calendar.

Show a model answer

In the window: the system prompt and tool definitions (needed on every call, so they are the fixed cost); the current student's one-line training status (small and decides what the assistant may do); the manual file path and section id (a few tokens that point at a large page).

Saved outside the window: every student's training record (it must survive between sessions and the window starts blank each time); a note after clearing, if you want a trail (cheap to keep, tells the model what to re-fetch).

Retrieved on demand: the manual section (large, needed only for some questions, so paying for it on every step would be wasteful); the booking calendar for the day asked about (changes often, so fetch it fresh rather than keep a stale copy).

Your lists may differ. The test is that each item has a reason tied to size, cost or whether it must survive the session, not that it matches this answer.

Summary 1 min

  • The window holds what the model reads this call, replies included, because the model sees only that text and every step re-sends all of it.
  • Saved notes hold what must outlive a session, such as a student's training status, because each session starts with only what the program puts in.
  • Retrieval brings in a large thing, such as a manual page, only when needed, because keeping it in the window costs tokens on every step.
  • Two levers keep the window small: clearing old tool results is the light one, compaction the heavy one, because more context is not better context.
  • Cost is a sum: a loop is billed for every step's full input, so a big result is paid for again on every later step.
