Lesson 3 · 30 minutes

Context and memory in an agent

By the end of this lesson you can take a makerspace request, sketch what is in the model's context at each step of the loop, say what is dropped, kept or saved, and choose between keeping, compacting, writing a note and retrieving a manual page, with a rough cost reason.

Objective O3: context and memory About 30 minutes
Why this matters for you

The makerspace assistant has to answer from long machine manuals and remember each student's training status between visits. Both jobs come down to deciding what the model sees at each call, and what waits somewhere else until it is needed.

The model sees only what your program puts into each call. Everything else, such as earlier steps, last week's visit or the laser cutter manual, has to be put there, or kept elsewhere and fetched. That gives three places where information can live: the context, saved notes and retrieved sources. Each has a different lifetime and a different cost. The sections below take them one at a time, then you trace a full request and do one yourself.

Warm-up: the loop 1 min

Take the question a student might ask on Friday: "Am I allowed to use the laser cutter, and book it Friday?" The agent loop handles it in steps. Each step is a separate call to the model, and each call ends with the model either asking for an action or giving a final answer. Here the steps are, by name only, search_manual, then check_calendar, then book, and then a final answer.

The point to hold on to is that every step is its own call. What the model knows at step 3 is whatever the program sends in step 3's call, and this lesson is about what that is.

Recall

When the model asks for check_calendar, who actually runs it: the model or your program?

Check your answer

Your program. The model only writes a request for the tool, and the program runs it and sends the result back in the next call. That is why your program controls everything the model sees.

Tokens and the context window 3 min

A token is the chunk of text a model reads and writes: often a whole short word, or a piece of a longer one. Models count text in tokens, not characters or words, so tokens are the unit for how much fits and how much you pay.

The context is the set of tokens included when the model generates its answer (Anthropic Engineering). It is chosen again at every call. The context window is the limit on how many tokens that set can hold. According to the context windows docs, several things count toward it: the system prompt, every message including tool results, the tool definitions, and the model's own output.

You are billed per token, input and output, so sending more text costs more. This page quotes no prices; costs here are compared in tokens only.

A rough rule for English is that one token is about three-quarters of a word, so 100 words are around 130 tokens. That is this lesson's own estimate, not a documented figure. Real counts depend on the model, and newer models can produce about 30 percent more tokens for the same text. To measure, use the token counting docs, which describe counting input tokens before you send them.

Why does size matter to your design? Two limits apply at once. The window is a hard ceiling: if the messages list plus the model's reply would go past it, the call cannot go through as it is. And the bill grows with every token sent, so a long context is expensive long before it is full. A makerspace assistant that handles hundreds of student questions a week feels this quickly, since each question may take several calls and each call resends the history. Counting tokens early, before you build, tells you which of your pieces is the big one: usually it is a pasted document or a long tool result, not the student's question.

Here is what a call looks like in code. A message is a dict with a role and content, and the context is a list of them plus the system prompt and tool definitions sent alongside.

messages = [
    {"role": "user", "content": "Am I allowed to use the laser cutter, and book it Friday?"},
]

Between steps: the program resends 3 min

The model does not keep anything from one call to the next. The Messages API is stateless: you always send the full conversational history (Messages API docs). So your program keeps a messages list, and after each step it appends what just happened and sends the whole list again. That list is the only memory the loop has.

Each turn's output becomes the next turn's input, as the context windows docs describe. So the input grows by a predictable amount:

input(step n) = input(step n-1) + output(step n-1) + tool result(step n-1)

Here is an illustrative run, with round numbers. The system prompt and tool definitions are 1,000 tokens and the question is 20, so step 1 sends 1,020. The model replies with a search_manual request of 60 tokens, and the manual passage that comes back is 600. Step 2 therefore sends 1,020 + 60 + 600 = 1,680 tokens. The model replies with a 50-token check_calendar request, and the result is 200 tokens. Step 3 sends 1,680 + 50 + 200 = 1,930.

Notice that the first 1,000 tokens are paid for again at every step, and so is the 600-token passage, even when it is no longer needed. Add up steps 1 to 3 and the program has sent 1,020 + 1,680 + 1,930 = 4,630 input tokens, although the student only typed 20. The model's own replies are billed as output tokens, and then billed again as input when they are resent. Growth is the reason the next section exists.

One consequence is that the order of things in the list is fixed by the order they happened. Your program does not edit the past by accident: it appends. If you want something removed, you must remove it yourself before the next call, which is exactly what the next section does.

A common mix-up

"The model remembers what I said earlier." It feels that way in a chat app, because the app resends the whole conversation each time. The model itself starts every call blank; if your program leaves a message out, it is gone for that call.

Check yourself

Step 3's call above sends 1,930 tokens. If the calendar result had been 500 instead of 200, what would step 3 send?

Show the answer

2,230. Step 3's input is step 2's input, plus the 50-token reply, plus the 500-token result. Nothing is dropped unless your program drops it.

When history gets too long 3 min

You might think a bigger window means you can put everything in. Two things say otherwise. The first is cost: every resent token is billed again. The second is quality. As the number of tokens grows, the model's ability to accurately recall information from the context decreases, which the Anthropic Engineering article and the context windows docs call context rot. The article's aim is the smallest set of high-signal tokens that gets the job done.

There are three ways to shrink a long history:

  • Clear old tool results. Once the model has used a result, replace it with a short stub or remove it. The article calls this one of the safest, lightest-touch forms of compaction.
  • Compact. When the conversation nears the window limit, summarise it and continue from the summary.
  • Use a sub-agent. A helper does a messy search in its own context and returns a condensed summary, often 1,000 to 2,000 tokens. A later lesson covers this; here it is just an option.

Example: after the model has read the 600-token laser cutter passage and found the rule it needs, the program replaces the passage with a 40-token summary: "Laser cutter: training level 2 required; kerf 0.2 mm." Every later call now carries 560 fewer tokens, and the one fact that mattered is still there. Anthropic reports that clearing old tool results helped on its own internal tests (context management announcement); treat those figures as the vendor's own.

Each choice loses something, so name the loss before you pick. Clearing loses the exact wording: if the student later asks "what was the kerf figure again?", the model has only your 40-token summary and would need to search again. Compacting loses detail across the whole history, and a summary can leave out something that turns out to matter. Doing nothing loses nothing at first, but costs more at every step and eventually hits the window limit. The skill is matching the loss to how likely you are to need that detail again.

Clearing fits when a large result has done its job and exact wording will not be needed again. Compaction fits when the whole conversation, questions, decisions and results together, has grown long and still matters.

Check yourself

Between sessions: notes and the memory tool 4 min

Clearing and compaction work inside one conversation. Between visits, the context is gone completely: nothing persists unless your application stores it. So the usual design is structured notes written to somewhere outside the context and read back later (Anthropic Engineering). A note costs nothing while it sits in storage, and it costs tokens only in the calls where you load it.

A common mix-up

"Memory means the model learned something." It does not. A note is an ordinary file or database row that your app writes and reads back; the model's weights do not change. Training is a different process and is outside this lesson.

Example: Riley's friend Sam finishes laser cutter training on Monday. At the end of that visit the app saves a short record, such as "Sam: laser cutter training complete, level 2." On Sam's next visit, that record goes into the first call, and the assistant can say "you are cleared for the laser cutter" without asking again.

There are two valid designs for the reading step. If your app keeps its own database, the app loads the record into the first message. This lesson's worked example uses that design. The other is the memory tool: the model itself calls view on /memories first, as step 1 of the loop. Either way, the model never touches storage. The memory tool is client-side: Claude requests file operations and your application runs them (memory tool docs). The six commands are view, create, str_replace, insert, delete and rename. A request looks like this:

{"command": "view", "path": "/memories"}
{"command": "create", "path": "/memories/sam.md",
 "file_text": "Sam: laser cutter training complete, level 2"}

Because your app runs the commands, the safety work is yours. The docs tell you to validate paths so a request cannot escape the memory folder, cap file sizes, expire old files, and strip sensitive data yourself; the model usually refuses to store it, but you should not rely on that. Note too that create can overwrite or error on an existing path, so handle both.

The same loop shape applies at the end of a visit. The model, or your app, decides what is worth keeping and writes it out; at the next visit it is read back. Keep notes short and structured, one fact per line, so loading them costs tens of tokens, not thousands. A note that grows without limit becomes the same problem as a pasted manual, which is why the docs advise capping file sizes and expiring old files.

Last, decide what is worth saving. Save what stays true: training status. Do not save what goes stale: Friday's open slots. A remembered calendar could be wrong by the time it is read, so the rule is that anything that changes is fetched by a fresh tool call, as step 3 of the worked example shows.

Check yourself

At the end of a visit, the app could save one of these. Which belongs in notes?

Show the answer

The training status. Durable and small goes in notes; fast-changing goes to a fresh tool call; big and already stored elsewhere is retrieved on demand.

Retrieval: finding the manual page 4 min

The manuals are too long to live in the context, and they do not fit in notes either. They stay in a store, and the model fetches the part it needs. There are three ways to arrange that (Anthropic Engineering):

  • Up-front retrieval: the program finds likely relevant text before the call and puts it in the context.
  • Just-in-time retrieval: the model holds only a way to look things up, such as a search tool, and fetches what it needs during the loop.
  • Hybrid: some things up front, and the rest on demand, such as loading a notes file at the start and searching for everything else as needed.

The article's advice is to do the simplest thing that works. For the makerspace, that is one tool. search_manual(machine, query) returns a single passage, for example search_manual("laser cutter", "who may use it") returns the 600-token passage about training levels. The model asks only when it needs a manual fact, and the passage is cleared once used. A hybrid version would also load the student's training record up front, since it is needed every visit.

Why just-in-time here? With up-front retrieval the program must guess what the question needs before the model has said anything, and a wrong guess leaves 600 tokens of the wrong page in every later call. Just-in-time costs one extra step, but the model asks with the question in hand. Each search is a full extra call, though, so a question the model can answer without the manual should not trigger one; the tool description is what tells the model when searching is worth a step.

How the tool finds the page

Before any question arrives, the program splits each manual into passages of a few hundred tokens and indexes them (our own simplification; the article does not prescribe a size). Matching a query to passages works in one of two ways. Keyword search scores passages by shared words, so "kerf" finds pages containing "kerf". Embedding search compares meaning, so "who may use it" can find a page headed "Authorised operators"; the article names embedding-based search as the usual up-front method. Either way the tool returns the best passage, not the whole manual.

A search can miss. Suppose search_manual("laser cutter", "who may use it") returns a page on lens cleaning. The result lands in the context like any other, the model sees it does not answer the question, and it calls the tool again with "training level required". That retry costs another full call, and up-front retrieval cannot do it at all. It is also why the loop needs a step limit.

A common mix-up

"The window is huge now, so just put the whole manual in." It is tempting because it removes the search step. But you pay for the manual on every call, and the model recalls less reliably in a crowded context. A retrieved 600-token passage usually beats a 40,000-token paste on both counts.

Worked example 6 min

Worked example

Request: "Am I allowed to use the laser cutter, and book it Friday?" All numbers are illustrative round numbers. Here the app loads the student's 100-token training record into the first message (the app-loaded design from the notes section).

  1. Call 1. Input is 1,000 (system prompt and tool definitions) + 100 (record) + 20 (question) = 1,120 tokens. The model outputs a search_manual call, 60 tokens. The program runs it and gets a 600-token passage. Why: the model needs the training rule, and it is not in context, so it fetches it.
  2. Call 2. Input is 1,120 + 60 + 600 = 1,780. The model sees the passage and the record, compares them, and outputs a check_calendar call, 50 tokens. The result is 200 tokens. Why a tool here: the calendar changes, so it must be fresh, never remembered.

Pause. Before reading on, work out what is in step 3's input and how big it is. Write the formula from the resending section.

Check your pause

Step 3's input is everything from call 2 (1,780) plus its 50-token output plus the 200-token result: 2,030 tokens. It contains the system prompt, the record, the question, the manual passage, and the calendar result.

  1. Call 3. Input 2,030. The model outputs a book call, 50 tokens, and the result is 40 tokens: "booked, Friday 2 pm".
  2. Call 4. Input is 2,030 + 50 + 40 = 2,120. The model writes the final answer, about 100 tokens, and the loop ends.

The program's messages list at call 1, as Python:

[
  {"role": "user", "content":
     "Training record: laser cutter level 2.\nAm I allowed to use the laser cutter, and book it Friday?"}
]

And at call 3, after two tool round trips (long text shortened):

[
  {"role": "user", "content": "Training record: ... Am I allowed ...?"},
  {"role": "assistant", "content": [{"type": "tool_use", "id": "t1",
     "name": "search_manual", "input": {"machine": "laser cutter", "query": "who may use it"}}]},
  {"role": "user", "content": [{"type": "tool_result", "tool_use_id": "t1",
     "content": "(600-token passage on training levels)"}]},
  {"role": "assistant", "content": [{"type": "tool_use", "id": "t2",
     "name": "check_calendar", "input": {"machine": "laser cutter", "day": "Friday"}}]},
  {"role": "user", "content": [{"type": "tool_result", "tool_use_id": "t2",
     "content": "(200 tokens of open slots)"}]}
]

Total. Input over the four calls is 1,120 + 1,780 + 2,030 + 2,120 = 7,050 tokens. Now compare the lazy design that pastes the whole 40,000-token manual into the context. Each of the four calls carries it, so that is 4 x 40,000 = 160,000 extra input tokens, and, because of context rot, probably worse recall. Billing is per input and output token, so that difference is real money, even though no price is quoted here.

After the answer. The app writes a short note, for example "booked laser cutter Friday 2 pm for Sam". If the chat continued, the 600-token passage would be cleared first, since its job is done. Notice what is dropped (nothing yet, until clearing), what is kept in context (the full list, resent), and what is saved (the note). The open slots are not saved, because they would be stale.

What if the student asks a follow-up? Say the student then asks "and what lens does it use?" Call 5 would carry 2,120 plus the 100-token answer plus the new question, and the program should first clear the 600-token passage, replacing it with its 40-token summary, so the call carries about 1,660 tokens of old history instead of 2,220. If the lens question needs the manual, the model searches again and gets a fresh passage.

Show the model answer

Call 2. Input is 1,125 + 60 + 500 = 1,685. The model has the filament passage and outputs check_calendar, 50 tokens; the program runs it and returns 150 tokens.

Call 3. Input is 1,685 + 50 + 150 = 1,885. The model outputs a book call, 50 tokens, with a 40-token result, so call 4 would carry 1,975 and give the final answer including the filament.

Decisions. Keep: the system prompt, record, question and the whole list while the conversation runs. Clear: the 500-token passage once the filament answer is given, if the chat continues; compaction is not needed yet, since the history is about 2,000 tokens. Note: at most a one-line note that the instructor booked the 3D printer, because a booking is a past event, while the free slots are never saved. Retrieve fresh: the manual passage and the calendar, each by a tool call at the moment they are needed.

Extra case. The instructor's class size is needed at every visit and is 10 tokens: load it up front, with the record, rather than fetching it each time. For compaction, suppose the chat runs on and the history reaches 4,000 tokens, mostly three used tool results. Clearing the results first (say 1,200 tokens, replaced by 100 tokens of summary) frees about 1,100; only if it is still too big do you compact the whole history to, say, 300 tokens, and keep the notes file as the record that survives.

Summary 2 min

  • The model sees only the context of this call; calls are stateless, so the program resends the messages list and the input grows each step.
  • Three places hold information: context (this conversation), saved notes (between sessions), retrieved sources (fetched on demand).
  • Keep what is needed now; clear a spent tool result; compact a long conversation that still matters.
  • Write a note for durable facts such as training status; never for fast-changing ones such as the calendar.
  • Retrieve big or rarely needed material, such as manual pages, instead of pasting it in; you pay per token, and more tokens also mean worse recall.
