Lesson 1 · 30 minutes

Context and memory: what the makerspace assistant keeps, saves and looks up

By the end of this lesson you can decide what the makerspace assistant keeps in context, what it saves between sessions, and how it finds a manual page, and justify each choice with cost.

Objective O3: context and memory About 30 minutes
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both jobs are memory design, and a bad design makes the assistant slow, expensive and wrong.

The big picture is short. In the API, the history is sent again with every turn, so at each step the model knows only the text in that one call (Context windows docs). Memory design is therefore the job of deciding what text to send. Every token you send costs money and spends some of the model's attention.

We go in this order: what context is, why it grows, how to shrink it, what to store outside it, and how to find one page in a long manual.

Warm-up 2 min

Two ideas from earlier sessions matter here. A language model takes text in and writes text out. An agent is a loop: the model asks for an action, the program carries it out, the result comes back, and this repeats until the task is done.

What the loop does not show is that each pass through it is a separate call to the model. Take the question "Is the laser cutter free Friday?" and trace it as two calls.

  • Call 1. The program sends the instructions and the student's question. The model replies with a request to run the calendar tool for Friday. It has not answered anything yet.
  • Call 2. The program runs the calendar tool, gets "booked 10:00 to 12:00, free after 12:00", and calls the model again. Only now can the model write the answer.
Recall

When the program makes call 2, what must the text of that call contain for the model to answer correctly? Decide before you open the answer.

Check your answer

Four things: the instructions and tool definitions, the student's question, the model's own tool request from call 1, and the calendar result. The model kept nothing from call 1, so if the program left out the question or the result, the model would have nothing to answer from. If you said "just the result", that is the usual slip: the result alone does not say what it is a result of. The rest of this lesson follows from that fact.

Tokens and the window 3 min

The model reads and writes tokens, which are chunks of text: a short word, part of a long word, or a punctuation mark. Context is the set of tokens included when the model generates its output (Anthropic Engineering). Whatever is in that set is all the model has. Anything else, including a chat from yesterday, does not exist for it.

The context window is the limit on how much text the model can reference in one call, and it includes the model's own response. It counts everything you send: the system prompt, the messages, the tool results and the tool definitions (Context windows docs). Window size depends on the model, from 200 thousand tokens on some up to 1 million on others, so check the docs for the model you use rather than memorizing one number.

A rough picture of tokens, labelled approximate because real tokenizers split text differently:

Manual sentence:  Clamp the acrylic sheet before you start cutting.
Rough tokens:     Clamp | the | acryl | ic | sheet | before | you | start | cut | ting | .

That is about 11 tokens for 8 words, so tokens run somewhat above the word count. For planning, this lesson uses an illustrative rule of thumb: one manual page is about 1,500 tokens. It is an invented round number for doing arithmetic, not a measured figure. Measure with your model's token counter before you rely on any real number.

Why does this matter for a makerspace? A student's question is short, usually under 100 tokens, but the system prompt, tool definitions and every result count toward the same window. The text you add around the question is what fills it, so it is also what you control.

A common mix-up

"The model remembers our earlier chats by itself." It feels true because chat apps show your old messages and the replies stay consistent. But the model only has its trained knowledge plus the text given in this call. If an earlier chat appears to be remembered, the program put it back into the text. Between sessions shows how.

Estimate

The laser cutter manual is 40 pages. Using the illustrative 1,500 tokens per page, roughly how many tokens is it?

Show the answer

40 x 1,500 = 60,000 tokens. If you got 40,000 or 6,000, you used the wrong page size or dropped a zero. Keep the units in the multiplication.

Why cost grows per step 4 min

Because the model keeps nothing, each turn's input is all the previous conversation history plus the new message, and the previous turns are preserved completely. The output of one turn becomes part of the input of the next (Context windows docs). In an agent loop, a step is a call, so every step resends everything that came before it.

Resent history is input the provider counts as tokens. The docs say so explicitly for kept thinking blocks, "billed as input tokens, like the rest of the conversation history", but they give no per-step formula. The sums below are our own arithmetic on invented numbers.

Worked example (all numbers invented, for illustration)

The system prompt is 1,000 tokens and the student's question is 100. Each step then adds 500 tokens of results to the history. Over 4 steps:

  1. Step 1 sends 1,000 + 100 = 1,100 tokens.
  2. Step 2 resends all of that and the 500 new tokens: 1,600.
  3. Step 3: 2,100. Step 4: 2,600.
  4. Total input across the four calls: 1,100 + 1,600 + 2,100 + 2,600 = 7,400 tokens.
  5. At an invented price of $3 per million input tokens, 7,400 tokens cost 7,400 x 3 / 1,000,000 = $0.0222, about 2.2 cents.

The point is that cost is a sum of growing contexts, not the size of the last one. The last call was 2,600 tokens, yet you paid for 7,400. Doubling the steps more than doubles the bill, because each new step is bigger than the one before.

Notice what changes between steps. Steps 1 to 4 each add 500 tokens, so every later call carries all earlier results again. A result that enters the history at step 2 is paid for in steps 2, 3 and 4, while one that enters at step 4 is paid for once. Big results that arrive early are therefore the expensive ones, which is why Between steps is about getting rid of them. If the numbers were real, you would measure them from the usage figures your API returns instead of estimating.

Prompt caching changes what you pay for repeated tokens, not whether they count toward the window (Context windows docs). This lesson does not teach it; read the docs when you start optimizing a real bill.
Compute

Keep the same numbers and add a fifth step. What is the input size of step 5, and what is the 5-step total?

Show the answer

Step 5 is 2,600 + 500 = 3,100 tokens. The total is 7,400 + 3,100 = 10,500 tokens, which is about 3.2 cents at the invented rate. A common slip is to answer 5 x 500 = 2,500 for the total, which counts only the new results and forgets that every call also resends the 1,100 base and all earlier results. Another is to give 3,100 as the total, which is the last call only. The fix: write each step's size on its own line, then add the lines.

Attention budget and context rot 2 min

Money is not the only cost. Models have what Anthropic calls an attention budget: as the number of tokens grows, accuracy and recall degrade, a phenomenon known as context rot (Anthropic Engineering). The page gives two reasons. Every token attends to every other token, so the number of pairwise relationships grows with the square of the length and attention is spread thinner. And models see fewer long sequences than short ones in training, so they are less practiced at them. Managing this is context engineering: curating what goes in the window. The practical rule is to aim for the smallest possible set of high-signal tokens that maximize the likelihood of the outcome you want.

Picture the same three facts in two calls: the laser cutter's maximum acrylic thickness, the Friday booking rule, and the student's training status. In call A they sit in a 2,000-token context with nothing else. In call B they are buried in a 60,000-token context that also holds the whole manual. The facts are identical, but the model has far more irrelevant text to weigh in call B, and the guidance above says recall gets less reliable as that text grows. This is a direction, not a measured number, and we invent no statistics for it.

This idea is why the next three sections exist: clearing, saving and looking things up all keep the window small and relevant.

Check yourself

A teammate says: "The manual is 60,000 tokens and the window is bigger than that, so we are fine." Why is that not enough?

Show the answer

The third option. A window limit says what fits, while cost (see Why cost grows per step) and context rot (this section) both scale with how much you send.

Between steps 3 min

Within one session, tool results stay in the history, so each result is resent at every later step. Most of them are only useful once. The lightest fix is tool result clearing: once the model has used a result, the program removes the raw output from the history. Anthropic describes this as one of the safest and lightest forms of compaction (Anthropic Engineering).

The heavier fix is compaction: when a conversation nears the window limit, the model summarizes it and a new window starts from that summary. The idea is general; the docs also describe a server-side feature for it, but this lesson teaches the idea, not that feature (Context windows docs). A summary loses detail, so you choose what it must keep: decisions and unresolved problems, not raw output.

Example. The assistant fetches a manual page of 1,200 tokens to find the maximum acrylic thickness. The model reads it and says 6 mm. After that, the program clears the page and keeps a one-line note: "Laser manual p. 14: max acrylic 6 mm." The next steps resend about 50 tokens instead of 1,200, and the model still has the fact it needs. If the student later asks something the note does not cover, the assistant can fetch the page again.

One more tool exists for large jobs. A sub-agent is a separate model run with its own clean window that explores a topic and returns a condensed summary, often 1,000 to 2,000 tokens, to the main agent. We only name it here; several agents working together come later.

Compaction can be costed. Take a 20,000-token troubleshooting chat compacted to a 1,000-token summary (invented figures). Each of the next 5 steps resends 1,000 tokens instead of 20,000, which saves 5 x 19,000 = 95,000 input tokens, minus one extra call to write the summary.

Clearing has a price too. Once the page is gone, the model cannot quote it, and a follow-up such as "what about 8 mm acrylic?" needs another fetch. So clear results that are bulky and unlikely to be reread, and keep short ones the next steps depend on.

Choose

For each case, pick clearing or compaction, then open the answer.

  1. A 1,200-token manual page was used once to answer one question, and the conversation is short.
  2. A long troubleshooting chat with a student is near the window limit, and the early turns hold decisions the later turns depend on.
Show the answers

Case 1 is clearing: the raw page has done its job, so drop it and keep a one-line note. Compacting a short conversation would add a summarizing call and risk losing detail for no gain. Case 2 is compaction: the conversation itself is the problem, not one bulky result, and clearing results would not remove the long early turns. If you chose clearing for case 2, you fixed the wrong thing: there is no single result to remove.

Between sessions 3 min

Everything so far lives in one window. When the session ends, that window is gone. The model holds nothing, so nothing persists unless your program saves it. The pattern is structured note-taking: the agent regularly writes notes that are persisted to memory outside the context window, and those notes are read back in later (Anthropic Engineering).

For the makerspace, the clear candidate is each student's training status. Keep a small file per student, for example students/riley.json, holding which machines they are trained on and the date. It is small, it changes rarely, and the assistant needs it every visit.

The flow in a real visit goes like this. At session start the program reads students/riley.json and inserts "Trained: laser cutter (2025-10-02); not trained: CNC router" into the first call. During the session the model can answer a question about permissions from that line. When a student finishes a new training, the program writes the updated file. Next week's session reads it again.

Keep the saved note small and structured. A line such as "laser: trained 2025-10-02" costs a few dozen tokens each visit, while a transcript of the whole last session could cost thousands and would dilute the context (see Attention budget). Decide what a future session will need to act on, and write only that. Anything the model could look up again, such as a manual page, should stay in its source file and not be copied into the notes.

A common mix-up

"If the assistant saved a note, it will see it next time." Saving only puts text on disk. The model sees it only if the program reads the file and puts it into the call. A note that nothing loads is the same as a note never written.

Your turn

For the training-status file, state what gets written, what reads it, and when. Then open the answer.

Show the answer

Written: the student's trained machines and dates, by the program when a training is recorded. Read: by the program, at the start of each session, which then inserts one short line into the first call. If you left out the reader, the note is never seen. If you wrote the whole conversation, that is the wrong thing to save: you pay to reload it forever, and the status line is all the model needs.

Finding the right page 4 min

Back to the 40-page manual. There are two ways to get the right page to the model. Upfront retrieval means the program prepares data before the model starts and puts it in the first call. Just-in-time retrieval means the agent keeps lightweight references, such as file paths, saved queries or links, and uses tools to load data into context only when it needs it (Anthropic Engineering).

Upfront is fast, because the lookup happens once before the model runs, and it suits data that is small and always needed. It spends tokens on data you may not use. Just-in-time keeps the window small and lets the agent follow what it finds, but each lookup is an extra step, and the agent needs a sensible tool and some guidance on where to look. The article describes a hybrid as often best, and Claude Code works that way: CLAUDE.md files are loaded up front, while tools like glob and grep let the agent explore and fetch files just in time (Anthropic Engineering).

Mapped to the makerspace, a just-in-time design keeps a list of manual paths in the system prompt, say manuals/laser-cutter.md, and gives the model a search tool. A question about acrylic thickness leads the model to call the search tool, which returns the matching page, and only that page enters the window. The other option is an embedding lookup, where the program finds pages whose meaning is close to the question and inserts the best few before the model runs. That is upfront retrieval: it saves the model a step, but the program decides what the model sees, and a wrong match means the right page never arrives.

On "What is the maximum acrylic thickness?", the embedding lookup makes one call of about 4,500 illustrative tokens (three pages inserted). The search tool makes two calls, about 2,100 and 3,400 tokens, with only one page. Neither is always better: the tool design needs good descriptions of where things live, and the embedding design needs a lookup you can trust.

A useful test is to ask what happens when the lookup is wrong. If the program picks the wrong pages, the model usually cannot tell and answers from what it was given. If the model picks the wrong search term, it can see the result is off and try again. That recovery is the strength of just-in-time retrieval, and it is paid for with extra steps, each of which resends the history (see Why cost grows per step).

Check yourself

Which design suits each item: (a) the 40-page laser manual, (b) the makerspace's three safety rules every student must hear, (c) Friday's laser cutter bookings? Pick the best match.

Show the answer

The second option. Choose by size and how often the data is needed: large and occasional goes just-in-time, small and always needed goes upfront, live data is fetched by a tool when asked (that is just-in-time too). In practice you combine them.

Worked example 3 min

The request is "Book the laser cutter Friday 2pm and tell me the max acrylic thickness." All numbers here are invented for illustration. The base context is 2,000 tokens of system prompt and tool definitions plus a 100-token question, so 2,100 tokens. Price: an invented $3 per million input tokens.

Design A: paste the whole 60,000-token manual

The first call already holds 62,100 tokens. Then each step adds its result and resends everything.

  1. Step 1: 62,100 (the model asks for the student's training notes).
  2. Step 2: 62,500 (training notes, +400; the model asks for the calendar).
  3. Step 3: 63,000 (calendar, +500; the model books the slot).
  4. Step 4: 63,250 (booking confirmation, +250; the model answers).

Total: 62,100 + 62,500 + 63,000 + 63,250 = 250,850 input tokens, about 75 cents at the invented rate.

Design B: retrieval of one page

Design B starts with just the base, 2,100 tokens. It has one more step, because the model has to fetch the manual page.

Before you read the next line, predict step 3. Step 2 held 2,500 tokens, and the manual page is 1,200 tokens plus about 100 for the search request.

Show step 3 and the rest

Step 3 is 2,500 + 1,300 = 3,800 tokens. The sizes are step 1: 2,100; step 2: 2,500 (training notes); step 3: 3,800 (manual page); step 4: 4,300 (calendar, +500); step 5: 4,550 (booking, +250). Total: 17,250 tokens, about 5 cents. If you predicted 2,500, you forgot that a result enters the history and is resent from then on.

Read the two totals as a pair. Design A pays for the manual four times over, 4 x 60,000 = 240,000 of its 250,850 tokens. Design B pays for one page three times, 3 x 1,300 = 3,900 tokens. The only thing the extra step changed was which tokens were allowed into the window.

Design B is about 14.5 times cheaper (250,850 / 17,250), and each call has less irrelevant text, so less context rot. Now add clearing from Between steps: clear the 1,200-token page after the model has read it. Steps 4 and 5 each drop by about 1,200, to roughly 3,100 and 3,350, so the total falls by about 2,400 to roughly 14,850 tokens. The extra step in B costs you latency; weigh that against the saving.

Faded practice 4 min

New scenario. A student returns a week later. They ask the assistant to cancel their 3D printer slot, and to tell them whether they may use the CNC router. Design the memory for this visit in three decisions. The first is solved, the second is half solved, and the third is yours.

Decision 1: what to save (solved)

Save the training status per student, in a small file such as students/riley.json, and have the program load it at session start. Reason: the CNC question cannot be answered without it, the model remembers nothing between sessions, and the file is tiny, so loading it each visit costs only a few hundred tokens against a manual's tens of thousands.

Decision 2: what stays in context (half given)

The cancellation needs a calendar lookup, and the model reads the student's booking from the result. The status file stays in context for the whole visit, since the CNC answer depends on it. Your part: the calendar result is a few hundred tokens and the cancellation is confirmed. Do you clear it, and why?

Compare with these criteria

A good answer says whether the result is still needed and ties the choice to cost. Clearing is reasonable once the cancellation is confirmed and nothing later depends on the raw output; keep a one-line note such as "3D printer slot Thu 4pm cancelled". If your visit is just two or three more steps, the saving is small, and keeping the result is also defensible. A weak answer says "clear it" or "keep it" with no reason. Also check that you counted resends: a 300-token result kept for three more steps costs about 900 extra input tokens, small next to a manual page but not nothing.

Decision 3: finding the page (yours)

The student asks about the CNC router, which has its own safety manual. Write how the assistant finds the right page, and add one sentence on what it costs compared with pasting the manual.

Check against these criteria

Your answer should name the approach (just-in-time: a path to the CNC manual in the system prompt plus a search tool, or an embedding lookup upfront), say that only the matching page enters the window, and give a cost sentence in tokens: one page of about 1,500 tokens is resent for a few steps, against a whole manual resent at every step. Check that your cost sentence says the cost is per step, not once. If you wrote "it is cheaper" with no reason, add the reason.

Summary 2 min

  • Context: keep only the smallest set of high-signal tokens in the window, because every step resends it and recall degrades as it grows. Clear used results, compact long chats.
  • Saved memory: write durable facts, such as training status, to a file outside the window, and make the program load them next session.
  • Finding a page: keep paths and a search tool, load a page when asked, and put small, always-needed data upfront.

Say it in your own words: why does pasting a whole manual cost far more than its size suggests, and what do you do instead?

The three decisions share one test. For any piece of text, ask how many times it will be resent, whether the model needs it that often, and whether a cheaper route exists: a one-line note instead of a page, a file instead of a transcript, a lookup instead of a paste. If the answer to the second question is no, the text does not belong in the window at every step.
