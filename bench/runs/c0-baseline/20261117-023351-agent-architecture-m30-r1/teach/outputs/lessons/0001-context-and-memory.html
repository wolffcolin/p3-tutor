Context and memory in an agent

What the model sees: the context window 5 min

Start with a small example. You ask a friend to help plan a project, but your friend has a strange rule: they can only look at one sheet of paper, and they have no memory except what is written on it. Each time you talk, you hand them the sheet. If something is not on the sheet, they do not know it.

A language model works like this friend. The context is everything the model is given for one call: the text it reads and the text it writes. The context window is the limit on how much that can be. Anthropic's documentation calls it the model's "working memory" and says it is the text the model can reference when generating a response, including the response itself (Anthropic: Context windows).

Context is measured in tokens: small pieces of text, often a short word or part of a word. For English, a rough guide is that a token is a bit less than one word. You do not need the exact count by hand; the API reports it for you.

What goes into the context for your makerspace assistant? According to the same documentation, everything in the request counts: the system prompt, every message including tool results, your tool definitions, and the output the model generates.

Notice two things. First, your own tool descriptions from the agent-loop lesson take up room in every call, so a long, rambling description is paid for again and again. Second, the window is a shared limit: the more the assistant reads, the less space is left to write.

Current models have large windows. Anthropic's documentation lists 1M tokens for its latest models, but says plainly that "more context isn't automatically better" (Anthropic: Context windows). We come back to that in a few minutes.

What is kept between steps 6 min

Here is the idea that surprises most people: the model keeps nothing between calls. Each call starts blank. What looks like memory inside one conversation is the program re-sending the earlier text every time.

The documentation describes it this way: each turn's input contains "all previous conversation history plus the current user message", and the model's output "becomes part of the input for the next turn" (Anthropic: Context windows). In an agent loop, a tool result counts as one more message added to that history.

That means the "state" of an agent between steps is a list of messages that your program holds and grows. In Python terms, it is a list you append to:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # whole list sent every time
    messages.append(reply)                               # keep what the model said
    if reply is a final answer:
        break
    result = run_tool(reply)                             # the program runs the tool
    messages.append(result)                              # keep what came back

Because the whole list goes out on every call, each call is billed for all of it again. Think of a taxi that charges you for the whole route every time you stop, not only for the new stretch. A long run is expensive not because of the last step but because the early steps are paid for repeatedly. Anthropic notes that kept history is billed as input tokens, like the rest of the conversation history (Anthropic: Context windows).

Add up the four bars and you get 13,900 input tokens, even though the largest single call is only 5,300. We will check that arithmetic in the worked example.

A common mix-up

"The model remembers the earlier steps because it is the same conversation." It is tempting, because a chatbot feels like one continuous mind. But the model is called fresh each time; the program re-sends the history. If your program forgets to append a tool result, the model will not know it ever asked. This also explains an important design lever: whatever your program leaves out of the list is gone for the model.

More context is not better context 4 min

If everything stays in the list, why not simply give the model everything: all the manuals, all the history? There are two reasons.

Cost. You saw it above: every token in the context is billed on every call.

Quality. Anthropic's engineering team describes context rot: as the number of tokens in the context grows, the model's ability to accurately recall information from it goes down. They treat context as "a finite resource with diminishing marginal returns" and say the goal is "the smallest set of high-signal tokens" that gets the result you want (Anthropic: Effective context engineering for AI agents). It is a gradual decline, not a cliff.

An everyday comparison: an engineer solving a problem is helped by the three data sheets that matter, not by a desk buried under fifty. The skill the engineering team calls context engineering is deciding what goes on the desk.

Two simple tools help when a long run piles up text:

  • Clear old tool results. After the model has used a 3,000-token manual page to answer, the raw page is rarely needed again. The article calls this one of the lightest forms of trimming.
  • Compaction. When the conversation nears the limit, ask the model to summarize it, and start a new context with the summary. It is a trade: the article warns that too aggressive a summary can drop a detail that matters later.
Anthropic also offers server-side compaction and context editing in its API, so you may not have to write these yourself. Check the current context windows page when your team picks tools.

For a makerspace question-and-answer assistant, most conversations are short, so you will rarely need compaction. Clearing a big tool result once it has been used is the first thing worth trying.

What is kept between sessions: notes 5 min

Now the second half of your mission question. A student finishes their laser cutter training on Monday. On Friday they come back and open a new chat. The assistant's context list is empty: a new session starts with a new list. How does the assistant know about Monday?

It does not, unless something was saved outside the model and the assistant can read it. This is memory in the practical sense: information written to storage that the agent can load into its context later. The Anthropic engineering article calls the pattern structured note-taking: the agent writes notes to persistent storage outside the context window and reads them back later. Their example is an agent that keeps a NOTES.md file or a to-do list, and after its context is reset reads the notes to continue (Anthropic: Effective context engineering for AI agents).

For your assistant, there are two kinds of memory to think about:

KindExampleWhere it lives
Facts about a student"Laser cutter training done on Monday; 3D printer not yet"A database or file, read and written through tools
Working notes in a long task"Checked calendar; Friday 2 pm free; still need to confirm training"A notes file the agent updates as it goes

The first kind is probably already in a system your makerspace has, such as a sign-in or training log. Then the right design is a tool, check_training_record(student_id), rather than anything clever. The model asks, the program looks up the record, and only that one record enters the context.

Two design questions for any piece of saved memory: what to write (only what will help next time, such as training status, not whole conversations) and when to read it (load only what this request needs, because it costs tokens and adds noise). Anthropic also offers a memory tool, a file-based system for this pattern (Anthropic: Memory tool), but the idea works with a plain table and two functions.

A common mix-up

"A bigger context window gives the assistant memory." It is tempting, because a bigger window holds more text. But the window is only the space for one session's list. When the session ends, the list is gone, however big the window was. Memory between sessions is storage that you build, plus a way to load it.

Retrieval: finding the right page in a long manual 5 min

The last piece. Your assistant answers from machine manuals, and a manual may run to hundreds of pages. Say a student asks, "How do I change the blade on the band saw?" You could paste every manual into the context. By now you can see why that is a bad plan: it costs tokens on every call, and the context rot effect means the answer may be worse, not better.

Retrieval is the alternative: find the few passages that matter for this question, and put only those into the context. The usual first step is to cut each manual into chunks (a section or a few paragraphs, each labelled with its machine and heading), and then search the chunks when a question comes in.

There are two ways to do the search, and they differ in who decides to search:

ApproachHow it worksTrade-off
Up frontThe program searches with the student's question before the first model call, and puts the best chunks into the context.Fast and simple, but one search with the question as typed; the model cannot refine it.
Just in timeThe model gets a search_manuals(query, machine) tool, and calls it when it needs something, possibly several times.Slower and uses more calls, but the model can narrow the search or try different words.

The engineering article describes the same two options. Many applications retrieve up front, and agents can instead keep lightweight references and load data when they need it. It suggests a hybrid is often sensible and gives advice worth repeating at a design review: "do the simplest thing that works" (Anthropic: Effective context engineering for AI agents). Anthropic's earlier guide to agents makes a similar point: improving a single model call with retrieval and examples is usually enough, so add complexity only when needed (Anthropic: Building effective agents).

How does a search tool decide which chunks match? Two common ways: a keyword search matches the words in the question to the words in the text, which is great for exact terms such as a part name or "M6 collet". A semantic search compares meaning, so "swap the blade" can match a section titled "Blade replacement". Many systems combine them. You do not need to build either today; you need to know the tool's output is what enters the context, so a good result is short and labelled (machine, section title, page number), so the model can cite it and the student can check it.

Worked example and practice 6 min

Worked example

A student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The system prompt and tool descriptions take 1,500 tokens, and the question 50. The model calls check_calendar (a 50-token request; result 400 tokens), then search_manuals (50 tokens; result 3,000), then check_training_record (50 tokens; result 200), then writes the answer. How many input tokens are billed across the four calls?

  1. Call 1 input: 1,500 + 50 = 1,550. The model replies with the calendar request (50 tokens of output).
  2. Call 2 input: everything so far, 1,550, plus the 50-token request and the 400-token result: 2,000.
  3. Call 3 input: 2,000 + 50 + 3,000 = 5,050. The big manual result enters here.
  4. Call 4 input: 5,050 + 50 + 200 = 5,300. The model writes its final answer.
  5. Total: 1,550 + 2,000 + 5,050 + 5,300 = 13,900 input tokens, and the output tokens are billed separately. Why add them? Because each call re-sends the history, so every call is billed for its full input.
  6. Where to save: the 3,000-token page is sent in calls 3 and 4. Returning an 800-token excerpt instead would cut it everywhere it appears.
Your turn

Same run, but search_manuals now returns only an 800-token excerpt. Step 1 is done for you: call 1 input is still 1,550, and call 2 input is still 2,000. Work out call 3 and call 4 inputs and the total.

Show a solution

Call 3 input: 2,000 + 50 + 800 = 2,850. Call 4 input: 2,850 + 50 + 200 = 3,100. Total: 1,550 + 2,000 + 2,850 + 3,100 = 9,500 input tokens, about 4,400 fewer than before. The excerpt saved 2,200 tokens in each of the two calls that carry it. A smaller tool result pays off more the earlier it appears in the run.

Summary 2 min

  • The context window is everything the model reads and writes in one call: system prompt, tool descriptions, messages, tool results and output.
  • The model keeps nothing between calls; the program re-sends the growing message list, and you pay for all of it each time.
  • More context is not better: it costs more and recall can degrade, so keep the smallest useful set and trim large results.
  • Between sessions, memory is storage outside the model (records, notes) that a tool reads back into a fresh context.
  • Retrieval puts only the relevant chunks of a long manual into the context, up front or through a search tool.
