Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can say, for the makerspace assistant, what sits in the context window at each step, what survives between steps and between sessions, and when to retrieve a page of a manual instead of loading the manual.

Why this matters for you

The context window, and why it costs money 6 min

Start with a concrete case. Your assistant is called with this text:

[system prompt: "You are the makerspace assistant..."]   ~500 tokens
[tool descriptions: check_calendar, book, search_manuals] ~1,000 tokens
[student]: Is the laser cutter free on Friday?             ~12 tokens

The model reads all of that and writes a reply. A token is the chunk of text the model reads and writes: roughly a short word or part of a word. The context is the set of tokens the model is given when it writes a response, and the context window is the limit on how many tokens that can be. Anthropic defines context in the same way: the tokens included when the model samples a response (Anthropic, Effective context engineering for AI agents).

The key fact for design is this: the model has no memory of its own between calls. Every call starts from nothing except the text you send. If the model should "remember" the student's question on the next step, your program has to send the question again. Whatever is not in the context, the model cannot use.

Why this drives cost

You pay for the tokens you send in and the tokens the model writes. Because each call re-sends the whole context, a long context is paid for again on every step. This is the link between today's topic and your small budget: cost per request is roughly the sum of the context sizes over all the model calls in that request, plus the output.

Why a bigger window is not the answer

It is tempting to say "just pick a model with a huge window and paste in every manual." Two problems. First, cost, as above. Second, quality: Anthropic reports that as the number of tokens in the window grows, the model's ability to recall information accurately from it decreases, which they call context rot, and that the effect shows up in all models to some degree. Their guidance is to find the smallest set of high-signal tokens that gets the job done (same source). Context is a budget to spend, not a bucket to fill.

A common mix-up

"A bigger context window means the assistant can know everything." It is tempting because the window sounds like the model's brain. But the window is only the text sent this call. It is paid for each call, and recall gets worse as it fills. A big window raises the limit; it does not remove the need to choose what goes in.

What is kept between steps 6 min

Now watch one request through the loop you already know. Here is what the program sends on each model call for "Is the laser cutter free Friday, and do I need training?"

CallContext sentModel writes
1system + tools + questionrequest: check_calendar(laser, Friday)
2call 1 + the request + the calendar resultrequest: search_manuals("laser training")
3call 2 + the request + the manual passagefinal answer

Nothing is kept inside the model. What is "kept between steps" is the list of messages your program maintains and re-sends. Each step appends to it: the model's tool request, then the tool's result. The context therefore only grows during a request, and the later calls are the expensive ones.

In a short request that is fine. In a long one, such as an agent working for 40 steps, old tool results pile up and most are no longer useful. Two standard remedies, both described by Anthropic:

  • Clearing old tool results. Once the assistant has used a calendar result, remove it from the list. Anthropic's context editing feature does this automatically as the window nears its limit; in their 100-turn web-search test, it let runs finish that otherwise failed from running out of context, with 84% fewer tokens used (Anthropic, Managing context on the Claude Developer Platform).
  • Compaction. When the conversation nears the limit, ask the model to summarize it and start a new window from the summary. The summary keeps decisions and open problems and drops redundant output (Anthropic, context engineering).
Compaction is lossy: a summary can drop a detail you later need. The cheap, safer first move is to clear tool results that have already been used.

For your assistant, most requests are three to five calls, so you may never need compaction. But you do need to know that tool results are the part of the context you control most. A tool that returns an entire month of bookings when the question was about Friday is spending your budget on every later call.

Check yourself

check_calendar returns all 200 bookings for the week as raw text, about 3,000 tokens. The request then takes five more calls. What is the best fix?

Show the answer

Make the tool return less. Anthropic's advice is that tools should return token-efficient information (source).

What is kept between sessions: notes 6 min

A session is one conversation: from the student's first message to when it ends. When it ends, the list of messages is gone, unless your program saved it. The next time Sam visits, a bare assistant starts with only the system prompt and tools. It does not know Sam finished laser cutter training last week.

A common mix-up

"The assistant automatically remembers earlier conversations, like a person." It is tempting because chatbot products appear to do this. But the model itself keeps nothing; any such memory is something the product's program saved and put back into the context. In your assistant, you build it or it does not exist.

The simplest way to build it is notes: the program stores facts outside the context window, in a file or database, and loads the relevant ones into a later context. Anthropic calls this structured note-taking, or agentic memory, and gives examples such as a to-do list or a NOTES.md file that an agent writes and rereads after its context is reset (Anthropic, context engineering). Their memory tool works this way: the model can create, read, update and delete files in a memory directory, the files persist across conversations, and the developer's own code stores them, so you choose where the data lives (Anthropic, context management).

Two design choices matter more than the technology.

  • What to write. Facts that stay true and will be needed again: training status, a student's preferred machine. Not the whole transcript, which would only refill the window with noise.
  • What to read back, and when. Loading every note into every session spends tokens on every call. Load the small, always-needed note at the start (the student's training status), and let the model look up the rest through a tool when needed.

There is also a trust question. A note is only as good as when it was written: if the training status changes in the booking system, a stale note will be wrong with full confidence. For facts that have an authoritative source, such as the calendar, store a pointer and call the tool again instead of saving a copy.

Retrieval: finding the right page in a long manual 6 min

Notes are memory about people and progress. The manuals are knowledge about machines, and they are too long to load every call (you worked out why in the first section). The answer is retrieval: fetch only the passages relevant to this question, and put just those into the context.

Anthropic describes the pattern as just-in-time context: the agent keeps light references, such as file names or stored queries, and loads the content through tools when needed, rather than loading everything first. The cost is some extra steps at run time, so many systems mix the two: a small amount up front, the rest on demand (Anthropic, context engineering).

A common way to build it is as follows, shown with your manuals:

  1. Split each manual into chunks, such as a section or a few paragraphs.
  2. Index the chunks so that they can be searched: by keywords, by embeddings (numbers that let a program find text with a similar meaning), or both.
  3. Expose a search_manuals(query) tool that returns the best few chunks.
  4. The model calls it like any other tool, and the chunks come back into the context.

Chunking has a catch. A chunk cut out of its manual can lose what it was about: a paragraph saying "set the power to 40%" does not say which machine. Anthropic's Contextual Retrieval fixes this by adding a short explanation of where the chunk comes from before it is indexed, and reported that this cut failed retrievals by 35% with embeddings alone, and by 49% when also combined with keyword search (Anthropic, Introducing Contextual Retrieval). A cheap version for your team: start every chunk with its machine name and section title.

A common mix-up

"Retrieval means the model searches the manual itself." It is tempting because the model seems to "look things up". But, as in the loop you already know, the model only writes a request, search_manuals("laser focus"). Your program runs the search and returns text. Whether the right page is found depends on your chunks and index, not on the model's cleverness; if the page was never retrieved, the model cannot see it.

Retrieval can fail in two ways that you can test separately: the right chunk was not returned (a search problem), or it was returned and the model ignored or misread it (a context problem). When an answer is wrong, check which one it was before changing anything.

Worked example and practice 4 min

Worked example

Design decision: Sam, a returning student, asks "What speed do I use to engrave acrylic?" Decide what goes in the context, what is saved, and what is retrieved.

  1. Always in context: the system prompt and the three tool descriptions. They are the same on every call, so keep them short; each word is paid for on every step.
  2. Loaded at session start from notes: "Sam: laser training complete". It is small and decides what the assistant may help with, so it is worth carrying from the start.
  3. Retrieved on demand: the model asks search_manuals("laser engrave acrylic speed") and receives, say, one 1,500-token chunk headed "Laser cutter: Materials".
  4. Count the cost (illustrative numbers): base context of 2,050 tokens. Call 1 sends 2,050. Call 2 sends 2,050 plus the request and the 1,500-token chunk, about 3,650. Total input is about 5,700 tokens. Pasting the 30,000-token manual instead would make it about 2 x 32,050 = 64,100.
  5. Saved after the session: nothing new, unless Sam states a stable preference. The speed setting is looked up again next time, because the manual is the source of truth.

Summary 2 min

  • The model keeps nothing between calls. The context window holds what the program sends this call, and it is re-sent and paid for every step.
  • Within a request, the context only grows. Keep tool results small, clear used ones, and compact only if a request runs long.
  • Between sessions, only what the program saves survives. Save stable facts as notes, and look up live data and long documents.
  • Retrieval puts one relevant chunk of a manual in the context instead of the whole manual; the model requests it and the program runs it.
