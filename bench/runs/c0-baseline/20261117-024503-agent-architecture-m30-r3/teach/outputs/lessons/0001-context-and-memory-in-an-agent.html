Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it goes in the context window, in a saved note, or in a searchable manual, and say why.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Those are three memory decisions, and each one changes both the quality of the answers and the cost of every request. You will defend them at your design review.

Warm-up 2 min

Recall

From the agent loop: a student asks, "Is the laser cutter free tomorrow?" Without looking back, say what the model outputs when it decides to check the calendar, and what the program does with the answer from the tool.

Check your answer

The model outputs a request naming the tool and its arguments (for example check_calendar("laser cutter", "tomorrow")); it does not run anything. The program runs the tool and sends the result back to the model as part of its next input, then calls the model again. That last phrase matters today: "part of its next input" means the result is added to the context.

The context window 6 min

Start with a concrete case. A student types: "How do I change the blade on the band saw?" Before the model writes one word, the program has to decide exactly what text to hand it. That text might be:

  • the assistant's instructions (the system prompt: its role and rules),
  • the descriptions of its tools,
  • the student's question,
  • and anything the assistant has already collected, such as a manual page.

All of that text, plus the answer the model is writing, is the context window: everything the model can reference when it generates a response. The Claude documentation calls it the model's "working memory", and it counts the system prompt, every message, tool results and tool definitions, and the model's own output (Claude docs: Context windows).

The window is measured in tokens, the small pieces of text a model reads and writes: a short word is often one token, a long or rare word several. Two facts follow from that, and both matter for your budget:

  1. There is a size limit. Current Claude models have windows of up to 1 million tokens, depending on the model (same page). That is large, but a set of long manuals, a long chat and many tool results can fill it.
  2. You pay for what you send. Usage is counted in tokens, and every request reports what it consumed. So a bigger context is a bigger bill, on every single model call.
A common mix-up

"The model has read the manuals, so it knows them." It is tempting because a chatbot answers fluently about all kinds of topics. But what the model learned in training is not your manuals; the context window is separate from the large body of data it was trained on (Claude docs). If a page about your band saw is not in the window, the model cannot read it, and it may produce a confident, plausible and wrong answer. This is the outdated-fact problem you noticed in chatbots, seen from the inside.

What is kept between steps 7 min

The agent loop calls the model once per step. Here is the key fact about memory inside a run: the model does not remember the previous step. The program remembers, by building the next request from the history so far. The docs describe it this way: each turn's input contains all previous history plus the new message, and what the model generates becomes part of the input for the next turn (Claude docs).

Worked example: one request, three steps

A student asks: "Is the laser cutter free Friday at 3 pm, and what do I need before using it?" Assume the system prompt and tools take 3,000 tokens, the question takes 40, a calendar result takes 150 and a manual page takes 1,800.

  1. Call 1 sends 3,000 + 40 = 3,040 tokens. The model asks for check_calendar.
  2. Call 2 sends everything again, plus the model's request and the 150-token result: roughly 3,200 tokens. The model asks for search_manuals.
  3. Call 3 sends all of that plus the 1,800-token page: roughly 5,000 tokens. The model writes the answer.

The total sent across the three calls is about 3,040 + 3,200 + 5,000, which is over 11,000 tokens, though the "conversation" holds only about 5,000. Every step re-reads everything before it. A long run is expensive because its cost grows faster than its length.

When the window fills: context rot, clearing and compaction

Two problems appear as a run gets long. One is cost, which you just saw. The other is quality: as the token count grows, accuracy and recall degrade, a phenomenon called context rot. The Anthropic engineering team treats context as a finite resource with diminishing returns, and its goal is "the smallest possible set of high-signal tokens" (Effective context engineering for AI agents). More context is not automatically better.

Two standard remedies, from that same post:

  • Tool result clearing: once a raw tool result has been used, remove it from the history. A 1,800-token manual page the model has already answered from does not need to be resent on every later step.
  • Compaction: when a conversation nears the limit, have the model summarize it, and start a fresh window with the summary. The summary keeps decisions and unresolved problems and drops redundant output.
The docs list server-side compaction and tool result clearing as built-in options for managing context (Claude docs). You do not need them for a first version: makerspace questions are short runs of a few steps.

The first option. Ignoring the page still costs tokens, and a larger window does not remove the page. Clearing it stops the resending.

What is kept between sessions: notes 6 min

Now the second kind of memory. A session is one conversation or run, from the first message to the last. When it ends, the context window is gone. The next time Jordan opens the assistant, the model starts with an empty window: no memory of the laser cutter safety course Jordan finished last week.

A common mix-up

"The assistant will remember the student next time." This is tempting because people remember each other, and chat apps sometimes look as if they do. A model does not keep anything between calls on its own. Remembering across sessions only happens if your program saves something and puts it into the next window. Memory is not automatic; it is something you design.

The simplest design is structured note-taking, which Anthropic also calls agentic memory: the agent writes notes to storage outside the context window and reads them back later (Effective context engineering). The post gives to-do lists and a NOTES.md file as examples. Anthropic's memory tool is a file-based version of this idea.

For your assistant, think of a small record per student, such as this one:

{
  "student_id": "s-4471",
  "trainings": {"laser_cutter": "2026-11-05", "3d_printer": null},
  "notes": "Prefers morning slots."
}

It would work like this. At the start of a session, the program looks up the student's record and puts it into the context (a few dozen tokens). During the session, a tool such as save_training(student_id, machine, date) updates it. At the end, the window is discarded, but the record stays in storage.

One design rule matters for correctness. Facts that the assistant must get exactly right, such as who completed which training, belong in a database that tools read and write, not in a free-text summary the model rewrites. A model summarizing its own notes can drop or garble a detail. Free-text notes suit softer things, such as preferences.

Retrieval: finding the right page 6 min

The third kind of memory is for knowledge too big to fit. Suppose the manuals total 400 pages, about 300,000 tokens. You could paste them all into every request, but that costs a fortune on each call, and context rot makes the answers worse. Instead, keep the manuals outside the window and bring in only the part the question needs. This is retrieval: searching a collection and putting the best matches into the context. Using retrieved text to ground the model's answer is often called retrieval-augmented generation, or RAG.

A chunk is a piece of a document, such as a section of a few hundred words. Chunks are searched rather than whole manuals, because a whole manual is too big to hand over and too broad to rank. A search can match by keywords (for instance, the exact phrase "blade tension") or by meaning, using embeddings: numbers that represent the meaning of a text so that similar meanings land close together. Anthropic's contextual retrieval article describes combining both approaches, and adds a short note to each chunk saying where it came from so that a chunk reading "change it every 40 hours" can be traced to the right machine (Contextual Retrieval).

You can wire retrieval in two ways. In up-front retrieval, the program searches before the model runs and puts the results in the first request. In just-in-time retrieval, the agent keeps lightweight handles, such as file names or saved queries, and loads content during the run through a tool such as search_manuals(query). The Anthropic post says just-in-time retrieval is slower to run and needs good tools and heuristics so that the agent does not waste context, and that a mix of the two often works, for example loading a few key facts up front and fetching the rest on demand (Effective context engineering). Your assistant already has the tool for it: search_manuals.

A common mix-up

"A bigger window replaces retrieval." It is tempting because windows now reach up to 1 million tokens. But filling the window with 300,000 tokens of manuals means paying for all of them on every call, and recall degrades as the context grows. Retrieval keeps the window small, so it is cheaper and often more accurate.

Worked example and practice 5 min

Worked example: where does each item go?

For each item, choose: window (fixed text sent every call), note (saved record, loaded per student) or retrieval (searched on demand).

  1. "You are the makerspace assistant. Never book a machine without training." This is short, needed on every call, and the same for everyone: window.
  2. Jordan completed 3D printer training on 12 Oct. It is specific to one student, must be exact, and must outlive the session: note (a database record, loaded at the start).
  3. The 60-page 3D printer manual. It is big, and any one question needs only a paragraph: retrieval.

Show a solution

(c) Window, since the model needs the description on every call to pick the tool. (d) Retrieval, for the same reason as (a), and even more so, since it is much larger.

Summary 2 min

  • The context window is everything the model sees on a call; it has a limit, and you pay for every token on every call.
  • Between steps, the program rebuilds the history and resends it, so runs grow costly and, through context rot, less accurate. Clear or compact what is no longer needed.
  • Between sessions, nothing is kept unless you save it: notes and records outside the model, loaded at the start.
  • Big knowledge such as manuals stays outside the window and is retrieved in chunks when needed.
