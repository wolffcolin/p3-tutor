Context and memory in an agent

By the end of this lesson you can say what goes into your makerspace assistant's context at each step, what survives to the next student's visit, and which of three tools (trimming, notes, retrieval) to use for each kind of information.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals, and remember each student's training status between visits, on a small budget. Both problems are about context: what the model sees, what it costs, and what you store outside it. At your design review you will need to defend those choices with reasons.

Warm-up 2 min

Recall

From the agent loop: a student asks, "Is the laser cutter free on Friday?" Without looking back, say in one sentence who runs the calendar tool, the model or the program, and where the tool's result goes next.

Check your answer

The program runs the tool, because the model only writes a request for it. The program then puts the result into the next call to the model, so the model can use it. That last part is today's topic: the program decides exactly what text the model gets on each call. That text is the context.

The context window: what the model sees 6 min

Start with a concrete case. A student types: "How do I change the blade on the band saw?" Your program calls the model. What exactly does it send?

It sends one package of text. In it are your instructions to the assistant (the system prompt), the descriptions of your tools, and the student's question. Nothing else is available to the model. It cannot look at your booking system or your manuals unless that text is in the package or a tool fetches it.

The context is the set of tokens given to the model when it generates a reply (Anthropic engineering). A token is a small piece of text, roughly a short word or part of one. The context window is the limit on how much the model can work with in one call. The API documentation calls it a "working memory" for the model, and says it holds the conversation history plus the new output the model generates (Claude API docs: context windows).

Three details matter for your design.

  1. Everything counts. The system prompt, every message, tool results, documents and tool definitions all count toward the window. So does the output the model writes, including any reasoning it writes before answering (API docs).
  2. Tool definitions cost space every time. Ten tools with long descriptions are paid for on every call, even for a question that uses none of them.
  3. Bigger windows exist, but fuller is not better. The docs describe context rot: as the token count grows, accuracy and recall degrade (API docs). Anthropic's engineers describe an "attention budget" that every new token draws down (Anthropic engineering). Their aim is the smallest set of high-signal tokens that gets the job done.
A common mix-up

"The model knows our manuals because we told it about them earlier." Tempting, because a chat feels like talking to someone who remembers. But the model keeps nothing between calls. Each call starts blank, except for the text your program sends. If the band-saw page is not in the package, the model will answer from general patterns, and may state an outdated or wrong procedure with confidence, as you have seen chatbots do.

What is kept between steps 5 min

Now the loop. A student asks: "Can I use the laser cutter tomorrow at 3 pm, and do I need training?" The agent makes several model calls. What does the model see on each one?

The docs say each user message and assistant response accumulates in the window, and previous turns are preserved completely (API docs). In an agent, your program does this. After each step it appends the model's request and the tool's result to a list, and sends the whole list again on the next call. The model has no other way to "remember" step 1 at step 3.

Worked example: the context grows

Suppose the fixed part (system prompt plus tools) is 1,500 tokens, the question is 30 tokens, and each tool result is 800 tokens. These numbers are invented for illustration.

  1. Call 1 sends 1,500 + 30 = 1,530 tokens. The model asks for check_calendar.
  2. Call 2 sends the above plus the request and the 800-token result: about 2,350 tokens (rounding the request away). The model asks for search_manuals.
  3. Call 3 sends about 3,150 tokens. It asks for check_training_record.
  4. Call 4 sends about 3,950 tokens, and the model writes the final answer.

Total sent across the four calls: about 1,530 + 2,350 + 3,150 + 3,950 = 10,980 tokens, though the "new" information was only 2,430. Each step re-sends everything before it, so cost grows faster than the number of steps. This is why a small budget makes you care about context.

Keeping the window from filling up 5 min

Because the program owns the list, the program can edit it. Two common edits:

  • Clearing old tool results. Once the agent has used a 3,000-token manual page to answer, the raw page may no longer be needed. Anthropic calls tool result clearing "one of the safest lightest touch forms of compaction" (Anthropic engineering). The API also offers context editing that clears tool results and thinking blocks (API docs).
  • Compaction. When a conversation nears the limit, summarize it and start a new context window with the summary (Anthropic engineering). The API docs describe server-side compaction as the primary strategy for long conversations.

The trade-off is that a summary loses detail. A good summary keeps decisions, open questions and facts still needed, and drops raw output.

For a makerspace chat, most requests finish in a handful of calls, so you may not need compaction at all. Clearing or shortening tool results is likelier to pay off. Measure a few real requests before you add machinery.
A common mix-up

"A bigger context window solves the memory problem." It raises the limit, but it does not keep anything after the conversation ends, and a fuller window costs more per call and can reduce recall (context rot). A big window is a bigger desk, not a filing cabinet.

What is kept between sessions: notes 5 min

Here is the second problem. On Monday, Sam completes the laser-cutter training. On Thursday, Sam opens a new chat. The new session starts with an empty list: no Monday conversation, no training record. The model cannot know Sam was trained unless something puts that fact into the new context.

That something is memory outside the window: information your program saves to a file or database, and loads again later. Anthropic describes structured note-taking, or agentic memory, as the agent regularly writing notes that are persisted outside the context window and pulled back in at later times (Anthropic engineering). Anthropic's memory tool is one ready-made version, where Claude stores and consults information through a file system (Anthropic: context management).

For your assistant there are two ways to build it, and they fit different data:

Kind of factExampleBetter as
Exact, must be rightSam passed laser-cutter training on MondayA database record that your program writes, and loads into context at the start of Sam's session
Soft, helpfulSam usually books afternoons and is working on a wooden boxA short notes file the agent can write to and read, kept small

My recommendation for a training status: do not leave it to the model to "remember" to write it. Your program should write it when the training system reports it, and load it at the start of the session. A permission fact is too important to depend on a model deciding to take a note.

Whatever you save, load only what the current session needs. Putting every old note into every new session fills the window and costs tokens on every call.

Retrieval: finding the right page 5 min

The last problem: the manuals. Suppose they total 2,000 pages. Pasting them all into every call would be slow, costly and subject to context rot, and it may not fit at all. The alternative is retrieval: search the manuals for a few relevant pieces, and put only those into the context.

There are two broad ways to do it (Anthropic engineering):

  • Retrieve up front. Before the model runs, your program searches the manuals using the student's question and adds the best matches to the context. Embedding-based search, which finds text by meaning, is a common version.
  • Retrieve just in time. Give the agent a search tool, as with search_manuals in your loop. The agent keeps lightweight identifiers, such as a file path or a query, and loads data into context at run time when it decides it needs it.

Anthropic notes that a hybrid is possible: some data up front, with tools for exploring further. For your assistant, the just-in-time version is a natural fit, because your loop already has a search_manuals tool and the agent can decide when a question needs a manual at all. "Is the laser cutter free tomorrow?" does not.

To retrieve well, manuals are split into chunks, pieces of a page or two. A chunk must make sense alone. A chunk that says "Remove the cover, then repeat step 3" is useless if it does not say which machine. Anthropic's Contextual Retrieval work addresses exactly this problem, by adding a short description of where the chunk comes from before it is indexed. A cheap version for you: start every chunk with the machine name and the section heading.

Return a few chunks, not a whole manual, and keep the tool result short. Every token the tool returns is re-sent on each later call, as Figure 2 showed.
A common mix-up

"Retrieval and memory are the same thing." They overlap in practice, but they answer different questions. Memory holds what the assistant learned about this student or earlier work. Retrieval finds relevant text in a large, fixed collection such as the manuals. Both end the same way: selected text is placed into the context window. Neither puts anything "into" the model.

Worked example and practice 5 min

Worked example: sorting what the assistant needs

For each piece of information, ask three questions: Is it needed in this step? Must it survive the session? Is it too big to keep around?

  1. The system prompt and tool descriptions. Needed on every call, so they live in the context every time. Keep them short, since you pay for them on each call.
  2. The 2,000 pages of manuals. Too big for the context, fixed over time, and needed only in pieces. Put them in a searchable store and retrieve chunks with a tool.
  3. Today's calendar result. Needed for this request only. Keep it in the context while the request runs, and let it go afterwards. Never save it as memory, because it will be stale tomorrow.
  4. "Sam passed laser training on Monday." Must survive the session, and must be exact. Save it in a database written by your program, and load it when Sam starts a session.
Your turn

Sort these three using the same questions. For the first, the start is given: "A student's preferred machine is the 3D printer" is soft, helpful and must survive the session, so it is a note. Now decide where to put (a) the 40-page safety handbook, and (b) the result of a manual search for the drill press that the agent used two steps ago.

Show a solution

(a) The handbook is fixed and large, so put it in the searchable store with the manuals and retrieve the relevant chunks. If part of it is a short rule that applies to every request, such as "never leave a machine running unattended", that part can go in the system prompt. (b) The old search result is only needed for the request in progress. Keep it while the agent may still use it. If the window is filling and the answer no longer needs it, clear it. Do not save it as memory.

Summary 2 min

  • The model sees only the context: prompt, tool definitions, history, tool results, and its own output. Nothing else.
  • Between steps, your program keeps the list and re-sends all of it, so cost grows with each step. You can trim it by clearing old results or summarizing.
  • Between sessions nothing is kept unless you save it. Exact facts go in a database; soft ones in short notes; load only what is needed.
  • For long manuals, retrieve a few relevant chunks instead of loading everything.
