Context and memory: what the assistant sees, saves and looks up

The big picture 2 min

Start with one fact that explains most of this lesson: the model keeps nothing. Everything it "knows" at a given step is the text the program sends it in that call. The model does not look anything up on its own and does not remember last Tuesday. If a fact is not in the text it was sent, it is not available to the model.

That text has three limits. It is finite, because there is a maximum size per call. It costs money, because you pay per token sent. And it gets worse when it is bloated, because a model given too much text uses it less well. You will meet each limit with numbers in the sections below.

So the design job for your assistant is three decisions.

  • Context: what text to send on each step.
  • Saved notes: what to store between sessions, outside the model.
  • Retrieval: what to fetch on demand, such as one manual page instead of the whole manual.

Every section that follows is one piece of those three decisions. By the end you will apply all three to a case you have not seen.

Warm-up 1 min

Recall the agent loop from earlier. A student types, "Book the laser cutter for Friday." The model replies with a request to check the calendar. The calendar result comes back, the model asks for a booking, the booking is confirmed, and the model writes a final answer. That is three model steps. We know the loop works, but not yet what each step is made of. Commit to an answer before you open the reveal.

Recall

In that loop, who actually runs the calendar tool: the model or the program? And at the second step, when the calendar result has come back, what does the model see?

Check your answer

The program runs the tool. The model only writes text that asks for it, and the program does the work. At step 2 the model is a fresh call: it sees what the program puts into that call, which is the student's request, its own earlier tool request and the calendar result. It does not hold a running memory of step 1. If you guessed that the model "remembers" step 1, that is the misconception the next section takes apart.

Context and tokens 3 min

A token is the unit a model reads and writes: a short word or a piece of a longer word. Tokens matter because they are the unit of everything below. The context is all the tokens given to the model in one call. The context window is the limit on how many tokens fit: the Claude docs describe it as all the text a model can reference, including the response itself. The limit varies by model; the docs list sizes from 200,000 tokens up to 1 million, so never assume one number.

Tokens are also the unit of the bill. Providers charge per token sent and per token produced, so a longer context costs more on every call. Anthropic's engineering team calls context a finite resource with diminishing marginal returns: more is not simply better.

Why does it matter that tokens, and not words or characters, are the unit? Because the limit and the price are both set in tokens, so a long identifier, a table of numbers or a block of code can use far more of the window than its length on screen suggests. When you estimate, count in tokens, and treat any figure here as a round number to reason with, not a measurement.

What is in the context? For your assistant, some parts are the same on every step. Here is the fixed part, with illustrative numbers (they are made up to show the mechanism, not measured):

  • The system prompt, which sets the assistant's role and rules: 800 tokens.
  • Four tool definitions (search the manual, check the calendar, book a machine, message staff): 1,200 tokens together.

That is 2,000 tokens before the student has typed anything. Everything else is added on top: the student's question, their record, tool results. The docs list the system prompt, every message including tool results, and the tool definitions as all counting toward the window.

A common mix-up

"The model remembers what I said earlier." It feels true because a chat appears continuous. But the model has no memory between calls; the program sends the history each call, and the model only sees what was sent. Remove a message from the call and, for the model, it never happened.

Every step re-sends everything 4 min

Because the model keeps nothing, each step sends the whole context again: the system prompt, the tool definitions, the conversation so far and every tool result. The docs say each turn's input is all previous conversation history plus the current message. So a request with four steps does not send the early material once; it sends it four times, and the context grows at every step.

Here is the makerspace assistant on one request, with illustrative numbers. Fixed part: 2,000 tokens (system prompt plus tool definitions). The student's training record adds 120 tokens and the question adds 50. A student asks how to change the laser cutter's lens and to book Friday.

  • Step 1. Input 2,000 + 120 + 50 = 2,170 tokens. The model outputs 60 tokens: a search_manual call.
  • Step 2. The program runs the search and returns a 1,500-token manual page. Input 2,170 + 60 + 1,500 = 3,730. Output 50: a calendar call.
  • Step 3. A 300-token calendar result arrives. Input 3,730 + 50 + 300 = 4,080. Output 60: a booking call.
  • Step 4. A 150-token confirmation arrives. Input 4,080 + 60 + 150 = 4,290. Output 120: the final answer.

Add the inputs: 2,170 + 3,730 + 4,080 + 4,290 = 14,270 input tokens, and 60 + 50 + 60 + 120 = 290 output tokens. At an illustrative price of $3 per million input tokens, the input costs about $0.043 for this one request. The price is made up; the pattern is not. Without caching, you pay for the early items on every step: the 2,000 fixed tokens were paid for four times. Prompt caching exists, but the docs say it changes what you pay for those tokens, not whether they count toward the window.

Two consequences follow. Cost grows because every step pays for everything before it. And length grows, so a long task gets nearer the window limit with each step. Hold the 14,270 in mind; the next two sections change it.

It helps to see why this happens in code. The program, not the model, runs the loop, and on each pass it builds the next call from a list it keeps. A sketch in Python, which you can read already:

history = [student_record, question]          # kept by the program
while True:
    reply = call_model(system_prompt, tools, history)   # a fresh call
    history.append(reply)                      # the output joins the history
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)      # the program runs the tool
    history.append(result)                     # the result joins it too

Each pass hands call_model the system prompt, the tools and the whole history. Nothing is held inside the model between passes. The list only ever gets longer unless the program decides to shorten it, which is exactly the lever the next section uses. Notice also that the model's own output is part of what you pay for on the next step, so a chatty model makes later steps dearer.

Keeping context small 3.5 min

If cost and length grow with every step, why not fill the window and be done? Because a bigger context is not a better one. Anthropic describes context rot: as the number of tokens grows, the model's ability to recall information from the context decreases. It also describes an attention budget: the model has only so much attention to spread, and every extra token uses some of it.

The rule that follows is to aim for the smallest possible set of high-signal tokens, meaning the few tokens that most increase the chance of a good answer. A page that was useful at step 2 may be dead weight at step 4.

Two techniques keep the context small during a long task, both from the same article.

  • Compaction: when the conversation nears the limit, summarize it and restart with the summary.
  • Clearing old tool results: drop the raw output of a tool call that has done its job. The article calls this one of the safest, lightest touch forms of compaction.

Try it on the trace from the last section. After step 2, the model has used the 1,500-token manual page to decide what to do. Replace the page with a 100-token note: "lens: step list at manual p. 14; use isopropyl wipes only." Now step 3 sends 4,080 − 1,400 = 2,680 tokens, and step 4 sends 4,290 − 1,400 = 2,890. The total input falls from 14,270 to 11,470, a saving of 2,800 tokens, with the same answer.

There is a catch, and it is this lesson's own inference rather than a quote from the sources: summarizing can lose detail. The 100-token note does not hold the cleaning ratio or the torque warning on the page. If the student now asks about them, the assistant must search the manual again. Clear what the next steps will not need, and keep what they will.

What counts as high-signal? Ask of each item, "would the next step change if this were gone?" The student's question, the rules in the system prompt and the booking confirmation pass that test. A raw search result whose useful part you have already copied into a note does not. Low-signal tokens are not free: they cost money on every remaining step and compete for the model's attention with the tokens that matter.

Compare the two techniques on the trace. Clearing is cheap and precise: you remove one known item and nothing else changes. Compaction is broader: you ask a model, or a rule, to condense the whole history into a summary and start again from it, which suits a long conversation that has grown many large items. Clearing is the safer first move, as the article says; compact when clearing is not enough.

Memory between sessions 3.5 min

Context covers one request. A session is one run of the assistant, such as a student's visit. The next problem is the visit after that. The Anthropic engineering team writes that each new session begins with no memory of what came before. For your assistant this means that unless something is saved, it will not know that Priya passed the laser safety training last week.

The fix is for the program, not the model, to save things. Anthropic calls one version structured note-taking, or agentic memory: the agent writes notes that are persisted to memory outside the context window, such as a to-do list or a NOTES.md, and pulls them back in later. A related pattern from the harness article is a progress file alongside the git history (claude-progress.txt) that a new session reads first to see where the last one stopped. Your assistant would do the same with a student record.

Here is the student training record in action. Priya finishes the laser training. The assistant calls a tool that writes laser_trained: yes to her record, a file or database row the program controls. Next week, at the start of her new session, the program reads that record and puts its 120 tokens into the context. Only then can the model say, "You're cleared for the laser."

Deciding what to save is its own judgment. Save facts that will still matter next visit and that the model cannot rebuild: training status, past incidents, a booking the student will turn up for. Do not save what is cheap to fetch again, such as manual pages, and do not save a whole transcript when two lines of notes will do. A smaller store means less to read back into the context at the next session start, and fewer tokens billed on every step of it.

There is also a timing question. The assistant can write a note as the fact becomes known, in the same session, or at the end. Writing as it goes is safer: if the session ends early, nothing is lost. It is the same idea as the progress file in the harness article, where a fresh session reads what the previous one left behind before it does any work. Your equivalent is that every session begins by loading the student's record, and ends with an update to it.

A common mix-up

"Notes and memory are the same as the context window." They are not. Notes live outside it, in storage that survives between sessions, and cost nothing per call while they sit there. Only what the program reads back enters the context and gets billed.

Check yourself

Next week the assistant tells Priya, "You are laser trained: yes." Where did that fact live in between?

Show the answer

In the saved store (the student record). The model did not keep it; the program loaded it into this week's context.

Finding the right page 4.5 min

Now the third decision. The laser cutter manual is 40 pages, about 40,000 tokens. The student needs one step from page 14. You could put the whole manual in the context, or you could fetch only the page you need. This section is about the second option, called retrieval: getting the right information into the context on demand.

For manuals, here is the lesson's own example of how to do it; it is not taken from the sources. Chunk the manual ahead of time into page-sized pieces and index them. When a question arrives, the model calls a search tool with a query like "replace lens". The tool returns only the best-matching page. How is "best" decided? Two common ways. A keyword index scores pages by shared words, so it is fast but misses a page that says "optics" when the query says "lens". An embedding search turns each chunk and the query into a list of numbers that captures meaning, and returns the chunks whose numbers sit closest to the query's, so "lens" finds "optics". You do not need the math (it is out of scope for your mission); you need to know that meaning-based search tolerates different wording and keyword search does not. That is what happened at step 2 of the trace: a 1,500-token page entered the context, and 38,500 tokens stayed out.

Anthropic describes two timings for retrieval. In pre-inference retrieval, the program finds relevant material before the model runs, usually with embedding-based retrieval, and puts it in the first call. In just-in-time retrieval, the agent keeps lightweight identifiers such as file paths, stored queries and web links and loads the data itself, when needed, using tools. A hybrid retrieves some data up front and lets the agent fetch the rest as it goes. Our search tool is just-in-time: nothing about the manual is loaded until the model asks. The article's trade-off is that runtime exploration is slower than having data loaded up front, and needs good tool guidance. Your assistant is therefore a hybrid: the student's record is loaded up front, and manual pages are searched for on demand.

What does stuffing cost? Suppose the 40,000-token manual sat in the context on all four steps. The 40,000 tokens ride along on every step, so four steps send at least 4 × 40,000 = 160,000 extra tokens on top of the 14,270 trace: about 174,000 in all. At the same illustrative $3 per million tokens, without caching, that is roughly $0.52 against $0.043: about 12 times as much. The 12 is this lesson's arithmetic, and the retrieved version is also likely to answer better, since rot (section 5) applies. A larger window is room, not a reason to fill it. Prompt caching can cut the price of repeated tokens, but they still fill the window and still dilute attention.

Retrieval is not free of risk. Two choices decide how well it works. The first is chunk size: if pages are cut mid-procedure, the search may return half of the lens-change steps, and if chunks are huge you are back to carrying text you do not need. The second is the query. If the model searches "lens" and the manual says "optics", the right page may not come back. The assistant should check what it got, and search again with different words when it does not answer the question.

A third technique, sub-agents, has a helper explore a task and return a condensed summary of often 1,000 to 2,000 tokens. It belongs to a later objective on multi-agent systems.
A common mix-up

"The window fits the whole manual, so send it all." It would fit, but you pay for it on every step and the model has more irrelevant text to attend to.

Step 2: 2,160 + 60 + 2,000 = 4,220. Step 3 with the page replaced by the note: 4,220 − 2,000 + 100 + 50 + 30 = 2,400. Step 4: 2,400 + 60 = 2,460, if the step 3 result adds nothing more. Clearing saved 1,900 tokens on each of steps 3 and 4, 3,800 in all.

Summary 1 min

  • Context: the model keeps nothing, so each step sends everything again; cost and length grow, so keep it to the smallest set of high-signal tokens.
  • Saved notes: anything that must survive a session is written outside the model and read back in by the program.
  • Retrieval: fetch the one manual page you need, not the whole manual.

Cost follows from these choices: without caching, every token in the context is paid for on every step, so what you leave out, clear or fetch late is money saved. The numbers here were illustrative; measure your own.
