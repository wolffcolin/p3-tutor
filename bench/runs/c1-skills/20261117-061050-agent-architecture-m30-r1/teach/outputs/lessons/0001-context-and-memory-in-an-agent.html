Context and memory in an agent

By the end of this lesson you can say what the makerspace assistant keeps in its context, what it saves between sessions, and how it finds the right page in a long manual, and you can estimate what a request costs in tokens.

Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context and memory decisions, and you will defend them at your design review.

Warm-up 2 min

Recall

From the agent loop: in "Is the laser cutter free on Friday?", what runs the calendar tool, the model or your program? And is the model's second step a continuation of the first call or a new call?

Check your answer

Your program runs the tool; the model only writes a request for it. Each step is a new, separate model call. That second fact is the key to this lesson: if each call is separate, whatever the model "remembers" must be sent to it again, every time.

The context window: all the model sees 5 min

The big picture: a model has no memory of its own. It reads text and writes text, and nothing carries over from one call to the next. An agent's "memory" is whatever your program decides to put into the text of the next call, or to store somewhere and bring back later.

The text the model reads in one call is its context. It is made of tokens, the chunks of text (roughly word fragments) the model reads and writes. The context window is the most tokens a single call can hold, the input and the model's output together. Anything outside the window does not exist for the model.

Your program builds this context at every step. For the makerspace assistant it holds:

  1. Instructions: who the assistant is, what it may and may not do.
  2. Tool descriptions: the names and descriptions of the tools it can call.
  3. The conversation so far: the student's messages, the model's earlier tool requests, and every tool result.
A common mix-up

"The model remembers what we said earlier in the chat." It is tempting because chat apps feel continuous. In fact the app re-sends the whole conversation each turn; if your program sent only the latest message, the model would not know what "it" refers to in "book it for Friday".

Check yourself

At step 4 of a request, which statement about what the model knows is right?

Show the answer

The third option. The model has no state between calls; its knowledge is exactly the context your program sent.

Why every step costs more than the last 4 min

Because each call is separate, step 4 re-sends everything from steps 1 to 3 plus the new result. Model usage is billed by tokens, so the cost of a request is driven by total input tokens across all its calls, not by the length of the final answer. This is the quantity to estimate when you defend the budget.

Worked numbers for "Book the laser cutter for Friday if the manual says my material is allowed". Assume the instructions, tool descriptions and question take 2,000 tokens, each tool request 50, the calendar result 400 and the booking result 100. The manual page the search tool returns is the big one: 3,000 tokens.

So the bill grows with (tokens in context) × (number of calls). Two levers follow: put fewer tokens into the context, and make fewer calls. The rest of this lesson is mostly about the first.

Size also affects quality, not just cost. Anthropic describes context as a finite resource: as the window fills, the model's recall of its contents gets worse, a gradual effect it calls context rot (Anthropic). A research paper found models use information at the start and end of a long input better than information in the middle (Liu et al.), even for models built for long inputs. A window that is big enough is not the same as a context that is good.

Show the answer

About 8,000: the result is in the input of calls 2 to 5, four calls at 2,000 tokens each.

Keeping the context small during a task 4 min

Anthropic's guidance is to find the smallest set of high-signal tokens that makes the right behaviour likely (Effective context engineering for AI agents). Within one long task, three moves do this, from lightest to heaviest:

  • Clear old tool results. Once the assistant has read the manual page and acted on it, your program can replace the 3,000-token page with a one-line stub like "manual page 14 read: acrylic up to 8 mm allowed". Anthropic calls this the lightest-touch form of trimming.
  • Compaction: when the context nears its limit, ask the model to summarise the conversation, then start a fresh context holding the summary. Claude Code does this, keeping decisions and open problems while dropping redundant tool output. Anthropic's advice is to first make sure the summary misses nothing important, then trim what is superfluous.
  • Return less from tools in the first place. A search tool that returns three paragraphs instead of a page costs less in every later call (Figure 2).

Example: after booking, the confirmation reads "Laser cutter, Fri 14:00-15:00, booking 8812". Any summary that loses the booking ID is a bad one, because the student may ask to cancel it three messages later.

A common mix-up

"A summary is as good as the original." Tempting because summaries read well. But the model chooses what to keep, and an exact value such as an ID, a time or a safety limit can be silently dropped. Facts that must stay exact belong in a structured store (next section), not only in a summary.

Check yourself

The context is getting long. Which part is the safest to trim first?

Show the answer

The old tool result: it is large, already used, and can be replaced by a short stub. Instructions, tool descriptions and the goal are needed on every call.

Memory between sessions: notes and stores 4 min

A session is one conversation. When it ends, the context is gone, so for a student to be remembered next week, your program must write something down and load it back. Anthropic describes this as structured note-taking: the agent writes notes to storage outside the context window and reads them back later; its example is an agent that keeps a notes file so it can continue after its context resets (Anthropic).

There are two kinds of thing to save, and they need different treatment:

KindMakerspace exampleWho writes itForm
Exact factsStudent 4471 passed laser cutter training on 3 OctYour program, from a booking or training systemA database row or JSON file, read by a tool
Soft notesThis student usually works with acrylic and prefers afternoonsThe model, via a "save note" toolA short text note per student

At the start of a session, the program (or a tool call) loads the student's record into the context, so a few hundred tokens replace a whole history.

Check yourself

A student returns a week later. Where should "trained on the laser cutter: yes" come from?

Show the answer

The saved record. The model keeps nothing between sessions, and a summary may lose or distort exact facts.

Retrieval: finding the right page 4 min

Retrieval means fetching only the relevant piece of a large body of text into the context, instead of loading all of it. Section 2's numbers show why: a manual of 12,000 tokens in context would be re-sent on every call. So the manuals are split into chunks (say one section each, with the machine name and page as an ID), and a search tool returns the few chunks that match the question.

Anthropic distinguishes two timings (Anthropic):

  • Up front: before the model is called, the program searches (often with embeddings, which match by meaning rather than exact words) and places the results in the context.
  • Just in time: the context holds only light pointers, such as manual titles, and the model calls a search or read tool when it needs more. This costs extra calls and needs good tool descriptions, but loads only what is used.

Anthropic notes a hybrid is common: load a small fixed piece up front, retrieve the rest at runtime. For your assistant that could be the safety rules and the list of machines up front, and manual chunks fetched by a search_manual(machine, question) tool.

Example: "What is the maximum acrylic thickness on the laser cutter?" The model calls search_manual("laser cutter", "max acrylic thickness"). The tool returns the two best chunks, about 600 tokens, each labeled "Laser cutter manual, p.14". The label lets the model cite the page and lets the student check it.

A common mix-up

"With a big enough context window, retrieval is unnecessary: load every manual." Tempting because it removes a component. But Section 2 shows you pay for every loaded token on every call, and context rot lowers recall as the window fills. Retrieval improves cost and accuracy together.

Check yourself

The makerspace has 40 manuals. A student asks about the 3D printer's nozzle temperature. Which design fits the budget best?

Show the answer

Worked example and practice 4 min

Worked example: design the context for one visit

Student 4471 opens a new session and asks: "Can I cut 5 mm acrylic on the laser cutter tomorrow afternoon?" Decide what is in the context, and estimate the input tokens.

  1. Always in context: instructions and tool descriptions, plus the question: 2,000 tokens (our assumption from Section 2).
  2. Memory load: the program reads the training record and the notes file for student 4471 and adds about 150 tokens. It shows "laser cutter: trained". The model can now skip a "check training" tool call.
  3. Retrieval: the model calls search_manual; two chunks come back, 600 tokens.
  4. Calendar: one call, 400 tokens back.
  5. Answer. Input sizes per call: 2,150 (call 1), then 2,150 + 50 + 600 = 2,800 (call 2), then 2,800 + 50 + 400 = 3,250 (call 3), which writes the answer. Total: 2,150 + 2,800 + 3,250 = 8,200 input tokens. If the whole 12,000-token manual had been in the instructions instead, every call would carry 12,000 extra tokens.
Your turn

The same request, but a teammate's design puts the whole 12,000-token manual in the instructions, with no search tool. Training status is still loaded (150 tokens). First call: 2,000 + 12,000 + 150 = 14,150 input tokens, and the model asks for the calendar (50 tokens). The calendar returns 400 tokens, then the model answers. Find the input of calls 2, the total over both calls, and compare it with 8,200.

Show a solution

Call 2 input: 14,150 + 50 + 400 = 14,600. Total: 14,150 + 14,600 = 28,750 input tokens, about 3.5 times the 8,200 of the retrieval design, even though it makes one call fewer. The extra tokens come from re-sending the manual on every call. A design review argument: fewer calls do not beat a smaller context.

Summary 1.5 min

  • The model has no memory; its context window is everything it sees in a call, rebuilt by your program each step.
  • Cost is total input tokens across all calls, so a big item in context is paid for on every later call.
  • During a task, shrink the context: stub old tool results, compact with care, make tools return less.
  • Between sessions, save exact facts in a store and soft notes in a file, and load them at the start.
  • For long manuals, retrieve labeled chunks on demand instead of loading everything.

Say it in your own words: without looking, explain to a teammate why the assistant is cheaper and more accurate when manuals are searched than when they are loaded in full, and name one fact that must not live only in a model-written summary.
