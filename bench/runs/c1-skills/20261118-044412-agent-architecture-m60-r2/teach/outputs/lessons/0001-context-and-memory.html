Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or behind a retrieval tool, and defend that choice with a token count.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 60 minutes
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context and memory decisions, and they are the decisions a design review will push on.

Warm-up 4 min

From your agent-loop session, two questions. Answer in your head or on paper first.

Recall 1

In the loop, who actually runs the tool when the model asks for check_calendar: the model or your program?

Check your answer

Your program. The model only writes a request naming the tool and its inputs. Your code runs it and sends the result back. That hand-back is the moment this lesson cares about: whatever you send back becomes part of what the model reads next.

Recall 2

The loop makes three tool calls before the final answer. How many separate model calls is that?

Check your answer

Four: one per step, three that end in a tool request and one that ends in the answer. Each is a fresh call. Hold that thought: it is the key to the cost arithmetic in section 2.

Before you read on, write down your guess: when the model makes call number four, what does it know about calls one to three? You will check the guess in section 2.

What the context window holds 6 min

The context window is all the text the model can reference when it generates a response, including the response itself. Anthropic's documentation calls it the model's "working memory", as opposed to the large body of text it was trained on (Claude docs: context windows). The units are tokens, the chunks of text the model reads and writes; a token is roughly a short word or a piece of a long one, and the docs' own token counting tool will give you exact numbers for your text.

The window is not just the chat. The docs list everything that counts: the system prompt, every message including tool results, your tool definitions, and the output the model generates. Anthropic's engineering team puts the same idea as "the set of tokens included when sampling from" the model, and calls the craft of choosing those tokens context engineering (Effective context engineering for AI agents).

Capacity depends on the model: the docs list a 1M-token window for the current Claude models and 200k for some older ones, and a single request can only generate up to a stated output limit. If the input alone is over the window the API rejects it with a "prompt is too long" error. You will rarely hit the ceiling in the makerspace assistant. Cost and quality bite much earlier, which the next two sections show.

Some models are told their remaining budget automatically; others can be given an explicit one with task budgets (beta). Check the docs for the model you pick; it is a detail for implementation, not for design.
Check yourself

Which of these does not count toward the context window of one request?

Show the answer

The training text. Everything the request carries (system prompt, tool definitions, messages, tool results) and everything the model writes counts.

What is kept between steps 9 min

Back to your guess from the warm-up. Between the steps of one agent run, the model keeps nothing by itself. What "continues" is the message list your program holds and sends again. The docs describe it as input and output phases: each turn's input is all previous conversation history plus the new message, and the output then becomes part of the input for the next turn (Claude docs). Previous turns are "preserved completely."

So the answer to your guess is: call four knows calls one to three only because your program pasted them back in. Remove a message from the list and, for the model, it never happened.

Here is what that looks like in the Python you already know. This is a sketch of the loop's bookkeeping, not a working program; the point is the list.

messages = [{"role": "user", "content": question}]

while True:
    reply = call_model(system, tools, messages)   # sends the WHOLE list
    messages.append({"role": "assistant", "content": reply.content})
    if reply.stop_reason != "tool_use":
        break                                      # final answer
    result = run_tool(reply)                       # your code, not the model
    messages.append({"role": "user", "content": result})  # grows every pass

The list grows by two entries each pass, and call_model gets the entire list each time. This is the only "memory between steps" there is. It also shows where you have control: you can edit messages before each call, which is what section 4 does.

That has a price consequence. Every step re-sends the whole history, so a tool result is paid for not once but on every later step. (Prompt caching can make repeated input cheaper, but the docs are explicit that cached tokens still occupy the window: caching changes what you pay, not whether they count.) The worked numbers below use one request to the assistant. All token counts are invented round numbers; measure yours with the token counting API.

Worked example: one request, three steps

A student asks: "Can I run the laser cutter on aluminum, and is it free Friday?" The system prompt and the two tool descriptions total 2,000 tokens, the question is 50.

  1. Step 1. Input is 2,050. The model writes a tool request for the manuals, 100 tokens. Output: 100.
  2. Step 2. The manual tool returns a 3,000-token page. Input is 2,050 + 100 + 3,000 = 5,150. The model asks for the calendar, 80 tokens.
  3. Step 3. The calendar returns 400 tokens. Input is 5,150 + 80 + 400 = 5,630. The model writes the 200-token answer.
  4. Total input processed: 2,050 + 5,150 + 5,630 = 12,830 tokens, for a conversation whose final size is only 5,830.

The 3,000-token manual page was read in step 2 and again in step 3. It would be read again in a step 4.

Check yourself

After the 200-token answer, the student replies with a new 100-token message, and your program calls the model again. What is that call's input?

Show the answer

About 5,930: the full history (5,630 + the 200-token answer) plus the 100-token message. The model's own earlier output is re-sent like everything else.

A common mix-up

"The model remembers the conversation." It feels true in a chat window, because the app resends the history for you. In your own program, if you forget to append a message, the model has no trace of it. Memory between steps is your list, not the model.

Why bigger is not better 5 min

With a 1M-token window, the temptation is to paste in everything. Two reasons not to. The first is the cost you just computed: whatever sits in context is re-read on every step. The second is quality. The docs warn that "as token count grows, accuracy and recall degrade, a phenomenon known as context rot", which makes "curating what's in context just as important as how much space is available" (Claude docs).

Anthropic's engineering post gives a mental model: the model has an attention budget that it spends on every token, so each added token takes some of it from the others. The goal they state is the smallest set of high-signal tokens that still gets the outcome you want (Anthropic engineering). Note that the post presents degradation as gradual and present in all models, not a cliff.

Put numbers on the teammate's idea below. Suppose each of 12 manuals is about 25,000 tokens (an invented figure; measure yours). In the system prompt that is 300,000 tokens, re-read on each step. Our three-step request would then process roughly 300,000 × 3 + 3,000 = 903,000 input tokens, against 12,830 in section 2: about 70 times as much, for the same answer, with a diluted prompt on top. The total also exceeds the roughly 200,000-token guidance in section 6.

For design purposes this gives you one question to ask of every item in context: what would the model do worse without this, on this step? If the answer is "nothing", it is cost and noise.

Check yourself

A teammate proposes putting all 12 machine manuals into the system prompt "so it always has them." Which objection is strongest?

Show the answer

The third: cost on every step (section 2) plus context rot. Section 6 returns to the one case where putting a whole knowledge base in the prompt is fine.

Managing a context that keeps growing 6 min

Long runs, such as a student who books three machines and asks ten follow-ups, grow past what you want to pay for. Three techniques, from lightest to heaviest. They all act on the message list your program holds.

TechniqueWhat it doesWhat it risks
Return lessDesign tools to send back only what is needed: three relevant lines, not a full page.Needs tool design effort; the model may need a second call if you trimmed too much.
Clear old tool resultsRemove stale tool outputs from the history once used. The docs call it tool result clearing, part of context editing.The model can no longer re-read that output; it can call the tool again.
CompactionSummarize the conversation near the limit and start a new window from the summary (Anthropic engineering).A summary drops detail. Details that must survive need to be saved elsewhere (next section).

The first row is the cheapest, because tool results usually dominate the window (Figure 1). Apply it first, and you can check it against the numbers in section 2: a tool returning a 400-token excerpt in place of a 3,000-token page removes 2,600 tokens from every later step.

Worked example: clearing in a long run

A student books four machines in one conversation. Each booking step calls the manual search (2,000-token result) and the calendar (500 tokens). Base context is 2,050.

  1. Without clearing, after four rounds the history holds 4 × 2,500 = 10,000 tokens of tool results, so the fifth call's input is about 12,050 plus the short messages.
  2. Rule: once a machine is booked, the manual page and calendar result for it are no longer needed. Replace each with a one-line stub such as "[manual search for the 3D printer: cleared]".
  3. After four rounds the history holds four stubs of about 15 tokens each, so the fifth call's input is about 2,110 plus the short messages.
  4. The cost: if the student comes back to the 3D printer, the model has to search again. That is a cheap repeat compared with carrying 2,500 tokens through every later step.
Check yourself

A booking conversation reaches 40 steps. A student's earlier statement "I'm in the wood shop safety class on Monday" is likely to be lost in which technique, if nothing else is done?

Show the answer

Compaction. It rewrites the whole history, so any fact it omits is gone. Facts that matter long-term should go into notes, which is the next section.

What is kept between sessions: notes 8 min

A session here is one conversation, from the first message to the end. When the next one starts, the message list is empty, and so is the model's knowledge of the last student visit. The model keeps nothing, and your program only keeps what you deliberately store. This is why the assistant has to be given a memory: something outside the context window that survives the end of a session and can be read back in.

The simplest design is notes: files the agent writes and reads through a tool. Anthropic's memory tool works like this. The agent can create, read, update and delete files in a /memories directory, and the docs say it "operates client-side: Claude requests file operations, and your application runs them" (Claude docs: memory tool). This is exactly the loop you already know: the model asks, your program acts. The storage is yours, whether that is a folder or a database.

Worked example: a returning student

Maya returns on Tuesday. The memory tool is enabled and your handler maps /memories to a per-student folder.

  1. The API adds a rule to the system prompt: view the memory directory before anything else. So step 1 is a tool request: view /memories.
  2. Your handler returns a listing: /memories/maya.md, 0.3K.
  3. The model asks to view maya.md. The result: "Prefers evening slots. Booked 3D printer twice. Asked about laser cutter Friday: waiting on safety class."
  4. The model now answers Maya's new question with those facts in context, 300 tokens' worth, and not the whole history of her past visits.
  5. Near the end, the model updates the file with the new booking so the next session starts correct.

The docs' protocol tells the model to assume interruption: "Your context window might be reset at any moment, so you risk losing any progress that is not recorded."

Your handler is ordinary Python. This sketch shows the shape of one command and the safety check the docs insist on, since a path like /memories/../../secrets.env must not escape the folder (Claude docs: security considerations). It is illustrative, not a complete handler.

from pathlib import Path

ROOT = Path("store/student_42").resolve()      # one folder per student

def safe(path: str) -> Path:
    p = (ROOT / path.removeprefix("/memories/")).resolve()
    p.relative_to(ROOT)                        # raises if p escapes ROOT
    return p

def handle(cmd: dict) -> str:
    if cmd["command"] == "view":
        return safe(cmd["path"]).read_text()
    if cmd["command"] == "create":
        safe(cmd["path"]).write_text(cmd["file_text"])
        return "File created successfully at: " + cmd["path"]

Two design consequences follow. First, one folder per student means one student's notes never appear in another's context, which matters for privacy. Second, you decide what is stored and for how long: the docs suggest capping file size and expiring files that have not been read for a long time. Writing to notes also costs tokens, because each memory call is a step in the loop with its own result in context.

A common mix-up

"A bigger context window is memory." A window only lasts for the calls that carry it. Memory is what you save and re-load. A 1M-token window cannot tell Tuesday's session what happened on Monday; a 300-token file can.

A design judgment: notes are not a database

A model writes notes in its own words, and a later model reads them as plain text. That is great for preferences ("likes evening slots") and poor for a fact that must be exactly right, such as "Maya passed laser cutter safety training." That is my recommendation rather than something the docs say, but the docs' own security notes point the same way: they tell you to cap file sizes, expire old memory and strip sensitive data in your handler, because you are responsible for what is stored. For the training status, store a record in your own database and expose it through a lookup tool, so a bad note can never grant access to a machine.

Check yourself

Which of these is best kept as a model-written note rather than a database record?

Show the answer

The preference. Notes suit soft, personal context where being a bit wrong costs little. Safety status and bookings are facts other systems depend on, so they live in a database behind a tool.

Retrieval: finding the right page 8 min

Notes are things the agent wrote. The manuals are different: a large reference the agent did not write, too big to carry in context. Retrieval means searching that reference and putting only the best matches into the context. In the standard setup, called retrieval-augmented generation (RAG), "a method that retrieves relevant information from a knowledge base and appends it to the user's prompt" (Anthropic: Contextual Retrieval).

How a manual becomes searchable

  1. Chunk. Split each manual into small pieces, usually no more than a few hundred tokens, so you can fetch just the relevant piece.
  2. Index. Two common ways. Embeddings convert each chunk into a list of numbers that encodes its meaning, so a question can be matched to chunks by similarity of meaning. BM25 is older word-matching, which the article notes is "particularly effective for queries that include unique identifiers or technical terms."
  3. Search. At question time, find the top few chunks and give them to the model.
Worked example: why you may want both

A student asks "What does error E-14 mean on the laser cutter?"

  1. An embedding search matches meaning, so it ranks chunks about laser cutter error messages in general highly. The chunk with the exact code "E-14" may not come first.
  2. BM25 matches the literal string E-14, so it surfaces the chunk containing it. This mirrors the article's own "TS-999" example.
  3. Run both and merge the results, which the article calls hybrid retrieval.
  4. Now the chunk "Replace the lens every 40 hours" has a problem: it does not say which machine. The article's fix is to prepend context to each chunk before indexing ("this is from the laser cutter manual, maintenance section"), which it calls contextual retrieval.

What does retrieval buy in tokens? Take one 60-page manual of about 30,000 tokens (invented), cut into 400-token chunks: about 75 chunks. Returning the top 3 puts 1,200 tokens into context, 4% of the manual. Section 2's arithmetic then says those 1,200 tokens are re-read on every later step, instead of 30,000.

Who triggers the search: you or the agent?

The same post names two styles. Pre-retrieval runs the search before the model call and loads the results up front. Just-in-time retrieval gives the agent a search tool and lets it fetch what it decides it needs; the post says this is more autonomous but slower, and recommends a hybrid for many tasks (Anthropic engineering). For your assistant, a search_manuals tool is just-in-time retrieval, and it fits the loop you already know. The memory tool is the same pattern for notes.

One boundary: retrieval is not always needed. The contextual retrieval article says that if the knowledge base is under about 200,000 tokens (roughly 500 pages), you can put it all in the prompt, and prompt caching makes that faster and cheaper. Measure your manuals before you build an index.

A common mix-up

"Retrieval means the model looks things up on its own." The search is a tool your program runs, and the model only sees the chunks you return. If the right chunk is not retrieved, the model cannot use it, and may answer from its training patterns instead. Retrieval quality, not model quality, is often the limit.

Check yourself

A student asks about "the 40-hour lens replacement on the CO2 cutter". Retrieval returns chunks about lens cleaning on a different machine. What is the most likely cause?

Show the answer

The chunks lost their machine name. A chunk cut from its manual is ambiguous, so label each chunk with its machine and section before indexing.

Worked example and practice 8 min

Worked example: price a design change

Take the section 2 request again (12,830 total input tokens over three steps). Change the manual tool to retrieve two 400-token chunks (800 tokens) instead of a 3,000-token page. What is the new total?

  1. Step 1 is unchanged: 2,050.
  2. Step 2 input: 2,050 + 100 + 800 = 2,950.
  3. Step 3 input: 2,950 + 80 + 400 = 3,430.
  4. Total: 2,050 + 2,950 + 3,430 = 8,430.
  5. Saving: 12,830 − 8,430 = 4,400 tokens, about a third, on a three-step request. A longer run would save more, because the saved tokens are re-read at every later step.
Your turn

System prompt and tool descriptions are 1,500 tokens and the student's question is 100, so step 1's input is 1,600. The model writes a 100-token request; a manual search returns 2,000 tokens. Then the model writes an 80-token calendar request and the calendar returns 1,200 tokens (the whole week). Then it writes the final answer.

(a) Step 2 input is 1,600 + 100 + 2,000 = 3,700. Work out step 3's input and the total input across the three steps.
(b) The calendar tool is changed to return only Friday's slots, 200 tokens. What is the new total, and how many tokens did that save?
(c) Would the saving be larger or smaller if there were a fourth step? Why?

Show a solution

(a) Step 3 input = 3,700 + 80 + 1,200 = 4,980. Total = 1,600 + 3,700 + 4,980 = 10,280.

(b) Step 3 input = 3,700 + 80 + 200 = 3,980. Total = 1,600 + 3,700 + 3,980 = 9,280, a saving of 1,000 tokens (the 1,000 tokens trimmed from the calendar result, counted once because it only entered at step 3).

(c) Larger. The trimmed 1,000 tokens would be re-sent in step 4 as well, so the saving becomes 2,000. Every extra step multiplies the saving, which is why tool result size matters more in long runs.

Your turn: spot the failure

A team builds the assistant this way: the program searches the manuals before each model call and always inserts the top 10 chunks (4,000 tokens) into the first message. On a student's fifth question, the quality of answers drops and the bill per request is high. Give two causes tied to this lesson and one change for each.

Show a solution

Cause 1: the 4,000 tokens are part of the history, so they are re-read on every step, and fresh chunks for later questions pile up on top (section 2). Change: retrieve per question and return only the top 2 or 3 chunks, or clear old chunks (section 4).

Cause 2: ten chunks, most irrelevant to a given question, dilute recall of the good one (section 3). Change: fewer, better chunks, labelled with machine and section, or let the agent call a search_manuals tool only when it needs to (just-in-time).

Summary 2 min

  • The context window holds everything one call sees: system prompt, tool definitions, messages, tool results and the output. Tool results usually dominate.
  • The model keeps nothing between steps; your program re-sends the history, so every token is paid for on every later step.
  • More context is not better: it costs on every step and context rot lowers recall. Trim tool results first, then clear, then compact.
  • Between sessions, only what you store survives: notes the agent writes through a tool, and database records for facts that must be exact.
  • Retrieval searches a large reference you did not write and returns a few chunks; label chunks and consider combining embeddings with word matching.
