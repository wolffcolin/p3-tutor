Context and memory in an agent

By the end of this lesson you can decide, for one request to the makerspace assistant, what goes into the model's context, what is dropped, what is saved for the next visit, and how the right manual page gets found.

The big picture 1 min

A model has no memory of its own. Everything it can use on one call is the text you send it on that call. An agent's "memory" is therefore a set of decisions your program makes about what text to send, at three time scales:

  • This call: the context window, a small, costly workspace.
  • This session: the history your program keeps and resends each step.
  • Across sessions: notes and records stored outside the model, loaded when needed.

Retrieval is how information from a big store, like a manual, gets into the window when it is needed. The rest of the lesson takes these in order.

The context window 8 min

The context window is all the text a model can reference when generating a response, including the response itself; the docs call it the model's "working memory" and distinguish it from the training data (Claude docs: context windows). It is measured in tokens, the chunks of text the model reads and writes (you met this in learning record 0001). A token is smaller than a word or about a word; for budgeting, count tokens, not words.

What counts toward it is everything in the request: the system prompt, every message in the history (including tool results), the tool definitions, and the output the model generates (docs). So the tool descriptions you will write for the makerspace assistant take up space on every single call.

Check yourself

One call has a 2,000-token system prompt plus tool list, a 100-token question, and a 300-token answer from the model. How much of the window does the call use?

Show the answer

2,400 tokens: system prompt and tools (2,000) + question (100) + output (300).

Between steps: nothing is kept unless you resend it 9 min

Each step of the loop is a separate model call, and the model keeps nothing from the last one. What looks like continuity is your program appending each new message and tool result to a list and sending the whole list again. The docs describe each turn's input as "all previous conversation history plus the current user message" (docs).

A common mix-up

"The model remembers what it did two steps ago." It feels true because the answers stay coherent. But if your program forgot to include step 2's tool result in the list, the model would have no trace that step 2 ever happened. The only memory is the list you send.

This is also the cost rule. You pay for the input on every call, so a step is more expensive than the one before it, even if it adds little. Here is one request to the assistant, with illustrative token numbers (real counts come from the API's usage field or its token-counting endpoint):

Add the three inputs: 2,100 + 2,580 + 5,660 = 10,340 input tokens billed for a request whose final window holds only 5,660. Two consequences for your budget:

  • Cost grows with the number of steps times the size of the history, so both a long loop and a bloated tool result hurt.
  • Prompt caching lowers the price of the repeated prefix, but cached tokens still occupy the window (docs). It changes what you pay, not what the model sees.

When the window fills up 7 min

Windows are large now (the docs list 1M tokens for current models), so running out is not the first problem. Quality is. Recall accuracy drops as the window grows, an effect called context rot, so context is "a finite resource with diminishing marginal returns" and the aim is "the smallest possible set of high-signal tokens" (Anthropic: effective context engineering). The article says this is a gradient, not a cliff.

A common mix-up

"With a window this large, I can paste all the manuals in and skip retrieval." Tempting because it needs no code. It fails twice: you pay for every manual token on every step (see the cost rule above), and the model finds the one relevant paragraph less reliably in a pile of irrelevant ones.

When a long task does fill the window, you curate the history. Two methods from the article:

MethodWhat it doesExample in the assistant
Tool result clearingRemoves old raw tool results, keeps the model's own conclusions. The lightest option.After the model has read a calendar listing and noted "Friday 2–4 pm is free", drop the full listing.
CompactionSummarizes the nearly full history and starts a fresh window from the summary. Keep decisions and open problems; drop redundant output.A 40-message booking conversation becomes: "Student wants the laser cutter, Fri 2 pm, training confirmed, still needs material choice."
Compaction loses detail. The article advises tuning it to keep everything important first, then trimming what is redundant.

Between sessions: notes and stores 8 min

When a session ends, the history list is gone and the next session starts with an empty window. The model's weights do not change either; it did not "learn" the student. Anything that must survive lives in a persistent store outside the model, such as a file or database, that your program reads at the start of a session and writes at the end or along the way.

Two ways to write to the store:

  • Notes the model writes (structured note-taking): the agent saves to a file such as NOTES.md and reads it back after a reset. Anthropic's example is an agent playing a game across thousands of steps, keeping notes like "Pikachu has gained 8 levels toward the target of 10" (article). Good for loose, evolving information.
  • Records your code writes: a database row updated by ordinary code, for example when a staff member signs off a training. Good for facts that must be exactly right.

For the makerspace, "Alex is certified on the laser cutter" must be exact, so it is a database row the assistant reads through a tool, not a note the model might paraphrase wrongly. "Alex prefers morning slots and cuts acrylic" is fine as a note. Whatever you load back in is still just context: it costs tokens on every step, so load the few facts the request needs, not the student's whole file.

Mechanically, session start looks like this. Your program reads the student's saved data and puts the relevant part into the first message, because that is the only way the model can see it:

record = db.get_student("alex")      # exact fields, written by code
notes  = open("notes/alex.md").read() # loose notes, written by the model

messages = [{"role": "user", "content":
  "Student record: " + json.dumps(record["certifications"]) +
  "\nNotes: " + notes[-500:] +          # only the last 500 characters
  "\n\nQuestion: " + question}]

Three choices are hidden in those lines: which fields to load (only certifications, not the booking history), how much of the notes (the tail, capped, so the notes cannot grow the window without limit), and whether to load them at all (a student asking a manual question may need neither). If notes grow too long, apply compaction to the notes file itself: rewrite it as a shorter summary.

Anthropic also describes a file-based memory tool, where the model itself reads and writes memory files through tool calls. That is the just-in-time idea from the next section applied to notes.
A common mix-up

"Memory means the model learns from past chats." It is tempting because the chatbot seems to know you. Nothing in the model changes; a product that "remembers" you is loading saved text into the window, which is exactly the store-and-load pattern above.

Check yourself

Where should the fact "this student passed the 3D-printer safety training" live?

Show the answer

The database record: exact, written by trusted code, and loaded only for the student who is asking.

Retrieval: finding the right page 9 min

Retrieval means fetching only the relevant piece of a large store into the window. A manual is split into chunks (a section or a page each), and a search ranks the chunks against the question; only the top few enter the context. A common search is embedding-based: chunks and questions are turned into number lists so that similar meanings land close together. A keyword search works too, and the choice is a later lesson's problem.

The design question is when to retrieve. The article names two options and a mix (article):

Worked example: how a search ranks chunks

A toy keyword search over three chunks of a laser cutter manual, for the question "acrylic cutting speed". Score = how many of the question's words appear in the chunk.

  1. Chunk A, "Focusing the lens": none of the three words appear. Score 0.
  2. Chunk B, "Acrylic: set the speed to 12 mm/s": contains "acrylic" and "speed". Score 2.
  3. Chunk C, "Cutting wood: set the speed to 20 mm/s": contains "cutting" and "speed". Score 2.
  4. B and C tie. A top-2 search returns both, and the model must read them and notice that only B is about acrylic. A wrong pick here would set the wrong speed.

Two lessons from the tie: retrieval returns candidates, not answers, and the model still has to choose among them. An embedding search would likely rank B first because "acrylic" is the rarest and most specific word, but it can also miss; so the assistant's prompt should say what to do when the chunks do not contain the answer: tell the student it was not found in the manual and point to staff, rather than guess.

Up-frontJust-in-time
SpeedOne model callExtra steps (the article: runtime exploration is slower)
Wasted tokensChunks may be irrelevantOnly what the model asks for, if its tool is well designed
Best forSmall, always-needed textLarge or changing data

A hybrid is often best: put a small fixed piece up front, such as the makerspace's safety rules, and give the model tools to fetch the rest. Claude Code does this: its CLAUDE.md files are placed in context up front and file search happens just-in-time (article). Anthropic's agent guide frames retrieval and memory as the basic building blocks an agent can use, and recommends the simplest approach that works (Building effective agents).

Worked example and your turn 13 min

Worked example (about 8 min)

Student Alex asks: "Can I cut 6 mm acrylic on the laser cutter Friday afternoon, and what settings should I use?" Decide what goes where.

  1. Up-front, every call: a short system prompt, the safety rules (small, fixed), and three tool definitions: check_training, get_calendar, search_manual. About 2,000 tokens, resent each step as in Figure 2.
  2. Training status is exact and per-student, so the first step is check_training(alex), a database read. It returns one short line (about 30 tokens): certified on the laser cutter. Cheap, so keep it.
  3. Calendar changes constantly, so get_calendar("laser", "Friday") fetches it just-in-time. Return free slots only, not the full week, to keep the result near 400 tokens.
  4. Settings live in the long manual. search_manual("acrylic 6 mm settings") returns the top chunks. Cap it at two chunks (about 2,000 tokens) rather than five (about 5,000), because that result is resent on every later step.
  5. Clear the raw calendar listing once the model has noted the free slots, if the conversation continues.
  6. After booking, the program writes the booking to the calendar database (exact), and a note "Alex cuts acrylic, prefers afternoons" to the student's notes file (loose).
  7. Next visit, a new session starts with an empty history and loads those two small things, not the old conversation.

Add up the input over the four calls, with about 50 tokens for each tool request: 2,100 (question) + 2,180 (after the training result) + 2,630 (after the calendar) + 4,680 (after two manual chunks) ≈ 11,600 tokens. Had step 4 returned five chunks, the last call would be about 7,700 tokens, roughly 3,000 more, and that is on the bill whether or not the extra chunks helped.

Notice what made the plan cheap: each tool returned the smallest useful result, and the exact facts came from records, not from the model's recall. You will reuse that checklist for every tool you design.

Show a solution

(3) The Tuesday calendar for the vinyl cutter, free slots only; and the loading procedure from the manual via search_manual. Summary 3 min

  • The context window is everything sent plus everything written on one call; it costs tokens and attention.
  • The model keeps nothing between steps; your program resends the history, so cost grows with steps times history.
  • Fight context rot with small, high-signal context: clear old tool results, compact when needed.
  • Across sessions, save exact facts in records your code writes, loose facts in notes, and load only what the request needs.
  • Retrieve up-front for small fixed text, just-in-time for large or changing data, and mix them.

Say it in your own words: explain to a teammate why the assistant is cheaper if the manual search returns two chunks rather than five, and where the student's training status lives.
