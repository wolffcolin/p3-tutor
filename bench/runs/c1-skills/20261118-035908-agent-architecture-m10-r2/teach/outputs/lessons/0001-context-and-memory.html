Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or behind a retrieval search.

Why this matters for you

The assistant must answer from long manuals, remember each student's training between visits, and stay inside a small budget. All three are context decisions.

Warm-up 1 min

Recall

From the agent loop: after the model asks for a tool, what happens next, in order, until the run ends?

Check your answer

The program runs the tool, the result goes back to the model, and the model is called again; this repeats until the model gives a final answer or a limit is hit. Today's question is what the model sees on each of those calls.

The big picture 1 min

A model keeps nothing between calls. All it has at any step is the text your program sends it. So "memory" in an agent is never something the model has; it is a choice your program makes about what text to send. There are three places that text can come from:

  • Context: the running record of this one task.
  • Notes: information saved so a later session can load it.
  • Retrieval: a search that pulls a few relevant pieces out of a large library.

The context window, and why it costs 2 min

The context window is all the text the model can reference when it writes a response, including the response itself; it is the model's working memory, separate from what it learned in training. It holds the system prompt, your tool definitions, every message, and every tool result. Each turn's input is the entire history plus the new message, and the output becomes part of the next input (Anthropic: Context windows).

That makes cost grow faster than step count. Here is a run with illustrative numbers: 2,050 tokens of system prompt, tools and question, then a 100-token tool request and a 1,500-token result at each step.

More is not automatically better either: as the token count grows, accuracy and recall degrade, which Anthropic calls context rot, so the goal is the smallest set of high-signal tokens (Anthropic: Effective context engineering). Prompt caching changes what you pay for repeated tokens, not whether they occupy the window.

Check yourself

A tool returns a 4,000-token manual page after the model's 2nd call. The run then makes calls 3, 4 and 5. In how many of those three calls is the page part of the input?

Show the answer

All three: the page stays in the history, and the whole history is sent on every call.

Between steps and between sessions 1.5 min

Between steps, your program keeps the message list and re-sends it (above). Between sessions, nothing survives unless your program saves it. The usual tool is notes: files the agent writes outside the context window and reads back later, such as a to-do list or a NOTES.md (Anthropic). Anthropic's memory tool is exactly this: Claude requests file operations in a /memories directory and your application carries them out against storage you control (Anthropic: Memory tool). It is the same tool loop you already know.

When a single session nears the limit, compaction summarizes the conversation and starts a fresh window from the summary. Anything that must survive the summary belongs in notes.

A common mix-up

"A bigger context window means the assistant remembers students." It is tempting because a window feels like memory. But a window is wiped when the session ends, and a bigger one only makes each call cost more.

Check yourself

Sam finishes laser-cutter training today. What makes that fact available at Sam's visit next week?

Show the answer

Save it to storage your program reloads: only saved text can return to a new session's context.

Retrieval 1.5 min

The manuals are too long to send on every call (see Figure 1's arithmetic). Retrieval fixes that: split each manual into chunks, index them, and let a search tool return only the few best chunks for the question. The agent loads data just in time through a tool instead of up front (Anthropic), so your search_manuals tool is retrieval.

Chunking has a failure. The chunk "Release the tension lever first, then remove the guard" does not say which machine it is from, and two manuals may read almost alike. Anthropic's Contextual Retrieval prepends a short note to each chunk before indexing, such as "Bandsaw manual, blade change", and reports a 49% cut in failed retrievals in its tests.

Check yourself

The drill press and bandsaw manuals contain near-identical chunks, so searches return the wrong machine. Which fix targets that cause?

Show the answer

Prepend the source: the problem is chunks that lost their origin, not too few chunks or too small a window.

Show a solution

(1) Retrieval: long, and only a chunk matters per question. (2) Saved notes: small, outlives the session, and useful only when booking, so load it then rather than carrying it in every call.

Summary 0.5 min

  • The model sees only what the program sends; the history is re-sent each call, so cost grows with every step.
  • A bigger window is not memory and is not free; keep context small.
  • Notes carry facts between sessions; the program saves and loads them.
  • Retrieval brings in only the relevant chunks from long documents.

Say it in your own words: why can't the assistant simply paste every manual into the context?
