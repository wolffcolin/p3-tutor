Context and memory in an agent

By the end of this lesson you can say what the makerspace assistant keeps in its context, what it saves between sessions, and how it finds one page in a long manual.

Warm-up 1 min

Recall

In the agent loop, who actually runs a tool such as "check the booking calendar": the model or your program? And is each loop step one model call or the same call continuing?

Check your answer

Your program runs the tool; the model only asks for it. Each step is a separate model call. That second fact is the key to today: a new call starts with nothing unless you send it.

The context window 2 min

The context window is all the text the model can see in one call, and its size is limited. A model keeps nothing between calls, so at every step your program sends the whole context again: instructions, tool descriptions, the conversation so far, and every tool result. Whatever is not in it, the model does not know.

Cost follows from this. You pay for the tokens you send on every call, so anything that enters the context is paid for again at each later step. Figure 1 shows four calls from one request (numbers are worked out in the example below).

A common mix-up

"The model remembers the conversation." It does not: the chat appears continuous only because your program re-sends the history. If your code forgets to include the earlier tool result, the model has never seen it.

Check yourself

A student's booking request takes six loop steps. Which is true about the first step's tool result?

Show the answer

The third option: results stay in the history your program re-sends, so they are paid for on every later call.

When the window fills 1 min

A bigger window does not solve this. Anthropic describes context as a finite resource: as the token count grows, the model's ability to recall information from it decreases, which they call context rot (Anthropic, Effective context engineering). The goal is the smallest set of useful tokens, not the most.

Two standard fixes for a long loop, both from that article: clearing old tool results once they are used (the safest light-touch trim), and compaction, summarizing a nearly full context and starting a new window with the summary. Compaction risks dropping a detail you needed later.

Check yourself

The assistant already booked Friday's laser slot. The 600-token calendar result is still in context. What is the cheapest safe move?

Show the answer

The third option: clear the spent result, keep the one-line confirmation.

Notes: memory between sessions 1 min

When a session ends, its context is gone. To remember a student next visit, the agent writes notes to storage outside the window, such as a file or database row, and a later session reads them back in. Anthropic calls this structured note-taking and gives a to-do list or NOTES.md as examples (same article).

For your assistant: after a booking, save {"student": "s1042", "laser_trained": true, "last_booking": "Fri 14:00"}. At the next session's start, your program loads that record into the context. You decide what to save; save facts you need later, not whole transcripts.

Notes are not magic: if your code never loads them, the model never sees them.

Retrieval: finding the right page 1.5 min

A machine manual is too long to put in every call. Retrieval searches the stored text for what is relevant to the current question and puts only that slice into the context. Splitting the manual into chunks (say, a page or section each) and searching them by similarity is the usual approach; Elastic and the memory survey on arXiv both describe retrieval as the bridge between long-term storage and the active context.

In the agent loop, retrieval is just another tool: search_manual(query) returns the top few chunks as its result. The model decides when to call it. This is Anthropic's "just-in-time" pattern: keep lightweight references and load content only when needed.

Check yourself

Which belongs in notes, and which in the retrieved manual?

Show the answer

The second option: personal, changing facts are notes; shared reference text is retrieved.

Worked example and practice 2 min

Worked example

Request: "Book the laser cutter Friday." Assume 1,500 tokens of instructions and tool descriptions, a 50-token question, and a 40,000-token manual. Compare total input tokens over the loop.

  1. Call 1 sends 1,500 + 50 = 1,550. The model calls check_training; call and result add 150.
  2. Call 2 sends 1,700. The model calls search_manual, which returns about 600 tokens of chunks; with the call, +650.
  3. Call 3 sends 2,350. The model calls book_slot; +150.
  4. Call 4 sends 2,500 and writes the answer. Total: 1,550 + 1,700 + 2,350 + 2,500 = 8,100 input tokens.
  5. With the whole manual preloaded, every call carries 40,000 more: 41,550 + 41,700 + 41,850 = 125,100 over three calls, about 15 times more, and more room for context rot.
Your turn

Same request, but search_manual returns 1,200 tokens instead of 600. Step 1 is done for you: calls 1 and 2 still send 1,550 and 1,700. Find calls 3 and 4 and the total. Then decide: what would you save as a note afterward?

Show a solution

Call 3 sends 1,700 + 50 (the call) + 1,200 = 2,950. Call 4 sends 2,950 + 150 = 3,100. Total: 1,550 + 1,700 + 2,950 + 3,100 = 9,300, so doubling the retrieved chunk adds only 1,200 tokens, because it is sent in two calls. Note to save: the student's training status and the booking, not the manual text.

Summary 0.5 min

  • The model sees only the context window of the current call; your program re-sends everything, and you pay for it every call.
  • Long contexts get noisy and costly: clear spent results, or compact.
  • Notes outside the window carry facts between sessions.
  • Retrieval is a search tool that loads only the relevant manual chunks.

Say it in your own words: for one student's second visit, what gets loaded into context, and from where?
