Context and memory in an agent

Warm-up 2 min

Recall

From the agent loop: in "Is the laser cutter free on Friday?", who actually runs the calendar tool, the model or your program? And is a request that takes three tool calls one model call or several?

Check your answer

Your program runs the tool; the model only writes a request naming it. Each step is a separate model call, so three tool calls plus the final answer is four calls. That second fact is the key to today: every call starts from scratch.

The big picture 1 min

A model remembers nothing by itself. Everything it "knows" about your conversation is text that your program puts in front of it on that call. So agent memory is a set of decisions about which text goes in, and three places that text can come from:

  • The context window: what the model reads on this one call.
  • The program's message list: what gets carried from one step to the next within a session.
  • Outside storage: notes, records and documents that survive between sessions and are pulled in only when needed.

The rest of the lesson takes these in order, then applies them to the assistant.

The context window, and what a step costs 5 min

A token is a small chunk of text, a word or part of one. The context window is all the text the model can reference when generating a response, including the response itself (Claude docs). It is a working memory, separate from what the model learned in training.

Everything the request contains counts toward it: the system prompt, every message, tool results, your tool definitions, and the output the model writes. Each response reports what it used in a usage field, and a token counting API lets you estimate before sending (same docs).

Here is the part that matters for cost. Because the model keeps nothing, your program resends the whole conversation so far on every step. Each turn's output becomes part of the next turn's input (same docs). You pay for those input tokens again each time.

Worked example: one request, four calls

Request: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Assume the system prompt, the three tool definitions and the question total 2,500 tokens. Each tool request the model writes is about 100 tokens. Results: calendar 400 tokens, a manual page 3,000, training record 100. The final answer is 200.

  1. Call 1 reads 2,500 tokens and writes a request for check_calendar.
  2. Call 2 reads the 2,500, plus that request (100) and its result (400): 3,000. It requests search_manuals.
  3. Call 3 reads 3,000 + 100 + 3,000 = 6,100. It requests check_training_record.
  4. Call 4 reads 6,100 + 100 + 100 = 6,300 and writes the answer.
  5. The total read across the four calls is 2,500 + 3,000 + 6,100 + 6,300 = 17,900 input tokens, although the context at the end holds only 6,500.
Prompt caching lowers what you pay for the repeated prefix, but cached tokens still occupy the window: it changes the price, not whether they count (prompt caching docs).

More context is not better context 4 min

Current models have windows up to 1M tokens (Claude docs), so it is tempting to put everything in. Two reasons not to. The first is the cost you just computed: every token resent is a token paid for again. The second is quality: as the token count grows, the model's accuracy and recall degrade, a phenomenon called context rot. The docs conclude that curating what is in context matters as much as how much space is available.

Anthropic's engineering team describes this as an attention budget: each new token draws it down, so the goal is "the smallest possible set of high-signal tokens" that makes the desired outcome likely, and the decline is gradual, not a cliff (Effective context engineering for AI agents).

Two ways to shrink the message list

TechniqueWhat it doesRisk
Clearing tool resultsDrops old tool outputs, such as the manual page after the answer used it, and keeps the rest.Low; a good first step.
CompactionSummarizes a conversation near the limit and starts a fresh window from the summary.The summary may drop a subtle detail needed later.

Both come from the same engineering post; the Claude platform also offers server-side compaction that does the summarizing for you.

A common mix-up

"The window is 1M tokens, so I can paste all our machine manuals into the prompt and skip the clever parts." It is tempting because it works in a demo. It fails twice: the whole pile is resent and paid for on every step, and accuracy on the one relevant paragraph drops as the pile grows.

Between sessions: notes as memory 5 min

When a session ends, the message list is gone. The student comes back next week and the model starts blank. Anything that must survive has to be written to storage outside the model, and read back in later. This is agentic memory: the agent regularly writes notes to memory outside the context window and pulls them back in at later times, such as a to-do list or a NOTES.md file, which keeps progress across many tool calls and resets (Anthropic).

For you that is usually plain Python: a database row or JSON file per student, and two tools, read_student_record(id) and save_student_note(id, text). The model decides when to call them, exactly like the calendar tool from the agent loop.

What to save

Save durable facts the assistant cannot rederive: "Sam passed laser cutter training on 12 March", "prefers morning slots". Do not save whole transcripts: they bloat every later read and carry the rot problem with them. Prefer facts you can look up authoritatively, and keep each note short with a date, so the agent can tell old from new.

For multi-session agents, Anthropic suggests designing state artifacts so context recovery is fast when a new session starts; see the memory tool's multisession pattern.
A common mix-up

"The assistant learns from each chat, so it will remember Sam next time." It is tempting because chat products appear to remember you. But the model's weights do not change when you talk to it. Any remembering is your program saving text and putting it back into the context later. If you do not build that, it does not happen.

Retrieval: finding the right page 6 min

A machine manual is too big to include on every call (the lesson above showed why), yet the answer is on one page. Retrieval means searching the documents outside the context and putting only the best matches in. Two main styles:

  • Embedding search. Split the manuals into chunks, turn each chunk into a vector that captures its meaning (an embedding), and store them. At question time, embed the question and fetch the nearest chunks (Contextual Retrieval). It finds "my cut is burning the edges" even if the manual says "scorching".
  • Keyword search (BM25). A classic ranking by shared words, which excels at exact matches such as unique identifiers or error codes that embeddings may miss (same post). Many systems combine both.

Retrieval is a tool like any other: search_manuals(query) returns a few chunks, and the program appends them to the message list. A small chunk costs far less than the whole manual, at every later step, by the arithmetic of Figure 1.

Where it fails

A chunk cut from its manual often loses what it is about. Anthropic's example is a chunk saying "The company's revenue grew by 3% over the previous quarter", which does not say which company or quarter, so it is hard to find. For you: a chunk reading "Set power to 40% and speed to 12" does not say which machine or material. The fix, contextual retrieval, has a model prepend a short note ("Laser cutter manual, cutting 3 mm acrylic") to each chunk before indexing. In Anthropic's tests the share of relevant chunks missed in the top 20 fell from 5.7% to 3.7% with contextual embeddings, and to 2.9% when contextual keyword search was added (Contextual Retrieval).

Retrieve ahead, or on demand?

You can retrieve upfront, before the model starts, or let the agent fetch just in time with tools, keeping lightweight references such as file paths or stored queries. On-demand is slower and needs good tool descriptions, and many systems mix the two (Anthropic).

There is a cheaper escape: Anthropic says that a knowledge base under about 200,000 tokens (roughly 500 pages) can go straight into the prompt, with prompt caching making this faster and cheaper, so check the size of your manuals before building search.

Deciding what goes where 2 min

For each piece of information the assistant needs, ask three questions: how long must it live, how big is it, and is it needed on every step? That gives your design rule.

InformationWhereWhy
Role, rules, tool descriptionsAlways in contextSmall and needed every call.
The current question and tool resultsMessage list, cleared when staleNeeded this session, then dead weight.
A student's training statusStorage; read by tool, then in contextMust outlive the session; tiny.
Machine manualsStorage; retrieved chunks onlyToo big to resend every step.

Worked example and practice 3 min

The earlier worked example paid 17,900 input tokens for four calls. Retrieval can change the number.

Your turn, with the first step given

Same request, but now search_manuals returns a 1,000-token chunk instead of a 3,000-token page. All other sizes are unchanged. What is the total input over the four calls?

  1. Call 1 and call 2 are unchanged: 2,500 and 3,000, since the manual is not yet in the list.
  2. Call 3: ___ + 100 + ___ = ?
  3. Call 4: call 3's input + 100 + 100 = ?
  4. Add the four.
Show a solution

Call 3 reads 3,000 + 100 + 1,000 = 4,100. Call 4 reads 4,100 + 100 + 100 = 4,300. Total: 2,500 + 3,000 + 4,100 + 4,300 = 13,900, which is 4,000 fewer than before. The 2,000 tokens saved from the chunk are saved on both calls 3 and 4.

Summary 2 min

  • The context window is everything the model reads on one call; the model keeps nothing between calls.
  • The program resends the message list each step, so cost grows with every token kept, and recall degrades (context rot).
  • Shrink it by clearing stale tool results, or by compaction when near the limit.
  • Between sessions, memory is text your program saves and reloads by tool, such as a student record.
  • Retrieval puts only the best chunks of a long manual in context; use keywords and embeddings together, and add context to chunks.
