Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a searchable manual index, and estimate what that choice costs per request.

Warm-up 3 min

Recall

From the agent loop: the loop repeats until something stops it. Name the two ways it can end. Then say who actually runs a tool when the model asks for it.

Check your answer

It ends when the model writes a final answer instead of requesting a tool, or when a limit (such as a step limit) stops it. The program around the model runs the tool, never the model itself. Today's question follows from that: every time the program calls the model again, what does the model get to see?

Predict

A language model, as you saw, only takes text in and writes text out. A student chats with your assistant on Monday, and comes back Wednesday. Before reading on, what do you think the model "remembers" of Monday, and where could Monday's information physically live?

Check your answer

The model itself remembers nothing: its learned patterns are fixed, and a chat does not change them. Anything it "remembers" is text that the program puts back in front of it. That text has to live somewhere the program can read: a saved file or a database. The rest of this lesson is about those places.

The big picture 3 min

A model sees only one thing: the text in front of it on this call. Everything else an agent "knows" is text that the program chose to put there. So memory in an agent is a question of what text goes in front of the model, and where it is stored until then.

There are three places information can live, and each answers a different problem:

  • The context window: what the model sees right now. Fast, but limited and paid for on every call.
  • Notes: files or database rows saved by the agent, which survive after a session ends. They solve "remember this student next week".
  • A retrieval index: a searchable copy of a large document set. It solves "find the one right page in 400 pages of manuals".

The context window, and what it costs 9 min

The context window is everything the model can reference when it writes its next output, including that output itself. Anthropic calls it the model's "working memory", distinct from the training data (Claude docs: context windows). It is measured in tokens, the chunks of text the model reads and writes; this is what you heard about before, and it is the unit you are billed in.

Everything in a request counts: the system prompt, every message so far including tool results, and the tool definitions. The model is stateless, so between steps of the loop the program keeps the list of messages and sends the whole list again on every call. Previous turns are "preserved completely" and the history is billed as input each time (same source).

That gives the cost rule you will use all lesson: total input tokens for a run = the sum, over every model call, of the full context at that call. Something added early is paid for again on every later call.

Worked example: one request, call by call

Student: "Can I book the 3D printer Saturday, and what's the bed temperature for PLA?" Numbers are invented but plausible. The system prompt plus tool definitions plus the question is 2,050 tokens. Each tool request the model writes is about 60 tokens. The check_calendar result is 300 tokens, and search_manuals returns a whole 3,000-token manual page.

  1. Call 1 input: 2,050. The model writes a calendar request (60).
  2. Call 2 input: 2,050 + 60 + 300 = 2,410. The model writes a manual search request (60).
  3. Call 3 input: 2,410 + 60 + 3,000 = 5,470. The model writes the final answer.
  4. Total input: 2,050 + 2,410 + 5,470 = 9,930 tokens, though the new information in the whole run was only 3,360 tokens.
Prompt caching can make the repeated prefix cheaper to pay for, but cached tokens still occupy the window: caching changes the price, not the size (same docs page). Treat it as a later optimisation.
A common mix-up

"The model learns from the chat and remembers it." Tempting because chat apps feel like they remember you. But nothing about the model changes; the app re-sends the transcript. Stop sending it and the "memory" is gone. It is also why a fact the model states with confidence can be old: it comes from training, not from today.

Keeping the window healthy 9 min

Two reasons to keep the window small. First, cost, from the rule above. Second, quality: Anthropic reports that as the number of tokens grows, the model's ability to recall information from the context decreases, which they call context rot, and describe an "attention budget" that every new token draws on (Effective context engineering for AI agents). Their goal is "the smallest possible set of high-signal tokens". A bigger window raises the ceiling, not the quality: current Claude models go up to 1M tokens, yet the docs still say "more context isn't automatically better".

In an agent loop the growth comes mostly from tool results, as figure 2 showed. There are three levers, from cheapest to most lossy:

  1. Return less. Design the tool so its result is small: the three best matches, not the whole manual. The same post says tools should return token-efficient output. This is a tool-description and tool-design decision, and it costs nothing at run time.
  2. Clear old tool results. Once the model has used the manual page to answer, the 3,000 tokens can be removed from later calls. The Claude docs call this tool result clearing, part of context editing. What is lost: the model can no longer re-read that page, though it can search again.
  3. Compaction. When a conversation nears the limit, summarize it and start a new window with the summary (Claude docs: compaction). It suits long sessions, such as a student chatting for an hour. What is lost: whatever the summary leaves out.

A fourth lever works at the design level: give a sub-task to a separate agent that has its own clean window, explores freely, and returns only a short summary. Anthropic's post lists this as a way to keep the main window focused. It adds model calls of its own, so whether it pays off is a question for a later lesson.

Worked example: the savings from lever 1 and 2

Using the 9,930-token run from the last section:

  1. Lever 1: the search returns 3 chunks of about 300 tokens, 900 instead of 3,000. Call 3 input becomes 2,410 + 60 + 900 = 3,370, so the total is 2,050 + 2,410 + 3,370 = 7,830, a saving of 2,100 tokens in this one request.
  2. Lever 2 helps only if a call 4 would follow: clearing the page after call 3 would remove its 3,000 tokens from every call after it. In a 3-call run it saves nothing, which is why it matters for longer sessions.
A common mix-up

"Compaction means nothing is lost." A summary is a rewrite, and what it drops is gone from the window. If something must survive (a student's training status, say), do not trust the summary: write it to notes, which the next section covers. The Claude docs make the same point: compaction keeps the window small, and memory "preserves the information that must survive summarization" (memory tool docs).

Check yourself

A student chats for an hour about a laser-cut project, asking many questions about materials, settings and bookings. Near the end the window is almost full, and early turns, including a "never cut PVC" safety rule the student mentioned, are no longer needed in full. Which handling is the best fit?

Show the answer

Compact, and write anything that must survive to notes. Dropping messages by age loses information at random, and a bigger window does not fix rot.

Notes: memory between sessions 9 min

When a session ends, the message list is gone unless your program saved it, so a new session starts with an empty window. Notes are the fix: the agent writes information to storage outside the window, and later reads it back. Anthropic describes this as the agent regularly writing notes "persisted to memory outside of the context window" that are pulled back in later, such as a to-do list or a NOTES.md file (context engineering post). This tutor works exactly that way: it reads NOTES.md before every session.

Claude's memory tool is one concrete version. Claude can create, read, update and delete files in a /memories directory that persist between sessions. It is client-side: Claude only requests a file operation, and your application runs it against storage you control and returns a tool_result (memory tool docs). That is the same loop you know, with a file tool. When the tool is on, the API adds an instruction to check the memory directory before anything else, and to assume the context may be reset at any moment.

An example: a student returns

Session 1: Riley finishes laser cutter training, and the assistant is told by the training system. The model decides this is worth keeping and requests:

{"name": "memory", "input": {
  "command": "create",
  "path": "/memories/students/riley.md",
  "file_text": "Laser cutter: trained 2026-10-03\nPrefers morning slots\n"}}

Your program writes the file and replies File created successfully. Two weeks later, session 2 opens with an empty window and "Book me the laser cutter like last time". The model's first call is view /memories, then view /memories/students/riley.md, which returns the file's lines. Only now does the window contain "trained, prefers mornings", so it can call check_calendar for a morning slot. Nothing was remembered by the model; the file was read.

What deserves a note

A note is a copy, and copies go stale. Save facts that are stable and costly to rediscover, such as preferences or a conversation's decisions. For facts with a source of truth that changes, such as the booking calendar or an official training record, call the tool again instead of trusting a note; or store a pointer ("check the training database") rather than the fact. The docs also warn you to cap file sizes, expire old files, and reject paths outside /memories, because your code runs whatever path the model asks for.

The student data in notes is personal. Per-user files, and the right to delete them, are a design-review question your team will meet later.
Check yourself

Your server restarts in the middle of the night. Which of these is still available to the assistant the next morning, assuming you wrote nothing special to save it?

Show the answer

The notes file. Anything that lives only in the window or the running program is lost; stored files and databases persist.

A common mix-up

"Turning on the memory tool gives the model memory by itself." It only gives the model a file tool. Storage, per-student separation, and what to save are yours to build and to prompt. Without your handler there is nothing to persist.

Check yourself

The assistant's notes for a student say "Plasma cutter: not trained". The student completed training yesterday, and the training database now says so. The assistant answers from its note. What went wrong, and which fix is best?

Show the answer

A stale note. For facts that change and have a live source, call the tool each session; reserve notes for what has no other home, like preferences.

Retrieval: finding the right page 11 min

Your manuals are too long to paste into every request. Retrieval (often called RAG, retrieval-augmented generation) searches a knowledge base for the few pieces relevant to the question and puts only those into the window (Anthropic: Contextual Retrieval). In a tool-using agent, search_manuals is simply a tool whose result is the best chunks.

The steps, as Anthropic describes them: chunk the corpus into pieces of usually a few hundred tokens; embed each chunk, which means converting it to a vector (a list of numbers) that captures its meaning; store the vectors in a database that supports similarity search; at query time, retrieve the chunks closest in meaning to the question. You will use a library for the embedding step, so you only need to know what it gives you: search by meaning.

Where meaning search fails, and what fixes it

Two failures matter for manuals, both from the same source:

  • Exact strings. A query for "Error code TS-999" may pull general error-code text by meaning, while BM25, a keyword-ranking method, finds the exact string. Machine manuals are full of error codes and part numbers, so combine both searches: a hybrid search.
  • Chunks that lost their context. A chunk reading "The unit must be vented before use" no longer says which unit, so it will not match "Is the laser cutter safe to run?" The fix, contextual retrieval, has a model prepend a short description to each chunk before indexing, e.g. "From the laser cutter manual, Safety section: ...".

Anthropic measured how often the right chunks were missing from the top 20 results: 5.7% for plain embeddings, 3.7% with contextual embeddings, 2.9% adding contextual BM25, and 1.9% adding reranking (re-sorting the candidates with a second model). Those are on Anthropic's test data, so take them as evidence about direction, not a promise for your manuals.

Do you need it at all?

The same post says that if a knowledge base is under about 200,000 tokens (roughly 500 pages), you can put all of it in the prompt with no retrieval, and prompt caching makes that faster and cheaper (latency down more than 2x, cost down up to 90%). Retrieval earns its keep when the manuals are bigger than that. This is a real design trade-off: simple but paying for the whole window each call, versus extra machinery but small windows. And the context engineering post notes that agents can also load data just in time through tools using lightweight identifiers like file paths, rather than retrieving everything in advance, and that a hybrid often works best.

Worked example: retrieval against pasting everything

Suppose the makerspace manuals total 400 pages. At about 500 pages per 200,000 tokens (the post's rule of thumb), that is about 160,000 tokens. Use these numbers: 1,540 tokens of prompt and question, 50 per model request, a 250-token calendar result, and for retrieval a 700-token search result.

  1. Pasting everything: every call carries the 160,000. Call 1 input: 161,540. Call 2 input: 161,540 + 50 + 250 = 161,840. No search call is needed, so there are two calls and the total is 323,380 input tokens.
  2. Retrieval: three calls, with inputs 1,540, then 1,540 + 50 + 250 = 1,840, then 1,840 + 50 + 700 = 2,590. The total is 5,970. (You will redo this sum yourself in the practice section.)
  3. The ratio is 323,380 / 5,970, about 54 to 1. Even if caching took the best-case 90% off the pasted version, 32,338 is still over five times the retrieval run. Retrieval pays for itself here; at 100 pages, the pasted prompt is 40,000 tokens and the answer is less obvious.
  4. What retrieval costs instead: the index to build and maintain, and the risk that search misses the page (the 5.7% to 1.9% figures above). Pasting never misses a page, though recall still degrades in a long window.

Worked example and practice 11 min

Worked example: where does each piece of information go?

The assistant needs five kinds of information. Place each, with the reason, using the rules from this lesson.

  1. The rules "never book without training; be brief" are short and needed on every call, so they go in the system prompt, part of every call's window. Cost: a few hundred tokens, paid every call, so keep it small.
  2. The booking calendar changes constantly and has its own source of truth, so it is a tool call: check_calendar returns the few relevant slots, and they live in the window only for this session.
  3. The manuals are large and mostly irrelevant to any one question, so they go in a retrieval index behind search_manuals, returning about three chunks. Unless the total is under about 200,000 tokens, where putting them all in a cached prompt is the simpler design.
  4. A student's training status has a live record, so use a tool; the saved note, if any, is only a pointer.
  5. "Prefers mornings" has no other home, is small and stable, and is useful next visit, so it is a note in that student's file.

Your turn, part 2: cost it

Same pattern as the earlier worked examples, with new numbers. System prompt plus tools plus question: 1,200 tokens. Each model request: 40 tokens. check_calendar returns 180 tokens. search_manuals returns 600 tokens. Three calls, the last one being the final answer. Call 1 input is 1,200. Work out calls 2 and 3 and the total. Then: what would the total be if search returned a 3,000-token page?

Show a solution

Call 2: 1,200 + 40 + 180 = 1,420. Call 3: 1,420 + 40 + 600 = 2,060. Total: 1,200 + 1,420 + 2,060 = 4,680. With a 3,000-token page, call 3 is 1,420 + 40 + 3,000 = 4,460 and the total is 7,080, about 51% more, from one tool's result size.

Your turn, part 3: defend it

At your design review a teammate says, "Just give the assistant a big window and save every chat transcript, then we need no notes or retrieval." Write two or three sentences answering with the lesson's reasons: one about cost, one about quality, one about what a saved transcript does or does not do. Then compare.

Show a model answer

Cost: the window is re-sent on every call, so a 160,000-token manual set costs about 54 times the retrieval design on one three-call request (the worked example). Quality: recall degrades as the window fills (context rot), so a bigger window is not a better one. Transcripts: a saved chat is only text; to use it, you must put it back in the window, which costs tokens each call, so a short note ("prefers mornings, trained 2026-10-03") is cheaper and clearer than replaying old chats.

Summary 3 min

  • The model sees only its context window; everything else it "knows" is text your program put there. It is stateless, so each call re-sends the whole history, and the bill is the sum of every call's full window.
  • Big windows rot and cost: keep tool results small, clear old results, compact long sessions, and save what must survive to notes.
  • Notes (like the memory tool) are files your program stores; they survive sessions but go stale, so use them for stable facts and use tools for live ones.
  • Retrieval puts only the best chunks in the window: chunk, embed, store, retrieve; add keyword search for exact strings; skip it for knowledge bases under about 200,000 tokens.
