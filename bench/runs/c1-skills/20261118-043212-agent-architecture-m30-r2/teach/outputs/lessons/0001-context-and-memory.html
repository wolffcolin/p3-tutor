Context and memory in an agent

By the end of this lesson you can say what the model sees at each step of the assistant's loop, what that costs, and where each kind of information should live: in the context, in a saved note, or in a searchable manual.

Objective O3: context and memory in an agent About 30 minutes Builds on your agent-loop session (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Those are three decisions: what stays in context, what is saved, and how the right manual page is found. This lesson gives you the rules for making them and defending them at your design review.

The big picture 3 min

A model does not remember anything between calls. Everything it can use must be in the text sent with that call. That text is the context: the set of tokens the model is given when it writes a response (Anthropic, Effective context engineering). The limit on how many tokens fit in one call is the context window.

So "memory" in an agent is never something inside the model. It is your program deciding, before each call, what text to put in front of it. That gives three layers, and the rest of the lesson takes them in turn.

A common mix-up

"The assistant remembers what we said earlier, so the model must store it." It feels true because chat apps behave that way. In fact your program stores the conversation and resends it. Delete the stored list and the model has no trace of it; start a new session and the same happens, unless you saved something. This is the same fact as "every step is a separate model call" from your agent-loop session, seen from the memory side.

The context window and what it costs 5 min

Each call's context holds, in order: the system prompt, the tool descriptions, the whole conversation so far, and every tool result so far. The model's reply is added, the tool result is added, and the whole thing is sent again for the next call. A token is the unit of text the model reads (roughly three-quarters of an English word). Usage is billed per token, so the cost of a request is the tokens summed over every call, not the tokens in the final context.

Here is the laser-cutter request from your agent-loop session, with illustrative sizes (the numbers are made up for arithmetic; yours will differ):

Total input across the four calls is 2,050 + 2,950 + 6,050 + 6,250 = 17,300 tokens, though the final context is only 6,250. A long request is therefore expensive twice over: each call is larger than the last, and there are more calls. Anything that arrives early is paid for on every later call. That one fact drives most of what follows.

A bigger window is not a fix 3 min

If the window were unlimited and free, you could put everything in it. It is neither. Beyond cost, accuracy suffers: as the token count grows, the model's ability to recall information from the context declines, which Anthropic calls context rot. The cause given is that each token draws on a finite "attention budget", and every token relates to every other token, so attention is spread thinner as the context grows. The decline is gradual, not a cliff (Anthropic). The design goal that follows is the smallest set of high-signal tokens that gets the right behavior.

A common mix-up

"Just paste all the machine manuals into the prompt; the window is big enough." It is tempting because it needs no engineering and it may fit. It fails on both counts above: every manual token is paid for on every call (see the sum in Figure 2), and a page about the bandsaw sits next to the laser question, competing for attention. Fitting is not the same as working well.

Between steps: trimming the context 4 min

Within one session your program keeps the message list and resends it. When it grows too large, you have two main moves, both described in Anthropic's post:

  • Clearing old tool results: once the model has used a manual page or calendar dump, delete that bulky result from the list. Anthropic's context editing does this automatically near the token limit (Anthropic, context management).
  • Compaction: near the limit, ask the model to summarize the conversation, then start a fresh context holding only the summary. Claude Code's summary keeps decisions, open bugs and recent files and drops redundant tool output. Tune it for recall first (don't lose something needed), then precision.

Clearing is cheap and lossy in one known way: the model can no longer see that result, so it must re-fetch it if needed. Compaction costs a model call and risks dropping a detail. For your assistant, most chats are short, so the first defense is simpler: return small tool results. A calendar tool that returns only Friday's free slots (not the month's JSON) costs less on every later call.

Between sessions: notes and saved records 4 min

When a session ends, the message list is gone, and a new session starts with an empty context. Anything that must survive has to be written to storage outside the context and loaded back by the program or by a tool. Anthropic calls the agent-written version structured note-taking: the agent writes notes to persistent storage and reads them back later. Their example is Claude playing Pokémon, which tracked progress over thousands of steps and, after a context reset, read its own notes and continued (Anthropic). Anthropic's memory tool packages this as files the model can create, read, update and delete in a directory on your own infrastructure, with your program running the calls, like any other tool (Anthropic).

For your assistant, there are two different kinds of thing to save, and they need different storage:

WhatExampleStore as
Facts that must be exact"Riley completed laser training on Oct 3"A database row, written and read by your code or a tool with fixed fields
Soft context"Prefers evening slots; working on a thesis enclosure"A short note file the model can update

The reason for the split: a booking must not depend on a note the model wrote, possibly wrongly, last week. Training status gates access to dangerous equipment, so the program should check it from a record and not trust a remembered sentence. Notes help the assistant be pleasant; records make it correct. Either way, the saved data enters the context only when loaded, so keep it short: loading a 3,000-token history at the start of every chat is paid on every call, as in Figure 2.

Retrieval: finding the right manual page 4 min

Manuals are the opposite case: too long to hold in context, and mostly irrelevant to any one question. Retrieval means searching a store outside the context and putting only the best matches in. Anthropic describes two timings:

  • Pre-inference retrieval: before the model runs, your program searches (often by embedding similarity) and places the results in the context.
  • Just-in-time retrieval: the model is given a search tool and calls it when it decides it needs something, loading data at runtime. It is slower and needs a good tool, but the context carries only what was actually requested (Anthropic).

The usual store is a vector store: manuals are cut into chunks (for example, one per section), each chunk is turned into a list of numbers that captures its meaning, and a question is matched to the chunks with the nearest numbers (Lilian Weng, LLM Powered Autonomous Agents). Cutting at section headings keeps a chunk about one thing, such as "Acrylic settings", so a match is a usable answer.

Your loop already has the shape for the just-in-time version: search_manual(query) is a tool, the program runs it, and the top three sections come back as the tool result. That result then sits in the message list, which is exactly what Figure 2 and the clearing rule above are about. Anthropic notes hybrids work too: preload a small fixed piece (Claude Code loads its CLAUDE.md first) and search for the rest. For the makerspace, a hybrid would preload a short list of machine names and rules, and search the manuals on demand.

Worked example and practice 3 min

Worked example

The student asks a follow-up after the booking in Figure 2. The 3,000-token manual page is still in context, and there are three more calls (a clarification, a second booking, a final answer). How many extra input tokens does the old page cost?

  1. Find where the page sits: it arrived as the result of call 3 and is in the message list from call 4 onward.
  2. Count the calls that resend it: the three new calls, each sending the whole list.
  3. Multiply: 3 calls x 3,000 tokens = 9,000 extra input tokens, for a page the model already used.
  4. Decide: clearing it after the answer is read saves all 9,000, at the cost of re-running search_manual if it is needed again (about one more call).

Show a solution

2. Five calls resend both. 3. Page: 5 x 3,000 = 15,000. Calendar: 5 x 800 = 4,000. Total 19,000. 4. Clear the page first: it is almost four times larger, so it saves the most, and a fresh search_manual can bring it back.

Summary 1 min

  • The model keeps nothing between calls; the context your program builds is all it sees, and it is resent every call.
  • Cost is tokens summed over all calls, and accuracy falls as context grows, so aim for the smallest useful context.
  • Between steps: small tool results, clearing stale ones, compaction when needed.
  • Between sessions: records for exact facts, short notes for soft context.
  • Retrieval puts only matching manual chunks in, either before the call or through a search tool.

Say it in your own words: without looking, explain to a teammate why pasting the manuals into the prompt costs more than searching them, and what you would save for each student.
