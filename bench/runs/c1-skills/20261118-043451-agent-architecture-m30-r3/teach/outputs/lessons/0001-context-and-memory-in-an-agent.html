Context and memory in an agent

Warm-up 2 min

Recall

In the agent loop, a model asks for a tool and gets a result back. Who actually runs the tool, and how many model calls does a request with two tool uses make? Answer from memory first.

Check your answer

Your program runs the tool. The model only writes a request for it. Two tool uses means at least three model calls: one for each tool request, plus one to write the final answer. Today's question is what the model sees on each of those calls.

The big picture 2 min

A model remembers nothing by itself. Every call starts blank, and the model sees only the text your program sends in that call. So all "memory" in an agent is your program choosing what text to put in front of the model. There are three places that text can come from:

The rest of the lesson takes them in order: how the window works and what it costs, what stays in it between steps, what outlives a session, and how to find one page in a long manual.

The context window, and what it costs 5 min

The context window is all the text the model can see when it writes its next output, including the output itself. It holds your system prompt, the tool definitions, every message so far and every tool result (Claude docs: context windows). It is the model's working memory, not its training data.

The model does not keep a running state between calls. The API is stateless: to continue a conversation, your program sends the whole history again with one new item added. That has a cost consequence that surprises most newcomers. You pay for input tokens on every call, so the same old tokens are paid for again at each step.

Worked example: one request, five steps

A student asks the assistant to check the laser cutter's calendar and then look up its material limits. Say the system prompt plus tool definitions are 2,000 tokens, the question is 50, each model tool request adds 100, and each tool result adds 1,500 (a manual page is large).

  1. Step 1 input: 2,000 + 50 = 2,050.
  2. Step 2 input: step 1 input, plus the 100-token request and the 1,500-token result = 3,650.
  3. Each later step adds another 1,600: 5,250, 6,850, 8,450.
  4. Total input tokens billed over the five calls: 2,050 + 3,650 + 5,250 + 6,850 + 8,450 = 26,250, not the 8,450 you might expect from the final size.

Size matters for quality too, not only price. As the token count grows, the model's recall of what is in the window gets worse, a problem called context rot. Anthropic describes the window as a finite "attention budget" and recommends the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents). Current windows are large, up to 1M tokens on many models, but fitting is not the same as working well.

Prompt caching lowers the price of the repeated prefix across calls. It does not make those tokens leave the window, so rot still applies (same docs page).
Check yourself

An agent run has 4 steps. The starting context is 3,000 tokens and every step adds 1,000. Roughly how many input tokens are billed in total?

Show the answer

18,000. The four calls carry 3,000, 4,000, 5,000 and 6,000 tokens because the whole history goes in each time.

Between steps 4 min

By default, everything stays. Each tool result is appended and resent on every later call, even after the model has pulled out the one fact it needed. For an agent this is the main way the window fills up, so the design question is what to remove. Three techniques, from lightest to heaviest (Anthropic):

TechniqueWhat it doesRisk
Clear old tool resultsDrops raw tool output once the model has used itLow: the model's own conclusion stays
CompactionSummarizes the conversation and continues in a fresh window with the summaryA detail missing from the summary is gone
Keep results small at the sourceThe tool returns a snippet, not a whole pageThe snippet may miss what was needed

The third row is the cheapest because the tokens never enter the window. Section 6 is largely about it. Anthropic also describes handing focused work to a sub-agent with its own clean window; whether that pays off is a later lesson.

Example: the laser cutter request

The model calls get_calendar and gets back a 1,500-token week of bookings, then get_manual_page and gets a 1,500-token page. Once it has written "Friday 2 pm is free; max acrylic thickness is 6 mm", the two raw results are dead weight. Clearing them returns the context to about 2,300 tokens plus that one-line conclusion. If the student then asks to book, the model still has what it needs.

A common mix-up

"A bigger window means the assistant remembers more, so I do not need to manage it." It is tempting because a chatbot feels like it remembers. But a larger window only raises the limit. You still pay for every token each call (Figure 2), and recall degrades as it fills.

Check yourself

The assistant's calendar tool returns 40 bookings, but a student only asked about Friday afternoon. What is the best fix?

Show the answer

Filter in the tool. Tokens that never enter the context are never billed and never rot.

Between sessions: notes 5 min

When a session ends, the window is gone. A student who returns next week meets an assistant with an empty context, so anything that must survive has to be written somewhere outside it and read back in. The simplest form is notes: text saved to a file or database, loaded into a later session when needed. Anthropic calls this structured note-taking and gives examples such as a to-do list or a NOTES.md (Anthropic).

Claude's API has a built-in version, the memory tool. The model asks to view, create, str_replace, insert, delete or rename files under /memories, and your program carries them out against storage you control and returns the result. Memory lives entirely in your application (Claude docs: memory tool). This is the agent loop again: the memory tool is just a tool whose job is reading and writing files.

Example: a returning student

Session 1: a student says they prefer morning slots and finished laser cutter training. Your program saves /memories/students/s4821.md:

prefers morning slots
laser cutter: trained 2026-10-04 (confirmed by staff)

Session 2, a week later: the context is empty. The model's first action is view /memories/students/s4821.md; the result costs about 30 tokens, and the model can now offer a morning slot.

Notice the trust problem in that file. Training status decides whether someone may use a dangerous machine, and a note the model wrote is only as reliable as the model's memory of the chat. Preferences are fine as model-written notes. Authority facts such as training status are safer as a record your program owns and exposes through a read-only tool. Deciding which facts go where is exactly the design call your review will probe.

A common mix-up

"The assistant will remember the student because the conversation is saved." Saving a transcript does not put anything in the model's context. Nothing is remembered until your program loads it into the next session's window, so you must decide what to load, and loading a whole transcript brings back the cost and rot problem from section 3.

Check yourself

Which of these should be stored as a model-written note rather than only in a program-owned record?

Show the answer

The style preference. Safety status and live bookings belong to systems of record that the assistant reads through tools.

Long manuals: retrieval 5 min

The manuals are too big to paste into every request, and a model's training does not contain your makerspace's machines. Retrieval means searching a library for the few relevant passages and putting only those in the window (Anthropic: Contextual Retrieval). Retrieval is a tool like any other: search_manuals(query) returns the top few chunks. It is the third row of the table in section 4, made systematic.

First check whether you need it. Anthropic's advice: if the knowledge base is under about 200,000 tokens (roughly 500 pages), you can put it all in the prompt, and prompt caching can cut the cost by up to 90% (same article). Count your manuals before building a search system. A set of twelve 40-page manuals is about 480 pages, which is borderline; one long equipment catalog is not.

When you do need it, the pipeline has three parts:

  1. Chunk: split manuals into pieces, usually no more than a few hundred tokens.
  2. Index two ways: an embedding turns each chunk into a vector that encodes its meaning, so "how thick can I cut?" finds a chunk about "maximum material thickness". BM25 is an older method that matches exact words, so an error code such as "E-07" is found literally. Embeddings can miss crucial exact matches, so combining both works better.
  3. Return the top few chunks to the model as the tool result.
Example: a chunk that lost its context

A chunk reads "Set the bed to 60 and keep the door closed." Which machine? Which material? The chunk has lost the page heading that said "PETG on the Prusa MK4". Anthropic's fix, contextual retrieval, has a model prepend a short explanation (usually 50 to 100 tokens) to each chunk before indexing it. On their benchmark, the share of relevant chunks missing from the top 20 fell from 5.7% to 3.7% with contextual embeddings, and to 2.9% when combined with contextual BM25 (same article). That is a result on their test set, not a promise for your manuals, so measure it on real student questions.

Check yourself

A student asks about "fault code F-12" on the CNC router. Which index is most likely to find the right chunk, and why?

Show the answer

BM25 for the exact code, ideally combined with embeddings so that paraphrased questions also work.

Worked example and practice 4 min

Worked example: a returning student on the laser cutter

Session 2. The student writes: "Book the laser cutter again like last time, and can I cut 8 mm acrylic?" Place each piece of information.

  1. Start of session, context is empty. The system prompt and tool definitions (about 2,000 tokens) are loaded. This is the fixed cost of every call.
  2. "Like last time" needs a note. The model views the student's file and learns "morning slots". Notes, 30 tokens, because last session's window is gone.
  3. "Am I trained?" needs a record. The model calls get_training_status, which reads the program-owned record. It does not trust the note.
  4. "8 mm acrylic?" needs retrieval. The model calls search_manuals("laser cutter maximum acrylic thickness"). Top 3 chunks, about 900 tokens, return in context. The answer: the maximum is 6 mm, so the model says no.
  5. Booking needs a live check. get_calendar with a date filter returns a few lines, not the full week.
  6. Before the session ends, the model updates the note only if something durable changed. The 900 manual tokens are not saved; they can be fetched again.
Your turn

Same assistant, a different student: "I want to use the 3D printer for my project like last time. Which settings did we use, and what does error E-07 mean?" For each of the three needs, name the home: context only, notes, program-owned record or retrieval. Step 1 is given: "last time's settings" is notes. Do the other two, and say what you would not save.

Show a solution

"Which settings did we use" is a note (a record of this student's past choices, written when they were chosen). "What does E-07 mean" is retrieval, and BM25 matters because it is an exact code. Whether the student is allowed to use the 3D printer, if it needs training, is a program-owned record, not a note. Do not save the retrieved E-07 chunk: it is in the manual and can be fetched again, and saving it would just duplicate the manual in a place that goes stale.

Summary 1 min

  • The model sees only the context window; your program resends the history on every call, so cost grows with every step.
  • Between steps everything stays unless you trim it: filter in tools, clear old results, compact.
  • Between sessions only what you write down survives: notes or the memory tool for soft facts, program-owned records for authority facts.
  • Retrieval puts only the best few chunks of a long manual in the window; check first whether the manuals fit in the prompt.
