Check your answer

Your program runs the tool, not the model. The result is handed back to the model as input for the next step, and each step is a separate model call. That last fact is the hinge of this lesson: it raises the question of what each call actually gets to see.

The big picture 2 min

A language model keeps nothing between calls. Everything it “knows” about your conversation is whatever text your program puts in front of it on that call. So an agent’s memory is not a property of the model; it is a design you build, in three layers:

The rest of the lesson takes the layers in order: the window and its cost, what happens to it during one run, notes across sessions, and retrieval from a library.

The context window, and why cost grows each step 6 min

The context window is all the text a model can reference when generating a response, including the response itself; Anthropic’s docs call it the model’s “working memory” (Claude docs: Context windows). It is measured in tokens, the small pieces of text (roughly word fragments) the model reads and writes. Per the docs, everything in the request counts: the system prompt, every message, tool results and your tool definitions, plus the model’s own output.

Two facts follow, and the second is the one that controls your budget.

  1. The limit is on the whole request. Some current models allow up to 1M tokens (check the docs’ model table for the one you pick), far more than the makerspace needs in one request.
  2. Each step resends everything. In the docs’ words, each turn’s input holds “all previous conversation history plus the current user message,” and the output becomes part of the next input. Your loop sends the growing list again on every call, and you pay input tokens on every call.

Here is one real makerspace request, with made-up but plausible sizes: a 2,000-token system prompt plus tool definitions, and a 50-token question, “Can I book the laser cutter Friday at 2? What material settings for 3 mm acrylic?”

The cost of a retrieved chunk is its size times the number of calls that remain, so what you fetch, and when, matters more than how big the window is. (Prompt caching can discount repeated prefixes, but cached tokens still occupy the window; see the docs.)

A common mix-up

“The model remembers the earlier steps, so only the new result gets sent.” It is tempting because a chat feels like a continuous mind. In fact every call starts blank, and the table above is what the program resends. If your code forgets to append a result, the model simply never saw it.

Between steps: what stays, and what to drop 4 min

Within one request, the answer to “what is kept between steps?” is: everything your loop keeps appending. That is simple, but it is not free. More tokens also hurt quality: as the count grows, accuracy and recall degrade, a phenomenon the docs call context rot. Anthropic’s engineering team frames context as “a finite resource with diminishing marginal returns” and the goal as the smallest set of high-signal tokens that makes the outcome likely (Effective context engineering for AI agents).

You have three levers, from lightest to heaviest:

  • Clear old tool results. Once the assistant has used the manual page to write settings into its reply, the raw page is dead weight. The source calls clearing old tool results one of the lightest forms of compaction; the API offers it as context editing.
  • Compaction: when the window is nearly full, summarize the history and start a fresh window containing that summary. You lose detail, so the summary has to keep what matters (decisions, open questions). See server-side compaction.
  • Hand work to a sub-agent that uses its own clean window and returns only a short summary (the source cites 1,000 to 2,000 tokens). Whether this pays off is a later lesson.
A chat app such as claude.ai may instead drop the oldest turns first-in-first-out. In your own code, the history is whatever list you send, so you decide what is dropped.
Check yourself

At call 12 of a long run, the 3,000-token manual page from call 2 has already been used and is no longer needed. What is the cheapest sensible fix?

Show the answer

Clear the old tool result. Instructions cannot make the model ignore sent tokens, and a bigger window only moves the limit.

Between sessions: notes as memory 5 min

When a session ends, the history you were sending is gone unless you saved it; the next session starts with an empty window. The standard fix is structured note-taking (also called agentic memory): the agent writes notes to storage outside the window, and reads them back later. Anthropic’s examples are a to-do list or a NOTES.md file (source); the API’s memory tool is one packaged version.

Notice what this means mechanically: the notes are just a file or database row. Your program loads them into the window at the start of a session, usually through a tool or a line in the system prompt, and the model writes updates through a tool. The model itself learns nothing; it is not trained on your students.

For the makerspace, a student’s note might be:

{"student_id": "s4471",
 "trained": ["laser_cutter", "3d_printer"],
 "pending": ["bandsaw (needs in-person safety check)"],
 "last_visit": "2026-11-10"}

At the start of the next session the program loads those four lines (about 60 tokens) into the system prompt. The assistant can then refuse a bandsaw booking and say why, without any retrieval.

Writing. The model decides when something is worth saving and calls a tool such as update_student_notes; your program applies the change to the file. Two rules keep this healthy: notes ride along on every call, so keep them short and structured (see the cost rule above); and an entry can go stale, so give the model a way to overwrite or delete entries, and let a staff-confirmed record win over a note when they disagree.

Your turn

During a session the student says, “I just finished the bandsaw safety check,” and staff confirm it. Starting from the JSON above, write the updated note and say who makes the change.

Show a solution

Move bandsaw from pending to trained and clear the pending line. The model requests the update through the tool; your program performs the write, just as it runs every other tool.

A common mix-up

“A 1M-token window means I do not need saved memory.” It is erased when the session ends, and billed on every call. Size does not give persistence.

Retrieval: finding the right page 6 min

The manuals are too long to load on every call (you saw what one 3,000-token page costs). Retrieval keeps them outside the window and pulls in only the relevant pieces. The common pattern, RAG (retrieval-augmented generation), works like this (Anthropic: Contextual Retrieval):

  1. Chunk each manual into pieces of at most a few hundred tokens.
  2. Index each chunk twice: as an embedding (a vector of numbers that encodes meaning, so similar meanings land close together) and for BM25 (older keyword matching on exact words).
  3. Search at question time: find the chunks nearest in meaning or sharing exact terms, such as a part number embeddings may miss.
  4. Insert the top few chunks into the window as a tool result.

Why chunks fail, and one fix

Chunking strips context. Anthropic’s example is a chunk saying “The company’s revenue grew by 3% over the previous quarter,” which names neither the company nor the period. A makerspace version: “Hold the foot pedal for 3 seconds” does not say which machine. The fix, contextual retrieval, prepends a short description of where the chunk comes from (“Vinyl cutter manual, section 4: loading material”) before indexing. In Anthropic’s tests, the share of missed relevant chunks in the top 20 fell from 5.7% to 3.7% with contextual embeddings, and to 2.9% with contextual BM25 added.

Load up front, or fetch just in time?

You can also give the agent lightweight pointers (a manual title, a section heading) and let it load the content with a tool when needed; Anthropic calls this just-in-time retrieval and notes that many systems mix it with up-front loading (source). The Contextual Retrieval post adds that if your knowledge base is under 200,000 tokens (about 500 pages) you can skip RAG and put it all in the prompt (source). That is only a feasibility check; the cost comparison below shows why you may not want to.

Worked example: a query, and what retrieval costs

Query: “settings for 3 mm acrylic on the laser cutter.” The index returns candidates:

  1. “Laser cutter manual, cutting acrylic: for 3 mm acrylic use 60% power, 10 mm/s.” Matches by meaning and by the exact words “3 mm” and “acrylic”: rank 1.
  2. “Laser cutter manual, engraving wood: use 30% power.” Close in meaning (laser settings), no shared keywords: rank 2.
  3. “Sewing machine manual, thread tension.” Unrelated: rank far down, not returned.

Insert the top 3 chunks of about 300 tokens each, 900 tokens in all, rather than the 3,000-token page. Now compare the four-call request from the table (its other tokens total 9,510 across the calls, plus the 60-token student note on every call, 240 in all, so 9,750). Worked example and practice 4 min

Worked example

Place this item: “Students must wear safety glasses at the 3D printer.” Is it context, notes or library?

  1. Is it the same for everyone? Yes, so it is not per-student notes.
  2. Is it needed on almost every request? No, only 3D-printer questions. So it should not sit in the window on every call, where it would be paid for each time (the cost rule from the table).
  3. Is it small, stable text findable by a topic query? Yes, so it belongs in the library, as a chunk labelled with the machine name, fetched by search_manual when relevant.

Rule of thumb from these steps: per-student and persistent goes to notes; same-for-all and bulky goes to the library; live and changing goes to a tool; only what every call needs lives in the system prompt.

Summary 1 min

  • The model keeps nothing between calls; the context window is whatever your program sends, and it is resent every call.
  • Cost is size times the calls remaining, and quality degrades as context fills, so clear, compact or delegate.
  • Notes carry facts between sessions; the program loads them, the model does not learn them.
  • Retrieval searches chunks of long documents and inserts only a few; chunks need their context attached.

Say it in your own words: explain to a teammate why the assistant’s bill grows with every tool call, and which of the three layers you would use to remember a student’s training.

Show a model answer

Each call is stateless, so the program resends the whole history, including every earlier tool result, and input tokens are billed per call. Training status goes in saved notes, loaded at session start and updated through a tool.
