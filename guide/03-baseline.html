Part I · Getting set up

Run the baseline and read what it made

Your first bench runs: one quick run of the tutor as it ships, so you see what it makes and where every file lands, and then three full runs that every later comparison in the project is measured against.

About 25 minutes to read.

The short path

Why

Every step you build is measured against c0-baseline, the tutor as it ships, so you need to know what it does well and where it falls short. Its three full runs also show how much one unchanged tutor varies from run to run, and that spread is what a later difference has to beat before it means anything.

Do
  1. In the Builder or a Plain terminal, make the quick run, uv run p3 bench --config c0-baseline --quick, about 4 minutes.
  2. Open what it made, in your browser and in VS Code: the lesson, the quiz and its key, the grades and the tutor's replies. Then read KNOWN-GAPS.md and reviews/README.md. The Guide can show you where each file is.
  3. In a Plain terminal, start the three full runs, uv run p3 bench --config c0-baseline --repeats 3, about 20 to 25 minutes, and commit bench/runs/c0-baseline/ when they finish.
Done when

uv run p3 check shows OK runs of c0-baseline: 3 scored full runs on agent-architecture at 30 minutes (3 needed), and uv run p3 next lists 2 The baseline under Done with no line about the baseline's runs under Also.

Then

Write your PREFERENCES.md, which you can do while the full runs go.

What c0-baseline is

c0-baseline is the tutor exactly as the template ships it, frozen as a snapshot in configs/c0-baseline/. A config is everything that decides how the tutor behaves: tutor/CLAUDE.md, tutor/PREFERENCES.md and everything under tutor/.claude/ (its skills, subagents and settings). A snapshot is a copy of a config under a name, with a hash of its files, so that a run always points at one exact tutor. Your tutor, configs and snapshots explains both in full.

The baseline has a single skill, teach, which does all four jobs in one shot. When the bench asks for a quiz, a grade or a tutor reply and the config has no skill of that name, the request goes to /teach, and tutor/CLAUDE.md tells the tutor to use /teach for every request. The skill is a fork of the teach skill in Matt Pocock's mattpocock/skills; I kept its workspace model and its pedagogy and changed it to do all four jobs in one pass. Its PREFERENCES.md is the neutral one the template ships. The allow list in its .claude/settings.json names only WebSearch and WebFetch, so in a bench run it cannot use the shell; the bench adds Glob and Grep for searching, as it does for every config.

You never change c0-baseline. Its snapshot is already in your repo, and once it has runs, overwriting it would make every one of those runs stop matching its config, which p3 check reports as a failure.

Why it is competent on purpose

The baseline keeps the teach skill's pedagogy and meets the output contract, the file formats in bench/FORMATS.md that the bench reads. I made it that way because a broken baseline makes every change look like a win. The honest question in this project is whether your machinery beats a good, simpler system.

In my runs it was good where a script can check: every key fact in its lessons was present and correct, its quiz keys agreed with both solvers, and its grades matched every true verdict. That has a cost for you: some of your steps will not beat it on those checks, and saying so plainly, with the numbers, is a real result and not a failure.

The quick run

A scenario is one request to the tutor, such as "teach a 30-minute lesson on objective O3", run headless with claude -p in a fresh folder that holds the config and the topic's starting workspace, so every config faces the same test. A quick run is five of the ten scenarios, once each, followed by their scoring: teach, quiz, grade-s1, tutor-p01 and tutor-p02. It is how you see what a tutor makes without paying for a full run.

This is the first p3 command that draws on your Claude plan: five Claude Code sessions, plus the judge and solver calls that score them. In my pilot it took about 4 minutes and 1.1 million tokens. Most of those tokens are cached reads of Claude Code's own instructions and tools, which cost far less than new input or output. (The Guide and Builder windows use your plan too, lightly.)

You can start it in either of two places. The Builder is the easy one:

Say to the Builder
Run the quick baseline: uv run p3 bench --config c0-baseline --quick

The Builder says how many sessions the run will start and asks before it starts anything. Say yes, and it runs the command in the background and tells you what it printed when it is done.

Or run it yourself in a plain terminal, a terminal tab with no Claude Code in it, where you can watch each line appear. The Guide and the Builder shows how to open one.

That is the shape of what it prints, with the numbers left out, because yours will differ from run to run. The first line names the config and the start of its hash, the topic, the lesson length, how many scenarios it runs, and the model. Each scenario then gets a line when it starts and one when it ends, with its status (ok is what you want; timeout and error are results about the tutor), its minutes, turns and tokens, and how many files it wrote. After the last scenario comes a table of what each one cost, and after the scoring, the headline numbers, one per line, which How to read what it made below goes through. The dollar figure is the list-price equivalent that Claude Code reports, not what you pay on a subscription; on your plan, the cost is your usage limit.

Watch out

A warning that a file "sits in a folder above the scenario folders". The bench runs each scenario in your system's temporary folder, which on Windows is inside your home folder, so a CLAUDE.md in your home folder reaches every scenario and shapes the results. run.json records it, and you should move or rename that file before the full runs, because those are runs you commit.

"removed ANTHROPIC_API_KEY so the bench uses your Claude subscription". That is p3 protecting you: an API key in your shell would silently replace your subscription in a headless session. Nothing to do.

On Windows, a warning about the path limit. Your repo sits at a path so long that a scenario's files may not copy or commit; When it breaks has the fix.

If it fails

If it says claude --version did not answer, or a scenario fails because you are not signed in, open claude once in a terminal and sign in, then run the command again. When it breaks covers this and the other usual causes.

Where everything is

Every run of c0-baseline writes one folder, bench/runs/c0-baseline/<run-id>/. The run id is the time the run started, the topic, the lesson length and the repeat number. In 20261105-141502-agent-architecture-m30-r1, that is November 5, 2026 at 14:15:02, the topic agent-architecture, a 30-minute lesson (m30), and repeat 1 (r1). The time is in UTC, so it can be several hours off your own clock; sort the folders by name and the newest is last.

A quick run's id also ends in -r1, like the first repeat of a full run. To tell them apart, look inside: a quick run has five scenario folders and its run.json says "quick": true, while a full run has ten.

bench/runs/c0-baseline/20261105-141502-agent-architecture-m30-r1/

Every scenario folder holds a result.json and a trace.jsonl.gz, plus an outputs/ folder when the scenario wrote or changed a file and a stderr.txt when Claude Code printed something there; the tree above shows only the files you read first. A tutor may also write or change other files, such as NOTES.md or a learning record, and those show up in outputs/ too, each at its own path.

How to open each kind of file

The lesson, in your browser

A lesson is a complete HTML page, so you read it in a browser, the way a learner would. Opening it in VS Code shows its source, not the page.

  • In VS Code's Explorer, find the lesson under teach/outputs/lessons/, right-click it, choose "Reveal in File Explorer" (Windows) or "Reveal in Finder" (macOS), and double-click the file there.
  • Or, in a terminal in work/p3-tutor, type start (Windows, in Git Bash or PowerShell) or open (macOS), a space, and the path, and press Enter. The Tab key completes each part of the path, so you do not have to type the run id.
Run in a plain terminal in work/p3-tutor
start bench/runs/c0-baseline/<run-id>/teach/outputs/lessons/<the lesson>.html

Open it where it is, and do not copy it somewhere else first: a lesson may load its stylesheet or images from ../assets/, and that relative path only works from inside outputs/.

Quizzes, keys and grades, in VS Code

Click the file in VS Code's Explorer. If a long line runs off the screen, turn on word wrap with Alt+Z (Option+Z on macOS); it changes only the view. Do not save changes to a run's files: a run is a record, and the README asks you never to edit one by hand. If you change one by accident, close it without saving.

A tutor's reply

result.json is the session's final result line, as Claude Code reports it, and for a tutor probe the reply is the value of its "result" field: one long string, in which \n marks a line break. With word wrap on, it reads well enough in VS Code. Or ask the Guide, which can read your runs' files:

Say to the Guide
Show me the tutor's reply in tutor-p01/result.json of my latest c0-baseline run, and the judge's note on that probe in score.json.

run.json and score.json

run.json says what ran: the config and its hash, the topic, the Claude Code version, the model, and for each scenario its status, duration, turns, tokens, subagents, web searches and fetches, and permission denials, the tool calls that were refused because the config does not allow them. score.json holds every check's result, the headline numbers, and what the scoring itself cost, and for each tutor probe the judge's short note on why it was met or not. You rarely need to read either one whole, because uv run p3 report turns them into tables, but they are where to look when one number surprises you.

The trace

trace.jsonl.gz is the whole stream of the session, gzipped, including every subagent's messages. For the baseline you will rarely need it; it is where to look when a scenario timed out or wrote nothing. Any gzip tool opens it, and the Builder can read it for you.

How to read what it made

Read the baseline's outputs the way you will read your own tutor's from step 1 on, because your c1-skills major review compares against them. The criteria in reviews/README.md are a good guide to what to look for, and these questions are a short version of them.

First, who the learner is. The shared topic, agent-architecture, is written for a fixed novice: an engineering junior who has written some Python and used a chatbot, but has never built an agent, and wants to build a makerspace assistant for a senior design project. You are not that novice, so read each output as that learner would, or as you would have when you were new to agents.

  • The lesson. Is every claim right? Does it teach in a good order, with examples before abstractions and a chance to practice? Does it stay on O3, at the novice's level, tied to the makerspace assistant? Would you want to learn from it: its length, its look, its figures, its references?
  • The quiz. Answer the six items yourself before you open the key. Is it the right difficulty for this learner? Does it test the core of O4 and not side details? Could any stem or option be read two ways, or give its answer away? Is the key's rationale worth reading?
  • The grades. For each of the six answers in s1, does the verdict match the true grade in grading.json? Does the feedback say what was right, what was missing and what to do next, without burying it?
  • The tutor's replies. Does it keep the quiz answer to itself, including hints that point at one option? Does it stay at the learner's level? Does it talk the way you would want to be talked to?

Then the numbers the scoring printed. These are the ones to set beside KNOWN-GAPS.md first:

  • teach_facts_correct: the share, 0 to 1, of the objective's facts that the judge, a fixed prompt on a pinned model, found in the lesson, present and correct.
  • teach_length_ratio: a rough reading-time estimate, the lesson's visible words divided by 150 words a minute, over the 30 minutes requested; 0.6 to 1.5 counts as on length.
  • quiz_key_agreement: the share of the items where the Sonnet solver, a model that answers the quiz without the key, agrees with the key.
  • grade_verdict_agreement: the share of graded answers whose verdict matches the true grade.
  • tutor_leaks and tutor_behavior_met: how many replies gave away a quiz answer, and the share of probes whose reply did what the probe expected, in the judge's view.

A quick run has only two tutor probes, so one reply moves the tutor numbers a lot; read the replies themselves before you trust the numbers. The bench defines all twelve headline numbers.

Example: notes on a quick run of the baseline, in a student's words

"Lesson: about 3,000 words for 30 minutes, ratio 0.67, short as KNOWN-GAPS says. It defines the context window well but shows the first example only halfway down, which is late for me. Quiz 0002: q4 asks for the better design without saying better for what. tutor-p01: it refuses the letter, then asks me who controls when the repetition ends, which points straight at the step limit."

Keep notes like these, anywhere you like for now. They are the start of your reading of the baseline in section 1 of EVAL.md, and of your first quick round in step 1.

KNOWN-GAPS.md: what I saw

KNOWN-GAPS.md, at the root of your repo, is my record of the failures I saw when I ran the baseline before release: three full runs and one quick run on the shared topic. The gaps in it are starting points, not a checklist. Nothing grades you on fixing them; your own runs will show the same kinds of failure, and perhaps others, and when you write about them in EVAL.md you cite your runs, not mine.

It names four gaps, here in a sentence each:

  • The tutor narrows a quiz item down while refusing to answer it. On tutor-p01 it refused to give the letter in every run, but in every run its hints still pointed at the keyed option, for example by asking "who controls when that repetition ends", so the leak check found no leak while the judge marked the probe not met; tutor-p02 was met in two runs of three. It is the hardest guardrail in the project, because a hint that applies to every option alike is much harder to write than a refusal.
  • The tutor answers above the learner's level. On tutor-p05, a novice's request to derive the PPO objective, it wrote out the formula in every run instead of steering the learner to a next step within reach.
  • Tutor replies run long. The tutor-p06 replies ran 300 to 380 words where the probe asks for about 250, and the judge failed them on length alone; across the three full runs, tutor_behavior_met was 0.33 to 0.50.
  • Lessons come in short. Asked for 30 minutes, the baseline wrote about 2,800 to 3,400 visible words, a length ratio of 0.62 to 0.75, just above the 0.6 minimum; in three of my four runs the teach session tried to count its words with a shell command the baseline does not allow, so it had no way to check its own length.

Two of these, on tutor-p05 and tutor-p06, only show in full runs, because a quick run has the first two probes only.

The file also says where I saw no failure. The lessons had every key fact present and correct, the quiz keys agreed with both solvers, and the grades matched every true verdict, even when I made two answers harder. So on the shared topic, the checks for teach facts, quiz and grade mainly catch a step that breaks something: the baseline already scores at the top of them, so what a review loop on quiz or grade buys shows up mostly in your own reviews and in its cost. Say so plainly if that is what you find; it is a real result. Last, the baseline never opened keys/ in any of its twenty probe sessions, so the guard you add in final is insurance, and it will probably not move tutor_leaks on the shared topic.

Then read reviews/README.md

Read reviews/README.md next, in VS Code or on your repo's page on GitHub, which shows the Markdown formatted. It says how you review your own tutor from step 1 on: quick rounds while you build a step, a major review at the end of each step, the criteria and the 1 to 5 ratings, what good evidence looks like, and who writes what. Your reviews explains the same in full.

The one rule to take from it now: your reviews are yours. You write them in the Markdown files in reviews/, in the VS Code editor, under the headings each file already has; you never type a review into a chat for an agent to write. The Builder writes only the What changed part of each round, and the Guide never writes your words, because your judgment is the measurement, and an agent's words in its place would measure the agent.

Reading the baseline with those criteria in mind costs nothing extra, and it means your first round in step 1 already has something to say.

The three full runs

A full run is all ten scenarios once: teach, quiz, grade-s1, grade-s2 and the six tutor probes, then the scoring. --repeats 3 runs it three times, one after another, so this command starts 30 Claude Code sessions plus the scoring of each run. These three runs are the yardstick every later step is measured against, and three of them, not one, show how much an unchanged tutor varies from run to run (Why three runs below says more). In my pilot the baseline's three took about 20 to 25 minutes, so start it when you can leave it running.

Run in a plain terminal in work/p3-tutor
uv run p3 bench --config c0-baseline --repeats 3

Run it in a plain terminal, not in a Claude Code window. The three runs take far longer than Claude Code lets a foreground command run, and they must not stop when a Claude Code window closes. If you ask the Builder to start it, it gives you this command to run yourself, and that is the Builder following its rules. On Windows, use Git Bash for the plain terminal, as in Project 2.

Before you start:

  • Type /usage in a Claude Code window to see how much of your plan is left. A full run of the baseline was 1.85 million tokens in my pilot, $1.75 at list price, so the three take about three times that.
  • If your quick run warned about a CLAUDE.md above the scenario folders, move that file first.
  • Keep the computer awake and the terminal open until it finishes.

It prints the same lines as the quick run, once for each repeat, each headed repeat 1 of 3:, repeat 2 of 3: and so on, with the run's folder, and at the end a list of the three run folders. If you want it to finish sooner, --jobs 2 runs two scenarios of a repeat at the same time; it saves time, not tokens.

While it runs

The full runs use the snapshot in configs/c0-baseline/, not tutor/, so you can work in tutor/ while they go. The natural thing to do is your PREFERENCES.md, which needs no run; uv run p3 next suggests the same thing on its Also line, after the words "While it runs". When the runs finish, read grade-s2 and the replies to tutor-p03 to tutor-p06 in one of them, which the quick run did not have.

If it stops partway

A usage limit, a sign-in problem or an outage. p3 bench stops at the first scenario that reports one, sets that repeat aside in bench/runs/_live/_aborted/, which git ignores, and keeps the repeats before it. Wait for the reset (/usage shows when), then run only what is missing: uv run p3 bench --config c0-baseline --repeats 2 if one repeat is done, or the same without --repeats if two are. uv run p3 check names the exact command.

You pressed Ctrl+C or closed the terminal. The folder of the repeat in progress is left incomplete, with no run.json; after Ctrl+C, p3 bench prints that and says to delete it. Delete that folder, because p3 check fails on a run folder with no run.json, then run what is missing.

A run has its run.json but no score. Score it with uv run p3 score bench/runs/c0-baseline/<run-id>.

A scenario timed out or wrote no lesson. That is a result about the tutor, not a broken run: keep it, and report it. When it breaks has more.

Why three runs, and why the baseline matters to every comparison

The same tutor does not make the same thing twice. Run c0-baseline three times and you get three different lessons, quizzes and replies, and different numbers: in my runs the length ratio went from 0.62 to 0.75, tutor_behavior_met from 0.33 to 0.50, and tutor-p02 was met in two runs of three. That spread is noise, and any difference you want to claim later has to be larger than it. If c1-skills scores better than the baseline's mean but inside the baseline's range, that is not yet evidence that your skills helped.

One run gives you one sample and no idea of the spread. Three give you a mean and a range, which uv run p3 report prints for every headline number, and lecture 23 (Tue Nov 17) shows how to read repeats with intervals. Three is what the project can afford: runs are not free, which is why only c0-baseline and final get repeats.

Almost every comparison you make later uses these runs:

  • Step 1's major review compares c1-skills with c0-baseline, and uv run p3 report --configs c0-baseline,c1-skills puts the one run of c1-skills beside the baseline's three. EVAL.md asks you what one run against three lets you claim.
  • final is measured against c0-baseline with three runs each, so you can ask whether each difference is larger than the spread between runs of the same config.
  • The blind comparison of c0-baseline against final pairs their runs by repeat order, three pairs of runs, which make 3 teach, 3 quiz, 36 grade and 18 tutor pairs.

So a problem in these three runs, such as a home-folder CLAUDE.md that reached every scenario, carries into every comparison after them. It is worth getting them right once.

One more thing to know: c0-baseline keeps the neutral PREFERENCES.md, and c1-skills is the first config with yours, so step 1 measures your skills and your preferences together. Write your PREFERENCES.md says what that means for what you claim.

Commit the runs

When all three are scored, commit the whole folder, which also holds the quick run. Runs are your evidence: p3 check, on your machine and in CI, confirms that each one still points at a config whose hash matches, and I read them when I grade.

Run in a plain terminal in work/p3-tutor
git add bench/runs/c0-baseline
git commit -m "Add the baseline's quick run and three full runs"
git push

Or ask the Builder:

Say to the Builder
Commit bench/runs/c0-baseline/ with the message "Add the baseline's quick run and three full runs", and push.

After the push, the p3-check run in your repo's Actions tab checks them, and it should stay green. Never edit a run, and never delete one because you do not like its numbers; the only runs to delete are the ones that measure nothing, such as a run whose scenarios say Claude was not working (When it breaks).

The baseline's section of EVAL.md

Section 1 of EVAL.md asks for the table of the baseline's three full runs, with their run ids, and your reading of the baseline: what it did well and where it fell short in each of the four jobs, which gaps in KNOWN-GAPS.md you saw in your own runs and whether you found one that is not listed, and which number moved the most from one run to the next. You can write it now, while the outputs are fresh, or later; nothing fails on it until uv run p3 check --final. The table comes from one command, which makes no model call:

Run in the Builder, or a plain terminal
uv run p3 report --configs c0-baseline

Paste its tables as they are, and write the reading yourself, in VS Code; the prose of EVAL.md is yours. The inventory and EVAL.md covers the whole file.

When this stage is done

uv run p3 next reads your repo and prints where you are on the project's map, with lines headed Done, Now, Next, Read and sometimes Also. Its stage 2, The baseline, has two items: a run of c0-baseline, which the quick run satisfies, and three scored full runs. While full runs are missing, its Next line gives you the command to start them in a plain terminal, with --repeats set to what is missing, and its Read line points at The three full runs on this page. Full runs are long runs, so they do not hold you back: once you have written your PREFERENCES.md while they go, p3 next counts the stage as passed, lists 2 The baseline under Done, moves Now on to step 1, and keeps naming the runs still missing on its Also line, such as the baseline's runs: 2 of 3 scored full runs (start the last one in a plain terminal). The stage is finished when all three are scored and the Also line no longer names them; if you have not written your preferences by then, Now moves on to 3 Your preferences. While a run is going, its folder has no run.json yet: p3 check reports that as a failure, but p3 next names it on its Also line as a bench still running, until 90 minutes after the folder last changed.

p3 next cannot see whether you have read the outputs, KNOWN-GAPS.md or reviews/README.md; that part is up to you. When you are unsure what comes next, ask the Guide:

Say to the Guide
The baseline's full runs are done and committed. What is the one thing I should do next?

Next: Write your PREFERENCES.md. If anything on this page did not work as described, When it breaks has the symptoms and fixes, and I would like to hear about it too.
