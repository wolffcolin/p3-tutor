When it breaks

Symptoms and their fixes, grouped by where you meet them: starting the windows, running the bench, scoring and comparing, and the checks. Find the heading that matches what you see, and the fix is under it.

About 27 minutes to read in full; most visits need one section.

  • Starting the Guide, the Builder and your tutor
  • Running the bench
  • Scoring and comparing

  • Windows
  • Still stuck

Three windows come up on this page. The Guide Guide is Claude Code started with claude --agent p3-guide in work/p3-tutor; it explains and never changes a file. The Builder Builder is plain claude in the same folder; it changes your tutor and runs the p3 commands you ask for. A plain terminal Plain terminal is a terminal tab with no Claude Code in it, where the long runs go. The Guide and the Builder explains all three.

Before anything else

Read the exact message. Every error and warning p3 prints says what went wrong, and most of them name the command that fixes it. The words on the screen usually save half the debugging time, so copy them before you close anything.

Ask the Guide what it means. It can read your repo, run p3 check, and tell you who fixes the problem: you, the Builder, or me.

Say to the Guide
p3 printed this. What does it mean, and who should fix it?
(paste the exact output here)

If p3 next sent you here

uv run p3 next points at this page when p3 check has an integrity failure: something is broken, such as a changed course file or a run whose snapshot no longer matches. Its Now line reads 1 Set up: p3 check reports an integrity failure, and its Next line is that failure's FAIL line. A run folder of a bench that is still running does not count as one there until 90 minutes after its last change; You stopped a run says why. Integrity comes first because a broken measurement makes everything after it unreliable, and CI stays red until it is fixed. Run the check to see the whole line:

Run in the Builder, or a plain terminal
uv run p3 check

The FAIL lines are in the Integrity section at the top, and each names a file. Then look under p3 check fails for the usual causes.

Starting the Guide, the Builder and your tutor

The Guide acts like a course assistant, or does not know P3

What you see. A window you started as the Guide answers questions about the course in general, does not know what p3 next is, or offers to edit files.

Why. It was started in the wrong folder, usually the course repo's root instead of work/p3-tutor, or it was started as plain claude. There the course repo's own CLAUDE.md applies, and its role is a course assistant. The Guide is defined in work/p3-tutor/.claude/agents/p3-guide.md, which Claude Code only finds from inside the P3 repo.

How to tell. A real Guide window shows @p3-guide in its startup header, sends its own first message ("Where am I in Project 3, and what is the one thing I should do next?"), and says in its first reply that it is the Guide.

Fix.

  1. Type /exit in that window.

  2. Open work/p3-tutor as its own VS Code window: File > Open Folder and choose work/p3-tutor, or run code work/p3-tutor in a terminal at the course repo's root. Then every terminal you open in that window starts in the P3 repo.

  3. Open a terminal there (Terminal > New Terminal) and check you are at the repo root, the folder that holds p3.json:

    Run in a plain terminal in work/p3-tutor
    pwd
ls p3.json

    pwd should end in work/p3-tutor, and ls should list p3.json.

  4. Start the Guide again with claude --agent p3-guide.

If you started it in tutor/, the Guide may load but tell you to close the window and start it again from work/p3-tutor; do that.

Claude Code says it cannot find the agent p3-guide

Why. Claude Code finds project agents in .claude/agents/ of the folder you start it in and of the folders above it, up to the root of that repository. The Guide's file is in work/p3-tutor/.claude/agents/, below the course repo's root, so a session started at the course repo's root, or anywhere outside work/p3-tutor, never sees it.

Fix. Start it at the repo root, the folder with p3.json, as in the steps just above. Then check that the agent's file is there and unchanged:

Run in a plain terminal in work/p3-tutor
ls .claude/agents/
git status .claude/

You should see p3-guide.md, and git status should show nothing changed under .claude/. If it shows the file deleted or modified, put it back with git restore .claude/agents/p3-guide.md; it is a course file, and the Guide's whole instructions are in it. Check the spelling too: the name is p3-guide, with a hyphen. If the file was never in your repo at all, tell me.

You tried to start the Guide from the Claude Code panel

The Claude Code panel in VS Code cannot start an agent with --agent, so a panel session is always plain claude, which in work/p3-tutor is the Builder. The Guide needs a terminal: Terminal > New Terminal, then claude --agent p3-guide. You can use the panel for the Builder if you prefer it, as long as the VS Code window has work/p3-tutor open as its folder.

You pressed Enter on the trust question and Claude Code exited

What you saw. The first time Claude Code starts in a folder, it asks "Quick safety check: Is this a project you created or one you trust?". The choice that starts highlighted is No, exit, so pressing Enter right away closes Claude Code.

Fix. Start it again with the same command. When the question comes back, press the down arrow to Yes, I trust this folder, then Enter. Claude Code remembers the answer for that folder, so you see the question once per folder.

Why it matters for the Guide

The Guide's guard, the hook that keeps it read-only, is registered in the Guide's own file, and a hook there runs only once the folder is trusted. Trusting work/p3-tutor is what turns the guard on.

The Guide says a command is blocked

What you see. The Guide tries a command and reports that it was blocked, often with a line that starts p3-guide guard:, such as p3-guide guard: the Guide only reads, so it cannot run this: ....

Why. That is the guard working, not a fault. The Guide's guard is a hook the course ships, in .claude/agents/p3-guide.md and .claude/hooks/, that lets the Guide read files and run only read-only commands: p3 next, p3 check, p3 report, p3 compare --list, read-only git and a few others. Everything that writes a file, starts Claude Code or calls a model, such as p3 bench, p3 snapshot or p3 score, is blocked, and so is any read of a blind comparison's key. (This is not the guard you build in final, which keeps keys/ from your tutor's main conversation; that one is in tutor/.claude/settings.json.)

Fix. Nothing to fix. The Guide then tells you who runs the command instead, with the exact words for the Builder or the exact command for a plain terminal. Do that. Do not ask the Guide to find a way around its guard, and do not ask it to edit a file; that is the Builder's job.

The Guide says no Python was found

What you see. Every tool call of the Guide fails with:

p3-guide guard: no Python found on
this machine, so the Guide's tools
are off; see
guide/19-troubleshooting.html

Why. The guard is a small Python script, and a shell script finds a Python to run it: it tries python3, python and py on your PATH, in that order, and uses the first that is Python 3.8 or later, skipping the Microsoft Store placeholder that Windows sometimes installs as python3. With none, it blocks the Guide's tools rather than let the Guide run unguarded. uv run p3 can work even then, because uv can bring its own Python, so a working uv does not mean Python is on your PATH.

Fix. Check in a VS Code terminal:

Run in a plain terminal in work/p3-tutor
python --version
python3 --version
py --version

If none prints Python 3. and a number, install Python as the course's setup guide says (setup.md in the course repo, section 3, "Install Python"): on Windows and macOS, the installer from python.org, and on Windows, tick Add Python to PATH in the installer. Then close VS Code completely and open it again, so its new terminals see the new PATH, check python --version once more, and start the Guide again.

The Builder gives you a list of steps, or plans ahead

Why it should not. The Builder's rules, in the root CLAUDE.md, say it does one thing per request, ends with what it changed and at most one next action, and never plans the project, because long lists of things to do overwhelmed students in Project 2. Planning and "why" are the Guide's job.

Fix. Ask it for one thing:

Say to the Builder
Do only the first of those, then stop and tell me what you changed.

For "what next" or "why", ask the Guide instead, for example "What do I do after this round?". If the Builder keeps doing it, check that its window was started in work/p3-tutor, where the root CLAUDE.md loads by itself, because that file is where its rules live; if it was started somewhere else, close it and start claude again in work/p3-tutor.

Your tutor acts like a course assistant

Why. When you learn with your tutor, you start claude in work/p3-tutor/tutor, and Claude Code also reads the CLAUDE.md of every folder above the one it starts in: the P3 repo's root CLAUDE.md and, inside the course repo, the course's own. The root file tells a session in tutor/ to ignore it and be the tutor, but the course's file can still pull a session toward being a course assistant. The bench avoids this, because it runs each scenario in a fresh folder outside your repo.

Fix. First check that the session really started in tutor/ (pwd should end in work/p3-tutor/tutor). If it still acts that way, learn from a copy of tutor/ outside the course repo instead.

In your own session, your tutor does not wait for its subagents

Why. From c2-review on, your tutor starts subagents and needs their reports. In an interactive session (the terminal, VS Code or the desktop app), Claude can wait for a subagent only once fork mode is off, and it is on by default.

Fix. Put this in tutor/.claude/settings.local.json, then start claude in tutor/ again:

{"env": {"CLAUDE_CODE_FORK_SUBAGENT": "0"}}

That file is personal: it is never part of a config and never reaches the bench, which is the point, and git ignores it, so it never reaches your public repo either. Do not put this setting in tutor/.claude/settings.json, because there it would change how your tutor runs in the bench. The last section of tutor/.claude/agents/README.md says more.

Running the bench

p3 cannot find claude

What you see.

Could not find the claude command.
Install Claude Code (see setup.md in
the course repo) and open a new
terminal, or set P3_CLAUDE to the
full path of the claude program.

Why. p3 looks for Claude Code in the environment variable P3_CLAUDE first, and then for claude on your PATH, and names P3_CLAUDE when it finds neither.

Fix. Check that claude --version works in the same terminal. If it does not, find where claude really is (which claude in Git Bash, macOS or Linux; where.exe claude in PowerShell) and point P3_CLAUDE at it:

Use the path where your claude really is. A path with spaces works as it is, with or without quotes around the whole path.
TerminalCommand
Git Bashexport P3_CLAUDE="C:/Users/<you>/.local/bin/claude.exe"
PowerShell$env:P3_CLAUDE = "C:\Users\<you>\.local\bin\claude.exe"
macOS or Linuxexport P3_CLAUDE="$HOME/.local/bin/claude"

Each of these lasts until you close that terminal, so set it again in a new one, or open a new terminal after installing Claude Code so its PATH is current.

On Windows you may see a different message instead: The claude command here is ..., a Windows script that cannot pass a prompt safely. That means the first claude on your PATH is a .cmd or .bat file, which cannot pass the bench's prompts through intact. Install Claude Code with the official installer from setup.md so that where.exe claude lists claude.exe first, or set P3_CLAUDE to the full path of claude.exe.

And if the message starts `claude --version` did not answer, so nothing was run, p3 found a program but it did not answer; the message quotes what it said, and its advice is to check that Claude Code is installed and signed in. Signing in is the next section.

claude -p fails, or asks you to sign in

Fix. Open claude once in a terminal and sign in, then run the command again. The bench stops at the first scenario that fails this way, as it does at a usage limit (below), so no half-made run is kept.

You see "removed ANTHROPIC_API_KEY so the bench uses your Claude subscription"

That is p3 protecting you, and nothing needs fixing. In headless mode an API key in your shell silently replaces your subscription login, and after lecture 20 many of you have one set. So p3 removes ANTHROPIC_API_KEY and ANTHROPIC_AUTH_TOKEN from every claude it starts, and says so. It also removes Claude Code's own session variables, so running the bench from inside a Claude Code session is fine. You never need an API key in this project.

A run hits your usage limit

What happens. p3 bench stops at the first scenario that reports a usage limit, a sign-in problem or an API outage, stops every scenario still running, and starts no new one. Its message begins with what went wrong and then says Nothing in repeat k measures your tutor, so it was not saved as a run.

  • That repeat says nothing about your tutor, so it is not saved as a run: its files go to bench/runs/_live/_aborted/, which git ignores.
  • The repeats after it do not run, and the repeats before it are complete and kept.
  • If the limit comes while a run is being scored, the run keeps its run.json with no score.json. p3 report, p3 compare and p3 check ignore it until you score it with uv run p3 score <run-dir>.

Fix. Wait for the reset (/usage in any Claude Code window shows when), then run the bench again, with --repeats set to the number still missing. In the meantime, do the work that needs no Claude: your test topics, your reviews of runs you already have, the blind comparison once its runs exist, and the write-up.

Watch out

If you ever find a committed run whose result.json files say Claude was not working, delete that run, because it measures nothing. A scenario that failed for any other reason, such as a timeout or a lesson that was never written, is a result about your tutor: keep it and report it.

A scenario keeps hitting permission denials

Why. A bench scenario has no one to approve a tool, so the bench passes your config's permissions.allow list from tutor/.claude/settings.json to Claude Code, and in a fresh folder that list is the only thing that allows a tool. Anything else that would need a prompt is denied, and run.json lists every scenario's denials. The bench always adds Glob and Grep to the list, so every config can search its workspace the same way on every system.

Fix. Either allow the narrow command you need in tutor/.claude/settings.json, or tell the skill how to finish without it. Try the change with --config live before you snapshot.

Say to the Builder
Read the permission denials of the teach scenario in run.json of my latest live run, and tell me which narrow allow rule in tutor/.claude/settings.json would fix them, or how the skill could finish without it.

An allow rule is a change of Kind other in a quick round.

If the denials are in a run of a snapshot, that run stays as it is: it is a result about that config, and the fix belongs in a round of the step you are building.

A scenario times out, or writes nothing

Why. Each scenario has a time and a turn limit, set in bench/scenarios.json: teach 45 minutes and 200 turns, quiz and each grade 15 minutes and 80 turns, each tutor probe 10 minutes and 40 turns. A scenario that reaches one is stopped and recorded as a timeout or an error. A review loop with no cap on its passes, or a pipeline of many subagents, can run into these limits.

Fix. Read its trace, <scenario>/trace.jsonl.gz in the run folder. It opens with any gzip tool, and the Builder can read it for you:

Say to the Builder
Read teach/trace.jsonl.gz in my latest live run and tell me where the session spent its turns and why it stopped.

Then rerun just that scenario, keeping its working folder so you can look inside it afterwards; the command prints where the folder is.

Run in the Builder, or a plain terminal
uv run p3 bench --config live --only teach --keep

A later p3 bench deletes kept folders more than a day old. A timeout in a committed run of a snapshot is a result: keep it and report it.

You stopped a run, or its terminal closed

What you see. Stopped. bench/runs/<config>/<run-id> is incomplete (no run.json); delete it., or a run folder with no run.json in it.

First check that it really stopped. p3 bench writes run.json only when its last scenario ends, so p3 check reports a bench that is still running the same way, as bench/runs/<config>/<run-id>/ has no run.json (a run that was stopped; delete it). p3 next tells the two apart by time: a folder with no run.json that changed in the last 90 minutes is a bench still running, which its Also line names as bench/runs/<config>/<run-id> has no run.json yet: a bench still running (or one that stopped, which you delete), and only after 90 minutes with no change does it count as a stopped run. So if a bench is still going in your plain terminal, let it finish.

Fix. Delete that folder before you commit, because p3 check fails on a run folder with no run.json. In Git Bash, macOS or Linux:

Run in a plain terminal in work/p3-tutor
rm -r bench/runs/<config>/<run-id>

In PowerShell, Remove-Item -Recurse bench/runs/<config>/<run-id>. Then start the run again in a plain terminal, where closing a Claude Code window cannot stop it; that is why full runs go there.

p3 bench warns about a CLAUDE.md above the scenario folders

What you see. warning: <path> sits in a folder above the scenario folders, so Claude Code reads it in every scenario and it shapes your results; move it or rename it before you make runs you will commit (run.json records it as ancestor_memory)

Why. The bench runs each scenario in your system's temporary folder. On Windows that folder is inside your home folder, so a CLAUDE.md in your home folder itself would reach every scenario and change how your tutor behaves.

Fix. Move or rename the file the warning names before you make runs you will commit.

p3 bench warns about Windows' path limit

What you see. A warning that the run folders are so long that a scenario's files may pass Windows' 260-character path limit and fail to copy or to commit.

Fix. The warning's own fix: clone the repo to a shorter path, such as C:\work\p3-tutor, and run git config core.longpaths true in it. Open the new folder as its own VS Code window, as before, and start the Guide and the Builder in it.

p3 bench refuses your test topic

p3 bench --topic <id> runs one of your test topics only when it is valid, has no TODO markers left, and is committed and unchanged. The message says which of the three it is.

  • bench/own/<id>/ is not a valid topic, followed by the problems. Fix each one; uv run p3 check lists them too.
  • bench/own/<id>/ still has TODO markers; fill them in first, followed by where they are.
  • bench/own/<id>/ must be committed and unchanged before it is run. Commit it, check that git status shows nothing under it, and run the bench again:
Run in a plain terminal in work/p3-tutor
git add bench/own/<id>
git commit -m "Test topic <id>"
git status bench/own/

The commit rule exists so your items are on record before any result: a test you write after seeing how the tutor does is a test you can shape, even without meaning to. Your two test topics says more.

When git itself cannot be used, the message says why instead:

  • git is missing from your PATH: install it, or open a terminal where git --version works.
  • git does not trust the repository, usually because another account owns the folder: the message quotes git's own, which names the git config --global --add safe.directory fix with your folder's path. Run that.
  • The folder is not its own clone, for example a downloaded zip inside another repo: clone your repo with git and work in the clone.

Scoring and comparing

The scorer warns that no link could be checked

What you see. no link could be checked, because this Python cannot verify web certificates, so dead links are unknown; on macOS, run Install Certificates.command in your Python folder (in Applications), then score again: p3 score <run-id>

Why. This happens with the python.org installer on macOS until its Install Certificates.command has run.

Fix. Open the Python folder in Applications, double-click Install Certificates.command, then score the run again:

Run in a plain terminal in work/p3-tutor
uv run p3 score <run-dir>

Until then, the run's dead links are unknown, not zero, so do not report them as zero.

p3 compare refuses

What you see. A message that starts nothing to compare:, such as nothing to compare: final has no scored full run on agent-architecture at 30 minutes that ran the teach job, usually followed by a hint.

Why. Both configs need scored full runs on that topic at the same lesson length, and the message says which one is missing. Quick runs and --only runs are left out on purpose, so a short run never takes a full run's place.

Fix, by what the hint says:

  • A run is not scored, for example because you ran with --no-score or a usage limit came during scoring: score it first with uv run p3 score <run-dir>.
  • The runs are at another length: add --minutes M.
  • The runs are the length study's teach-only runs: add --teach-only (with --job teach).
  • There are no runs yet: make them first, with uv run p3 bench --config <name> in a plain terminal.

Three other refusals you may meet:

  • live runs are not committed and cannot be compared: snapshot the tutor, run the snapshot, and compare that.
  • session <id> is not finished: k of n pairs have no pick yet, when you try --reveal early: finish it with uv run p3 compare --resume <session-id>, because revealing early would end the blinding. uv run p3 compare --list shows your sessions.
  • cannot listen on 127.0.0.1:<port>: pick another port with --port, or leave it out for a free one. If a browser is awkward altogether, --terminal writes each pair as one side-by-side HTML file and asks the three questions in the terminal.

p3 check, p3 next and CI

p3 check lists a review as still to do, and you think it is done

Its line names the file and the heading, such as reviews/c1-skills.md, quick rounds with Quick rounds > Round 2: ... under it. p3 check finds each part of a review by its heading, so most causes are about headings and the exact form of a few lines. The usual causes:

  • A heading that no longer matches the template's word for word, such as #### Wording and misreadings for #### Wording and possible misreadings. Copy the heading back from the template.
  • One of the template's marker lines left somewhere in the part, such as a TODO under your text. A marker word inside code you quote, in backticks or a code block, is your quote and does not count.
  • A rating that is not a whole number from 1 to 5 on its own line: Rating: 4.5, Rating: four or Rating: 3-4 instead of Rating: 4.
  • A major review whose Run line does not name a scored full run of that step on the shared topic under bench/runs/. It should look like **Run:** bench/runs/c1-skills/20261105-141502-agent-architecture-m30-r1, with your own run id.
  • A major review that is complete on your disk but in no commit yet: complete here but in no commit yet; commit it. p3 check compares the time of that commit with when the run finished, so commit a review when you finish it.
  • A learning session whose Topic line does not start with the id of one of your test topics, such as **Topic:** statics-trusses, the method of joints; all three sessions must name the same test topic.
  • A skill or subagent in one of your snapshots whose name matches no heading in reviews/components.md. The heading is the skill's folder name or the subagent's name from its frontmatter, exactly.
  • A review file saved as UTF-16, which Windows PowerShell's > and Out-File write, or in another encoding than UTF-8. p3 check names the encoding. In VS Code, click the encoding in the status bar, choose Save with Encoding, then UTF-8.

A round of yours where only the Run line is missing is complete, so it gets a warning and not a TODO line; write the Run line anyway, because it is the trail I follow. Your reviews shows each part done well.

CI is red, but p3 check passes on your machine

CI runs python -m p3 check on the files you pushed, not on your disk. So the cause is a difference between what you pushed and what is on your disk, such as something committed without what it depends on: runs pushed without the snapshot they name in configs/, a blind comparison's session file without its key file, or a change you made and never committed. Run git status, commit what belongs together (configs/ with bench/runs/, both files of every session in bench/compare/), and push again. Then open the failed run in the Actions tab: its FAIL lines are the same as the ones p3 check would print.

p3 next says set up is not done

Why. Stage 1 of p3 next is done when your repo has an origin remote that is not the course's template. Without one, you are working in a copy that is not your own GitHub repo, such as a clone of the template itself or a downloaded zip, and nothing you push would reach a repo of yours.

Check.

Run in a plain terminal in work/p3-tutor
git remote -v
origin  https://github.com/<your-github-username>/p3-tutor.git (fetch)
origin  https://github.com/<your-github-username>/p3-tutor.git (push)

That is what it should show. Fix. If it shows no origin, do what p3 next says and point origin at your own repo on GitHub, with your own username: git remote add origin https://github.com/<your-github-username>/p3-tutor.git. If it shows the course's template, make your own copy with Use this template and clone it into work/p3-tutor, as Set up your repo describes. If you have already done work in the other copy, do not delete it; come to office hours or message me, and we will move it across without losing anything.

If its Now line reads 1 Set up: p3 check reports an integrity failure instead, set up is waiting on something broken, which is the case under If p3 next sent you here.

Windows

The template is written to run on Windows, macOS and Linux, and its own tests run on all three, but Windows is the setup I have tested least. A few things that help:

  • Use Git Bash for the commands, as in P2. PowerShell works for p3 too.
  • Line endings do not matter. Git stores this repo's text files with LF line endings, and every hash p3 computes ignores the difference, so a checkout with Windows line endings does not break the check.
  • Do not write review files with PowerShell's > or Out-File, which write UTF-16; edit them in VS Code, which saves UTF-8.
  • Your guard hook in final runs on your machine, so register it with the Python command that works in your own terminal (python on Windows, python3 on macOS and Linux), and use forward slashes in its paths. A hook that fails to start lets every tool call through, so a broken guard looks exactly like no guard, unless its entry in tutor/.claude/settings.json sets "onFailure": "block", which makes a hook that crashes or cannot run block the call instead. Either way, confirm with a live run and its trace that it runs; final, under the guard, says how.
