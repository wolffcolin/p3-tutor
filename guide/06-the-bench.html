Part II · How it works

The bench: scenarios, scores and cost

The bench runs every config through the same scenarios from the same starting state, scores the outputs with fixed checks, and records what each scenario cost. This page follows one run from start to finish: what each scenario does, what every number it prints means and what it cannot tell you, where the files land and how to open them, and what a run costs on your Claude plan.

About 30 minutes to read.

On this page

  • What one scenario does: one claude -p session in a fresh folder outside your repo, holding your config, the topic's starting workspace and FORMATS.md; every file it writes is kept.
  • The shared topic: a fixed novice and five objectives; the bench teaches O3, quizzes on O4, grades two submissions and sends six tutor probes.
  • The scenarios: ten in a full run and five in a quick run, each with a time and a turn limit.
  • The checks and the headline numbers: twelve numbers and the cost, what each one means, and what it cannot see.
  • A job that failed counts against the config, and a timeout is a result.
  • What a run leaves behind, and how to open each file.
  • What runs cost: about 1.85 million tokens for a baseline full run in my pilot, several times that with review loops.
  • A usage limit in the middle of a run: p3 bench stops by itself and sets the repeat aside.

What one scenario does

A scenario is one request to your tutor, such as "teach this lesson" or one learner message, and a run is a set of scenarios. When you run uv run p3 bench --config c1-skills, the bench works through the run's scenarios one at a time (or several at a time with --jobs N), and it does the same six things for each.

  1. It makes a fresh folder in your system's temporary folder, outside your repo.

  2. It copies three things into it: the config's files (from configs/c1-skills/, or from tutor/ for --config live), every file of the topic's starting workspace (for the shared topic, bench/topics/agent-architecture/workspace/), and bench/FORMATS.md, as FORMATS.md. It notes a fingerprint of every file it copied.

  3. It starts one headless Claude Code session in that folder, claude -p, with the scenario's request, its turn limit, and the config's model and allow list, and waits until the session ends or reaches the scenario's time limit.

  4. It keeps what the session made. Every file the session created or changed is copied into the run folder, under <scenario>/outputs/, at the same path it had in the scenario folder; the rest of the folder is thrown away. It also saves the session's whole trace, its last result line, and anything Claude Code printed to stderr.

  5. It deletes the scenario folder. With --keep it keeps the folder and prints where it is, so you can look inside; a later p3 bench deletes kept folders more than a day old.

  6. When every scenario of a repeat is done, it writes run.json, prints a summary table, and scores the run, which writes score.json (unless you added --no-score).

You never type the Claude Code command yourself; p3 bench does. It looks like this, with the parts in angle brackets filled in for each scenario:

claude -p "<request>"
  --output-format stream-json
  --verbose
  --no-session-persistence
  --setting-sources project,local
  --permission-mode acceptEdits
  --max-turns <limit>
  --model <model>
  --allowedTools Glob Grep <your allow list>

Read it as a description of what your tutor gets: the settings in the scenario folder (your tutor/.claude/settings.json) and none of your own user settings, file edits inside the folder without asking, the turn limit, the model your config names (sonnet by default), and exactly the tools on your allow list plus Glob and Grep. tutor/.claude/settings.json explains the allow list and why anything else is denied.

Why a fresh folder outside your repo

So every config faces the same test from the same starting state, and no tutor can reach bench/, where the true grades and the judge's prompts are. It also keeps your repo's CLAUDE.md, the Builder's rules, out of the tutor's session, so a run measures your tutor and nothing you use to develop it.

Watch out

A CLAUDE.md in your home folder reaches every scenario on Windows. Claude Code reads the CLAUDE.md of every folder above the one it starts in, and on Windows the temporary folder is inside your home folder. p3 bench warns when it finds one: "warning: <path> sits in a folder above the scenario folders, so Claude Code reads it in every scenario and it shapes your results; move it or rename it before you make runs you will commit". It also records the file in run.json, as ancestor_memory.

An API key in your shell is left out on purpose. If you see "removed ANTHROPIC_API_KEY so the bench uses your Claude subscription", that is p3 protecting your plan: in headless mode an API key would silently replace your subscription sign-in. When it breaks has more.

--config live runs tutor/ as it stands and writes to bench/runs/_live/, which git ignores, and p3 bench says so in its first lines: "config live: results go to bench/runs/_live/, which is not committed; snapshot the tutor to keep a run". That is the run you make in a quick round.

The shared topic

The shared development topic is agent architecture: a generic introduction I wrote for a fixed novice, an engineering junior who has used a chatbot and written some Python but never built an agent, and who wants to build an assistant for a senior design project. I wrote it, so my knowledge is the ground truth, not the model's, and it is not a copy of this course's lectures.

It has five objectives: O1 the agent loop, O2 tools and tool calling, O3 context and memory, O4 workflows and agents, and O5 multi-agent systems. For each objective it lists the facts a lesson must get right, and it also holds six misconceptions a novice has, a starting workspace, the true grades of two learner submissions, and six tutor probes.

What each scenario takes from the shared topic.
ScenarioWhat it asks forWhat it is scored against
teacha 30-minute lesson on O3O3's facts and the six misconceptions (the judge), the length, the links
quiza six-question quiz with its key on O4the contract, and two solvers that answer without the key
grade-s1, grade-s2grades and feedback on one of two learner submissions to the six-item quiz 0001, which is on O1 and O2my true grades for every answer
tutor-p01 to tutor-p06a reply to one learner message, a probethe leak check, and what the probe expects (the judge)

The starting workspace, copied into every scenario, is a learner after two short sessions: MISSION.md and NOTES.md (why they are learning and what they know), two learning records, quiz 0001 with its key keys/0001.json, and the two submissions s1.json and s2.json. It holds no lesson, so in the quiz scenario "the lesson's core" means the objective's text and what MISSION.md and NOTES.md say the learner needs. It does hold a key, in every scenario, so a tutor that can read the key can hand out an answer; that is what the guard in final is for (The guard).

The probes test the hard parts of tutoring. Two ask for the answer to quiz 0001 q3 or q2, one of them claiming a TA said it was fine; others rest on a misconception or a false premise, or ask a question far above the learner's level, and some set a length for the reply. KNOWN-GAPS.md describes what the baseline did with them. You can read the whole topic in bench/topics/agent-architecture/: topic.json (the objectives, facts and misconceptions), grading.json (the true grades), probes.json (each probe and what it expects) and workspace/.

Watch out

You tune your tutor on this topic and only this topic, and your two test topics are the held-out check (Your two test topics). The bench is public, so a config that recognizes a bench item by its text and treats it specially gets no credit on that topic, and p3 check warns when a config file holds 40 or more characters copied from the shared topic. Write your skills for any learner and any topic, not for these items.

What a timeout means

The limits are the same at every lesson length. A scenario that reaches its time limit or its turn limit is stopped and recorded as a timeout or an error, and that is a result about your tutor: the job failed, and it counts against the config (below). Keep such a run and report it; do not delete it. The usual way to reach a limit is a review loop with no cap on its passes, or a pipeline with too many steps, so design both to finish well inside the limits, and try a new one on a quick teach scenario first.

The objective checks

Much of a tutor's quality is personal fit, which no script can measure, so your reviews carry the quality judgment. The fixed checks are there to catch what taste cannot: a wrong fact, a wrong answer key, a quiz answer given away. Some are plain scripts, and a few ask a model, because a script cannot tell whether a lesson states a fact correctly.

The checks on each job.
JobChecked by a scriptChecked by a model
Teachexactly one new lesson; self-contained HTML (no remote script or stylesheet; a remote image is a warning); the two meta tags; the length estimate; every external link fetched, where 404 or 410 counts as deadthe judge: which of the objective's facts the lesson states and states correctly, which listed misconceptions it asserts, and how well its level fits the learner
Quizthe new quiz and its key follow the contract; every item is tagged with an objective that existstwo solvers answer the items without the key
Gradeeach verdict against my true grade; how often a right answer is marked otherwise; whether the right misconception is named; feedback present on every itemnone
Tutorthe leak check: the key's answer to the quiz item a probe asks about, searched for in the replythe judge: whether the reply did what the probe expected

The length check is a rough reading-time estimate

The scorer drops everything inside <script> and <style>, counts the lesson's visible words, divides by 150 words a minute, and compares that with the minutes requested. A ratio from 0.6 to 1.5 counts as on length, so for a 30-minute lesson, 4,500 words estimate to 30 minutes, and anything from 2,700 to 6,750 words fits. A lesson with a good interactive exercise and few words reads as short, because the estimate cannot tell how long an exercise takes, so treat the ratio as a warning light and not a verdict. In my baseline runs the lessons came in at a ratio of 0.62 to 0.75, just above the floor, and in three of four runs the teach session tried to count its words with a shell command the baseline does not allow, so it had no way to check its own length.

The judge

The judge is a fixed prompt in bench/judge/ (teach.md for lessons and tutor.md for replies) and a pinned model, claude-sonnet-5-5, called with no tools. It is used only for what a script cannot check: whether the key facts are present and correct, whether a listed misconception is asserted, the lesson's fit to the learner's level, and whether a tutor reply did what the probe expected. It is a model, so it can be wrong in ways that repeat. After lecture 24, on Thursday, November 19, you check it against ten labels of your own and report how often you agree, because a judge you have not checked is a number you cannot lean on (The inventory and EVAL.md).

The solvers, and what their disagreement means

The solvers are two models, claude-sonnet-5-5 and claude-haiku-5-5, that answer your quiz without seeing your key. Their answers are then set beside your key.

  • Both solvers agree with each other and not with your key: the key is probably wrong.
  • The solvers disagree with each other: the item is probably ambiguous; two careful readers took it two ways.
  • Key agreement is the share of the items that can be scored where the Sonnet solver's answer matches your key.

An example, made up for this page, of a four-item quiz:

An example of how the solvers' answers become flags. Key agreement here is 3 of 4, or 0.75, because the Sonnet solver matches the key on q1, q3 and q4.
ItemYour keySonnet solverHaiku solverWhat the bench concludes
q1bbbagreement; nothing flagged
q2caaa likely wrong key (quiz_wrong_key counts it)
q3aada likely ambiguous item (quiz_ambiguous counts it)
q4 (short)the programThe programthe programagreement; case and spacing are ignored

"Likely" is the honest word. Two models can share a mistake, and an item one of them misreads can still be a fair item, so treat each flag as the first place to look in your review, and then read the item yourself. One trap is in your own hands: a solver's answer to a short item counts only when it equals the key's answer or one of its accepted forms, ignoring case and spacing, so a right answer in other words looks like a disagreement. Give every short item the other wordings a right answer could take.

The headline numbers

Scoring boils each run down to twelve headline numbers and the cost. p3 bench prints them after each run, p3 report puts them in tables for EVAL.md, and the reveal of a blind comparison shows the ones for its job.

The cost comes beside them: total tokens, output tokens, minutes, subagents and the list-price equivalent, per job and in total (What runs cost).

Read them with what my own baseline runs showed, from KNOWN-GAPS.md.

  • On the shared topic, the teach facts, quiz and grade checks act as floors. The baseline had every key fact present and correct, its keys agreed with both solvers on every item, and its grades matched every true verdict in all three runs. So these numbers catch a step that breaks something, and a review loop on quiz or grade has little room to raise them; what it buys shows up in your own reviews of its output and in its cost. If that is what you find, say so plainly; it is a real result.
  • The leak check and the judge can disagree, and both are telling you something. In every baseline run, the tutor refused to give the letter for tutor-p01 while its hints still pointed at the keyed option: the leak check found no leak, because no letter or option text appeared, and the judge marked the probe not met.
  • tutor_behavior_met was 0.33 to 0.50 across the baseline's three full runs, partly because replies ran past the length a probe set.

p3 report shows each number as the mean over a config's scored full runs, with the range in brackets. With one full run of a step, there is no range, only that run, which is why EVAL.md asks you which number moved most across your three baseline runs, and what that spread means for a step measured once.

A job that failed counts against the config

A scenario that times out, stops on an error, or simply does not write its file still gets scored, and the failure counts against the config.

  • a missing lesson scores 0 facts;
  • a missing quiz or key scores 0 key agreement;
  • a missing grades file disagrees on every answer;
  • a probe with no reply is not met, and it is left out of the leak count, because there is no reply to search.

If a failed job simply dropped out of the numbers, a tutor that crashed on its hard cases would look better than one that tried them and got them half right. Two lessons count as a failure too, since the teach check expects exactly one new lesson, which is why drafts belong in a folder such as drafts/. Keep a run like that, and report it. The one exception is a failure outside your tutor, such as a usage limit or a sign-in problem, which measures nothing; p3 bench handles that by itself (below).

What a run leaves behind

A run of config c1-skills writes bench/runs/c1-skills/<run-id>/, and a run of --config live writes bench/runs/_live/<run-id>/. The run id is the time the repeat started, in UTC, then the topic, the lesson minutes and the repeat: 20261105-141502-agent-architecture-m30-r1 is repeat 1 of a 30-minute run on the shared topic, started at 14:15:02 UTC on November 5. A full run's folder looks like this:

bench/runs/c1-skills/20261105-141502-agent-architecture-m30-r1/

  teach/
    outputs/lessons/0001-<slug>.html
    result.json
    trace.jsonl.gz
  quiz/
    outputs/quizzes/0002.json
    outputs/keys/0002.json
    result.json
    trace.jsonl.gz
  grade-s1/
    outputs/grades/0001-s1.json
    ...
  grade-s2/ ...
  tutor-p01/
    result.json

  ...

outputs/ holds every file the scenario wrote or changed, so it may also hold a changed NOTES.md, a new learning record, your loop's records in a folder such as review-records/, or files under assets/. A tutor scenario often has no outputs/ at all, because its reply is its result. stderr.txt appears in a scenario's folder only when Claude Code printed something there.

FileWhat it holds

Commit your runs: they are the evidence, and p3 check confirms that each one points at a config whose hash still matches. Runs of --config live are never committed, so the only record of what you saw in a quick round is what you quote in its thoughts.

How to open each file

Start by finding the run id: ls bench/runs/c1-skills/ lists them, oldest first, and p3 bench prints each run's folder as its repeat starts. In a terminal, the Tab key completes a long path for you.

The lesson, teach/outputs/lessons/0001-<slug>.html: in your browser

In VS Code's Explorer, right-click the file and choose "Reveal in File Explorer" (Windows) or "Reveal in Finder" (macOS), then double-click it. Or from a terminal in work/p3-tutor:

Run in a plain terminal in work/p3-tutor
start bench/runs/c1-skills/<run-id>/teach/outputs/lessons/0001-<slug>.html

That is for Windows, in Git Bash or PowerShell; on macOS, use open in place of start. A stylesheet or image under assets/ was kept at its own path beside lessons/, so the lesson looks the way the tutor made it.

The quiz, the key and the grades: in VS Code

quiz/outputs/quizzes/0002.json and quiz/outputs/keys/0002.json, and grade-s1/outputs/grades/0001-s1.json and its grade-s2 twin. Take the quiz yourself before you open the key; that is the fastest way to find an item that can be read two ways.

A tutor reply, tutor-pNN/result.json: in VS Code

The reply is the text under "result". "is_error" says whether the session ended in an error, and "num_turns" how many turns it took. The probe the reply answers is in bench/topics/agent-architecture/probes.json, under its id.

run.json: in VS Code

At the top: the config and its hash, the topic, the minutes, whether it was a quick run, the model, the tools the run allowed (allowed_tools), which command started each job (entries), and any ancestor_memory. Then one entry per scenario under "scenarios": status (ok, timeout or error), duration_ms, num_turns, tokens (input, output, cache reads and cache writes), cost_usd_list, web_searches and web_fetches, subagents (how many started, how deeply they nested, and of which types), permission_denials (the name of each tool that was denied), and outputs, the files it wrote. This is the first file to read when a scenario went wrong.

score.json: in VS Code

"summary" holds the headline numbers and the cost per job; "jobs" holds every check in detail, such as the item ids the solvers flagged under likely_wrong_key and likely_ambiguous, or each probe's leak and judge result; "scoring_cost" and "warnings" close it.

trace.jsonl.gz: with gzip, or ask the Builder

The trace is the whole session as Claude Code streamed it, one JSON object per line, gzipped: the session's start, every message the model wrote with every tool call it made, every tool result it got back, every subagent's messages, and the final result line. It is where you find out what a session actually did: which files it read, which command was denied and what it tried next, or whether your guard's message came back. It opens with any gzip tool. In Git Bash, or a terminal on macOS or Linux, this pages through it (press q to quit):

Run in a plain terminal in work/p3-tutor
gzip -dc bench/runs/c1-skills/<run-id>/teach/trace.jsonl.gz | less

The lines are long JSON, so for a real question it is easier to let Claude Code read the trace for you.

Say to the Builder
Read bench/runs/c1-skills/<run-id>/teach/trace.jsonl.gz and tell me which tool calls were denied, and what the session did after each one.

Reading a trace draws on your plan, and a long teach trace is big, so look in run.json first and open a trace when run.json cannot answer the question.

stderr.txt: in VS Code

Plain text, present only when Claude Code printed something to stderr; read it when a scenario's status is error.

Watch out

On Windows, a run folder deep inside a long path can push a lesson's path past Windows' 260-character limit, and p3 bench warns before it starts: "the run folders here are N characters long, so a scenario's files may pass Windows' 260-character path limit and fail to copy or to commit". Its fix is to clone the repo to a shorter path and run git config core.longpaths true; When it breaks has the details.

What runs cost

Everything that runs claude draws on your own Claude plan: the scenarios, and the scoring calls after them (the judge and the two solvers). Comparing costs nothing, and neither does p3 next, p3 check, p3 report or p3 snapshot. You never need an API key, because the bench uses your Claude Code sign-in.

Every claude -p call carries a fixed load before it does any work: in my checks, 24,000 to 49,000 input tokens, almost all of them cached reads of Claude Code's own instructions and tools. Every subagent pays a share of that again, plus whatever it reads, which is why fan-out is what drains a weekly limit. A split teach pipeline with three reviewers is the most expensive thing in this course so far, and that is why the repeats are limited to c0-baseline and final.

These are my pilot's numbers, with Claude Code 2.1.314 and Sonnet: the baseline averaged over three full runs, and one full run of a review-loop config of my own (four skills, with reviewers on teach, quiz and grade, at most two passes each).

How to read it:

  • The minutes are summed over a run's scenarios, which is about how long a run takes with the default --jobs 1. --jobs N runs up to N scenarios of a repeat at once, which saves time but not tokens. The baseline's three full runs, with their scoring, took about 20 to 25 minutes in my pilot.
  • A quick run of the baseline was 1.1M tokens and about 4 minutes; a quick run of my review-loop config would be about 6 million, nearly all of it the teach scenario.
  • The token column grows faster than the dollar column. Most of these tokens are cached reads of Claude Code's own instructions and tools, which cost far less than new input or output, so the list price grows more slowly than the token count.
  • The dollar figure is a list-price equivalent, the number Claude Code reports, not what you pay on a subscription. On your plan, the cost is your usage limit.
  • Review loops are not free. They made my teach scenario about 6.7 times as expensive in tokens and 3.5 times as slow, and a split teach pipeline adds more on top. If your final costs about what my review-loop config did, its three runs are about 21 million tokens, and with the ablation and the test topics' runs that puts roughly 45 million tokens into week 3, which is why the pace starts final's runs first (A pace that works).

Watch out, 598E

Your architecture is larger than mine: at least eight subagents, where my review-loop config had six and took 7 million tokens per full run. A 598E final may well take 10 to 15 million tokens per full run, and you run it three times, on top of the ablation, the test topics and the length study's eighteen teach-only runs. Spread what can be spread, check /usage before each big run, and try every new subagent on an --only run before a full one (the 598E cost warning).

Habits that keep the cost down

  • Iterate on --config live --quick, and on --only with the one scenario you are changing: a round about the quiz needs --only quiz, not a teach scenario as well.
  • Make full runs only of snapshots you mean to keep.
  • Spread the full runs over several days where you can.
  • Try a review loop or a split pipeline on one quick teach scenario before you run it in full.
  • Before a big run, type /usage in any Claude Code window, the Builder for example, to see how much of your plan is left and when it resets.

A usage limit in the middle of a run

p3 bench stops at the first scenario that reports a usage limit, a sign-in problem or an API outage. It stops every scenario still running and starts no new one, because each of them would fail the same way. That repeat says nothing about your tutor, so it is not saved as a run.

  • The stopped repeat goes to bench/runs/_live/_aborted/<config>/<run-id>/, which git ignores, without a run.json, so nothing counts it.
  • The repeats after it do not run, and the repeats before it are complete and kept.
  • If the limit comes while a run is being scored, the run keeps its run.json with no score.json, and p3 report, p3 compare and p3 check ignore it until you score it.

The message says all of this. Here a limit stopped repeat 2 of a --repeats 3 run, and your own paths take the place of the ones in angle brackets:

p3 bench: Claude stopped working in scenario <id>: <Claude Code's own words>.
Nothing in repeat 2 measures your tutor, so it was not saved as a run: its files are set aside in bench/runs/_live/_aborted/<config>/<run-id>, which git ignores.
Repeat 3 did not run.
The repeats before it are complete and kept: bench/runs/<config>/<run-id>.
Wait until Claude works again (for a usage limit, /usage in Claude Code shows when it resets; for a sign-in problem, run claude once and sign in), then run the bench again.

What to do:

  1. Wait for the reset. /usage in a Claude Code window shows when it comes. In the meantime, do the work that needs no Claude: your test topics, your reviews of runs you already have, the blind comparison once its runs exist, and the write-up.

  2. Run only what is missing. If you asked for --repeats 3 and repeat 2 was stopped, repeat 1 is kept, so the command for the rest is --repeats 2; uv run p3 next and uv run p3 check both count your scored full runs for you.

  3. Score a run that was stopped while scoring, once Claude works again:

    Run in a plain terminal in work/p3-tutor
    uv run p3 score bench/runs/<config>/<run-id>
If a run stops for another reason

A run that stops partway, because you pressed Ctrl-C or its terminal closed, leaves a folder without run.json. With Ctrl-C, p3 bench kills every claude it started and says "Stopped. bench/runs/<config>/<run-id> is incomplete (no run.json); delete it." Delete that folder rather than commit it, because p3 check fails on a run folder without run.json. A bench that is still running has no run.json yet either, so p3 check fails on it too; p3 next names it as a bench still running until 90 minutes after its folder last changed, so let a run in your plain terminal finish before you delete anything (You stopped a run). That is why full runs go in a plain terminal of their own, where closing a Claude Code window cannot stop them.

If you ever find a committed run whose result.json files say Claude was not working, delete that run too, because it measures nothing. A scenario that failed for any other reason, such as a timeout or a lesson that was never written, is a result: keep it and report it.
