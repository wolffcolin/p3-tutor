Commands and files

Every p3 command with its options, what each one prints or writes, and whether it draws on your Claude plan; then every file and folder in your repo, who owns it, and where to find each output. Come here to look something up; the step pages explain when and why you run each command.

How to run a p3 command

p3 is the course's tool for this project: it snapshots your tutor, runs the bench, scores and reports runs, runs blind comparisons, and checks the repo. Every command runs from the root of your P3 repo, work/p3-tutor, and starts with uv run:

Run in the Builder, or a plain terminal
uv run p3 check

If you do not have uv, every command also works as python -m p3 check, or python3 -m p3 check on macOS and Linux, because p3 uses only Python's standard library, from Python 3.11 on. This guide writes every command with uv run; swap in the other form wherever you need it.

  • Help. uv run p3 --help lists the commands, and uv run p3 <command> --help lists a command's options. uv run p3 --version prints the version.
  • Which repo. p3 works on the nearest folder at or above the one you are in that holds p3.json, so it also works from tutor/; --root <path>, before the command name, points it at another repo.
  • Errors. A command that cannot do its job prints one message, starting with p3 <command>:, that says what is wrong and usually what to do, and exits with status 1. Ctrl-C prints p3: stopped.

Who runs what

You work in three places: the Guide window, which explains and changes nothing; the Builder window, which changes your tutor and runs commands you ask for; and a Plain terminal, a terminal tab with no Claude Code in it (The Guide and the Builder sets them up). Which one runs a command depends on how long it takes and whose judgment it records.

Where each command belongs.
CommandWhere it belongsWhy
p3 next, p3 check, p3 report, p3 compare --listanywhere; the Guide runs them itselfthey only read
p3 snapshot, p3 new-topicthe Builder when you ask, or a plain terminalthey write files, so the Guide may not run them
p3 bench --quick, or with --onlythe Builder, in the background, after it asks you; or a plain terminala quick run is short (about 4 minutes for the baseline in my pilot, longer once review loops are in), and the Builder says how many sessions it will start before it starts any

When the Guide says a command is blocked, that is its guard working: the Guide only reads, and it tells you who runs the command instead, with the exact words for the Builder or the exact command for a plain terminal.

p3 next

uv run p3 next

It prints where you are on the project's map and the one next thing to do, with the guide page that explains it. It makes no model call and changes nothing: it reads the same state p3 check reads, and exits 0 unless the repo cannot be read. Run it whenever you are unsure what comes next; a new Guide window runs it first thing.

Run in a plain terminal in work/p3-tutor, or ask the Guide
uv run p3 next
p3 next: 498E (C:\...\work\p3-tutor)

Done:  1 Set up, 2 The baseline, 3 Your preferences
Now:   4 Step 1, c1-skills: quick rounds (1 of at least 2 complete)
Next:  In the Builder window, say: Act on Round 2 of reviews/c1-skills.md.
Read:  guide/08-step1-skills.html#rounds
Also:  the baseline's runs: 2 of 3 scored full runs (start the last one in a plain terminal)
Done

the stages before the one you are in, and any later stage already complete.

Now

the first stage with something not done, and where you are in it.

Next

that stage's next item, as one action: the words to say to the Builder, the command to run in a plain terminal, or the file and heading to write under. A long run is always given as the exact command for a plain terminal, with --repeats N for the runs still missing, --topic <id> for a test topic, and --only teach --minutes M --repeats N for the length study.

Read

the guide page and section that explain it.

Also

sometimes: a bench still running (below), at most two items not done from earlier stages (the long runs left behind), and, when Next is a long run, the first later item that needs no run, as "While it runs: ...".

Two rules keep a long run from holding you back. A stage whose only items left are long runs counts as passed once you have done an item of a later stage, so you can go on while a run goes in a plain terminal, and Also keeps the run in view; within a stage the items stay in order, because a major review needs its run. And an item that needs runs you left behind sends Now back to the first of those runs: a blind comparison pairs only the runs there are when it starts, the test topics' open review reads their runs, and EVAL.md with no TODO reports on every run.

Two cases change the shape. When p3 check has an integrity failure, Now says so ("1 Set up: p3 check reports an integrity failure"), Next is its FAIL line, and Read is When it breaks, because nothing else is worth doing until the repo is sound. The one exception is a bench still running: a run folder with no run.json that changed in the last 90 minutes is not a failure for p3 next, which names it under Also, while p3 check still fails on it; after 90 minutes with no change it counts as a stopped run (You stopped a run). When everything p3 check --final checks is done, Now is 12 Hand in, and Next says the video, the push and the Canvas post remain.

What Next says during quick rounds

In stages 4, 5 and 7, p3 next looks at the first round in the step's review file that is not complete, and names the one thing that round needs.

  • The round is untouched: "Run the live tutor (uv run p3 bench --config live --quick, or --only with the scenarios you are working on), then write what you noticed under Round k > My thoughts in reviews/<step>.md."
  • Your thoughts are written and What changed still holds its markers: "In the Builder window, say: Act on Round k of reviews/<step>.md."
  • Something else in the round is incomplete: "Finish Round k in reviews/<step>.md:" and the first problem.
  • Every round is complete, and there are fewer than the minimum of two: "Add Round k to reviews/<step>.md by copying the last round with its marker lines."
  • The minimum is reached: in step 1, while one of the four required skills is missing from tutor/, "Add a round for the <job> skill: copy the last round of reviews/c1-skills.md with its marker lines, as Round k."; otherwise the rounds are done, and Next moves on to the snapshot.

The snapshot advice names what the step must hold, which neither p3 next nor p3 check can see: in step 1, "When the four skills are in and you are happy with the tutor, snapshot it: uv run p3 snapshot c1-skills (or add another round first)."; in step 2, "When teach, quiz and grade each have their review loop and you are happy with the tutor, ..."; in step 3, "When the teach job is split across its subagents and you are happy with the tutor, ...". So step 2 takes at least three rounds, one reviewer per round, even though p3 check counts only two.

p3 next cannot see everything: whether CI is green, whether you have read KNOWN-GAPS.md, or what your skills and subagents actually do. The Guide asks you about those when they matter.

p3 check

uv run p3 check [--final]

It prints a checklist of the repo's state, one line per item, in two parts, and it is the same command CI runs on every push (the p3-check workflow). It calls no model. Run it before every push.

  • Integrity, always: the fixed files are unchanged (p3/bench.sha256 matches), tutor/FORMATS.md is identical to bench/FORMATS.md, every snapshot matches its SNAPSHOT.json, every run names a config whose hash matches, every JSON file under bench/ and configs/ parses, every topic validates, every comparison record fits its configs and runs and has its key file, and c1-skills adds no subagent. A FAIL here makes the command exit with status 1, and turns CI red.
  • Hand-in: everything you hand in, from the snapshots and runs to every part of your reviews, the inventory and EVAL.md. Without --final, a missing item is a TODO line, which is work still to do and not an error; with --final, each one is a FAIL.

Each line starts with one of four words: OK (the item holds), TODO (hand-in work not done yet), WARN (worth a look, never a failure) or FAIL (something is broken, or, with --final, something the hand-in needs is missing). A line can have indented detail lines under it, such as the review headings still to write. On a fresh copy of the template it starts like this:

The reviews part of Hand-in reads your files in reviews/ and lists what is still to do in them, by file and heading, such as a round with an empty part, a rating that is not a whole number from 1 to 5, or a component with no inventory entry. Your reviews explains those lines, and When it breaks has the usual reasons for a FAIL and for a review it will not count. Run uv run p3 check --final before you hand in (Hand in).

p3 snapshot

uv run p3 snapshot <name> [--force]

It copies the config files of tutor/ (CLAUDE.md, PREFERENCES.md and everything under .claude/ except settings.local.json) into configs/<name>/, and records their hash in configs/<name>/SNAPSHOT.json. It calls no model.

The options of p3 snapshot.
Argument or optionWhat it does
<name>the config's name, such as c1-skills: lowercase letters, digits and hyphens, starting with a letter or a digit, at most 41 characters, and not live
--forcereplaces an existing snapshot of that name; when that snapshot has runs, p3 check then fails, because the runs no longer match it
Run in the Builder, or a plain terminal
uv run p3 snapshot c1-skills
configs/c1-skills/: <N> config files, sha256:<64 hexadecimal digits>
Run it with: p3 bench --config c1-skills

It refuses an existing name without --force, and a config file that is not UTF-8, naming the file. A snapshot explains the hash, why snapshots are frozen once they have runs, and when --force is safe.

p3 bench

uv run p3 bench --config <name>
    [--topic <id>] [--repeats N]
    [--quick] [--minutes M]
    [--only <ids>] [--jobs N] [--keep]
    [--no-score] [--offline]

It runs a config's tutor on a topic's scenarios, each one a headless claude -p session in a fresh folder outside your repo, saves everything each session did, and scores the run. It draws on your Claude plan: every scenario is a real Claude Code session, and so is each scoring call. The bench explains what a scenario does and what each number means.

Here are the commands you will use most.

Run in the Builder, or a plain terminal
uv run p3 bench --config live --quick

A quick round's run: five scenarios of tutor/ as it stands; add --only in place of --quick to run just the scenarios you are working on.

Run in a plain terminal in work/p3-tutor
uv run p3 bench --config c0-baseline --repeats 3

Three full runs of a snapshot, 30 sessions plus their scoring; start it when you can leave it running.

It may also print one of these lines, each worth reading; all but the last come before the first scenario starts:

  • for a live run, "config live: results go to bench/runs/_live/, which is not committed; snapshot the tutor to keep a run";
  • when you add --repeats to --quick, "--quick runs once; --repeats is ignored";
  • a warning that a CLAUDE.md sits in a folder above the scenario folders, so it reaches every scenario (What one scenario does);
  • on Windows, a warning that the run folders are long enough to pass the 260-character path limit (When it breaks);
  • a line saying it removed ANTHROPIC_API_KEY so the bench uses your Claude subscription;
  • after a run, a warning that Claude Code changed version during it.

And it refuses to start, with a message that says why, when the config does not exist ("there is no config named ..."), when a snapshot no longer matches its SNAPSHOT.json, when an --only id is not a scenario (it lists the real ones), when a test topic still has TODO markers or is not committed and unchanged, or when claude --version does not answer (the message names P3_CLAUDE). If a usage limit or a sign-in problem stops a run partway, it sets that repeat aside under bench/runs/_live/_aborted/; A usage limit in the middle of a run says what to do.

p3 score

uv run p3 score [--offline]
    [--no-model] <run>

It scores one run, or scores it again, and writes the run's score.json, replacing any earlier one. <run> is a run folder, such as bench/runs/c0-baseline/<run-id>, or just the run id. p3 bench already scores every run, so you need this command only in a few cases: a run made with --no-score, a run whose scoring a usage limit stopped, and a run scored before you fixed this Python's certificates on macOS. It draws on your plan for the judge and the two solvers, about 57,000 tokens for a full run in my pilot, unless you add --no-model.

The options of p3 score.
OptionWhat it does
--offlineskips the link checks, so teach_dead_links is unknown
--no-modelskips every check that calls a model (the judge and the solvers); the checks done by script still run

It prints "scored <run>", the twelve headline numbers, one line on what the scoring cost, and any warnings.

Watch out

Because p3 score replaces score.json, scoring a run again with --no-model replaces its judged numbers with unknowns (shown as "-"). Use --no-model to try the script checks for free, not on a run you will report.

p3 report

uv run p3 report [--topic <id>]
    [--configs a,b,...] [--minutes M]
    [--quick] [--teach-only]
    [--reviews]

It prints Markdown tables, for pasting into EVAL.md: one row per config with each headline number as the mean over its scored full runs and the range in brackets, with the run count, then a cost table per job and one for all jobs. In a report of the shared topic's full runs, it then adds "Your ratings": the 1 to 5 ratings from your major reviews in reviews/, one row per criterion and one column per step. It calls no model.

The options of p3 report.
OptionWhat it does
--topic <id>the topic; agent-architecture by default
--configs a,b,...only these configs, in this order; by default every config with a scored run
--minutes Monly runs at this lesson length; by default every length, one row each
--quickthe quick runs instead of the full ones
--teach-onlythe length study's teach-only runs (p3 bench --only teach) instead of the full runs
--reviewsonly the table of your ratings; the other options do not apply
Run in the Builder, or a plain terminal
uv run p3 report --configs c0-baseline,c1-skills

Runs made with --only are left out of a full-run report, because a job they did not run would count as zero tokens and minutes. "Your ratings" is left out of a report of a test topic, of quick runs or of teach-only runs. When there is nothing to report, it says so and why, for example "no scored full runs (quick runs and --only runs left out) on topic agent-architecture", and suggests --quick when only quick runs exist. The inventory and EVAL.md says where each table goes.

p3 compare

uv run p3 compare <config-a> <config-b>
    --job teach|quiz|grade|tutor
    [--minutes M] [--quick]
    [--teach-only] [--terminal]
    [--port P] [--topic <id>]
uv run p3 compare --resume <session-id>
uv run p3 compare --reveal <session-id>
uv run p3 compare --list

It runs a blind comparison: it puts two configs' outputs for the same task side by side, labelled only "Left" and "Right", records your pick for each pair, and at the end reveals which config was which, quality first and then cost. It calls no model, because the pairs come from runs you already have; it costs your reading time and nothing else. Run it yourself, in a plain terminal, because the picks must be yours.

The options of p3 compare.
OptionWhat it does
<config-a> <config-b>the two configs, such as c0-baseline final
--jobteach, quiz, grade or tutor: whose outputs to compare
--minutes Mpairs only runs at this lesson length; the topic's 30 by default
--quickpairs quick runs instead, for trying the tool out; p3 check does not count such a session
--teach-onlywith --job teach: pairs the length study's teach-only runs
--terminalwrites each pair as one side-by-side HTML file, prints its path, and asks the three questions in the terminal, for when a browser is awkward
--port Pthe local port for the comparison page; a free one by default
--topic <id>the topic; every comparison this project asks for is on the shared topic, the default, and there are none on the test topics
--resume <session-id>continues a session you closed; every answer was saved as you gave it
--reveal <session-id>shows the result of a finished session: the tally, the sign-test p-value, how often you could tell, your reasons, the objective checks, and only then the cost
--listlists your sessions

When a session starts it prints its id, how many pairs it found, where the key file is ("do not open it before the reveal"), and the address of the comparison page, which opens in your browser. It writes two files, bench/compare/<session-id>.json (the pairs and your picks) and bench/compare/<session-id>.key.json (which config was on which side); commit both after the reveal, and never open the key file before it. It refuses, saying which run is missing, when either config has no scored full run on the topic at that length. The blind comparison explains the whole procedure and how to read the tally.

p3 new-topic

uv run p3 new-topic <id>

It writes a skeleton test topic in bench/own/<id>/, with every file present, placeholder text marked TODO, and a short example of each JSON file's shape. The id is lowercase letters, digits and hyphens, such as statics-trusses. It calls no model.

Run in the Builder, or a plain terminal
uv run p3 new-topic statics-trusses
wrote bench/own/statics-trusses/ with 9 files
9 files hold TODO markers to fill in; p3 check lists them.
Then commit the topic before its first run: the bench runs an own topic only when it is committed and unchanged.

Your two test topics walks through filling it in, and bench/own/README.md says what each file holds.

p3 rehash

It rewrites p3/bench.sha256 after I change a fixed file in the course's template. Never run it in your repo. When p3 check reports that a fixed file differs from the course's version, restore that file from git instead (git checkout -- <path>). The point of the check is that your bench measures the same way as everyone's, and rehashing would only hide the difference from it.

The course's files you leave as they are

Besides bench/ (outside bench/own/), p3/, the test files already in tests/ and .github/workflows/, two parts of your repo belong to the course and run the windows you work in. They are not hash-checked, but please leave them as they are: the Guide's read-only limits come from them, and the Guide reads the guide to answer you.

.claude/agents/p3-guide.md

The Guide: claude --agent p3-guide starts a session with this file's body as its whole instructions, with the tools Read, Glob, Grep and Bash, and with a first message it sends by itself, "Where am I in Project 3, and what is the one thing I should do next?". Its frontmatter registers the Guide's guard as a PreToolUse hook.

.claude/hooks/guide_guard.sh and .claude/hooks/guide_guard.py

The Guide's guard. The shell script finds a working Python and hands it the hook's input; with no Python it blocks the Guide's tools, with a message that points at When it breaks. The Python script lets the Guide read anything except a blind comparison's key, run read-only shell commands, and run p3 next, p3 check, p3 report, p3 compare --list and any --help; it blocks everything else, with a message that tells the Guide to tell you who runs the command instead.

.claude/settings.json

The root settings, which the Guide and the Builder both load: an allow list for the read-only commands the Guide runs (p3 next, p3 check and p3 report through uv run, python -m, python3 -m and py -m, and git status, git log and git diff), so they run without a prompt, and a deny of Agent(p3-guide), so the Builder never hands work to the Guide.

guide/

This guide: index.html and the numbered pages, their stylesheet book.css and script book.js, the chapter list chapters.json, and build.py and _page-template.html, which I use to make the pages. It opens from disk, with no server: in VS Code, right-click guide/index.html and choose "Reveal in File Explorer" (Windows) or "Reveal in Finder" (macOS), then double-click it, or run start guide/index.html (Windows) or open guide/index.html (macOS) in a terminal in work/p3-tutor.

Watch out

There are two guards in this project, and they are not the same thing. The Guide's guard, above, is the course's, and keeps the Guide read-only. The guard you build in final is yours: a PreToolUse hook in tutor/.claude/settings.json that keeps keys/ from your tutor's main conversation (The guard).

The review files

You write your reviews yourself, in VS Code, in these files, under the headings they already have; you never type a review into a chat for an agent to write. Each file ships with marker lines, the word TODO where your words go; replace each one, keep every heading exactly as it is, because p3 check finds your reviews by their headings, and save as UTF-8. Your reviews explains every part, with examples.

Names and ids

A config name

lowercase letters, digits and hyphens, starting with a letter or a digit, at most 41 characters: c0-baseline, c1-skills, c2-review, c3-split, final, final-minus-<x>; live means tutor/ as it is now.

A run id

the time the repeat started in UTC, the topic, the lesson minutes and the repeat number, such as 20261105-141502-agent-architecture-m30-r1.

A scenario id

teach, quiz, grade- and a submission id (grade-s1, grade-s2), and tutor- and a probe id (tutor-p01 to tutor-p06); on a test topic, its own submissions and probes give the ids.

A session id

a blind comparison's id: the time it started in UTC and the job, such as 20261120-190312-tutor; uv run p3 compare --list shows yours.

A topic id

lowercase letters, digits and hyphens: agent-architecture for the shared topic, and your own, such as statics-trusses or knife-skills, in bench/own/.

If a command fails

Read its message first: every p3 message says what is wrong, and most say what to do. When it breaks has the symptoms and fixes, from a missing claude to a review p3 check will not count, and the glossary defines every term on this page. If the message does not make sense, paste it to the Guide.

Say to the Guide
This command failed with the message below. What does it mean, and who should run what next?

Paste the exact message under your question; the words on the screen usually save half the debugging time.
