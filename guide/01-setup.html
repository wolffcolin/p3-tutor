Part I · Getting set up

Set up your repo

This page takes you from the template to your own P3 repo: a public copy on GitHub, cloned into work/p3-tutor, open as its own VS Code window, with p3 check passing on your machine and in CI. It costs nothing from your Claude plan, and it is the step with the most ways to go wrong, so please do it on the day P3 is released.

About 14 minutes to read.

The short path

Why

Every later step runs in this repo, so it has to be your own public copy, in the right folder, with a green check, before you spend any of your Claude plan on it. Getting it right now means a problem shows up while there is plenty of time to ask.

Do
  1. In your browser, on GitHub: make your copy of the template with Use this template, named p3-tutor, Public.
  2. In a terminal at the root of the course repo: clone it into work/p3-tutor, then open work/p3-tutor as its own VS Code window.
  3. In a terminal in that new window: check p3.json, run uv run p3 check, then commit and push; then, in your browser, watch p3-check go green on your repo's Actions tab.
Done when

uv run p3 check shows Integrity: no failures., the p3-check run on your repo's Actions tab has a green check mark, and uv run p3 next lists 1 Set up under Done.

Then

The Guide and the Builder, to start the two windows you work in from now on.

What you are setting up

By the end of this page your files sit like this on your machine.

<course repo>/          your clone of the course repo
  work/                 your own space, which the course repo's git ignores
    p3-tutor/           your P3 repo: open this folder in VS Code
      README.md         the brief
      CLAUDE.md         the rules for the Builder, the Claude Code
                        window that builds
      p3.json           your section and your stretch
      tutor/            your tutor
      reviews/          your reviews
      guide/            this guide
      ...

Three choices shape that picture, and each has a reason. Your repo is your own copy on GitHub, because you hand it in by its URL. It sits inside work/, so it never gets in the way of course updates. And you open work/p3-tutor itself in VS Code, not the course repo around it, so every terminal and every Claude Code session starts inside your P3 repo. The sections below take these one at a time.

Make your copy of the template

  1. Open the P3 template's page on GitHub, the repo whose README.md is the Project 3 brief.

  2. Click Use this template, near the top right, then Create a new repository.

  3. Set the owner to your own GitHub account, name it p3-tutor, and choose Public. Leave the other options as they are.

  4. Click Create repository. GitHub makes the copy in a few seconds and opens its page, at github.com/<your-github-username>/p3-tutor.

Why it is this way

Public, because you hand the project in by posting your repo's URL on Canvas, and I read your work there, so it has to be open to me without an invitation. p3-tutor, because every path in this guide and in the README assumes work/p3-tutor, and when the names match you can copy any command as it is.

Watch out

Your repo is public, and so is its history: anything you commit stays readable even after you delete it. Never commit an API key, a password, or private information about anyone. You never need an API key in this project, because the bench runs on your Claude Code sign-in.

Clone it into work/p3-tutor

Open a terminal at the root of the course repo, the folder that holds work/, and clone your copy into work/p3-tutor with this command, putting your own GitHub username in place of the placeholder:

Run in a terminal at the root of the course repo
gh repo clone <your-github-username>/p3-tutor work/p3-tutor

If you would rather not type it, say "clone my P3 repo into work/p3-tutor" to Claude Code in the course repo, the way you use it for the rest of the course, and it does the same. That session is the course's assistant, not the Guide or the Builder, the two Claude Code windows you work in for P3 (The Guide and the Builder sets them up), so use it for the clone and nothing else in P3.

The course repo's git ignores everything in work/, so your P3 repo can live there as a git repository of its own, with its own history and its own remote on GitHub, and a course update never collides with it.

Check that you cloned your copy, and not the template itself:

Run in a terminal at the root of the course repo
git -C work/p3-tutor remote -v
What you will see

Two lines starting with origin, one ending in (fetch) and one in (push), each with your GitHub username and p3-tutor in the address.

Watch out

If the address names the course's template instead of your username, you cloned the template, and GitHub would refuse your pushes. Delete the work/p3-tutor folder and clone your own copy. uv run p3 next does not count setup as done until origin is a repo other than the course template.

If it fails

If gh says you are not logged in, run gh auth login as you did when you set up the course, then clone again. If it says the repository is not found, check the spelling of your username and that the repo is named exactly p3-tutor.

Open work/p3-tutor as its own VS Code window

Open the P3 repo as a VS Code window of its own, with work/p3-tutor as the folder at the top of the Explorer. Either way works:

  • In VS Code, choose File > Open Folder, go into your course repo, then into work, select p3-tutor, and open it.
  • Or, from a terminal at the root of the course repo, run code work/p3-tutor. If code is not found, use the menu instead.

VS Code may ask whether you trust the authors of the files in this folder. It is your own repo, so say yes. Keep the course repo's window too if you use it for other parts of the course, but do all of your P3 work in this one.

Why a window of its own

VS Code starts every terminal in the folder the window has open, and Claude Code starts in the folder of the terminal you start it from. Claude Code reads the CLAUDE.md of the folder it starts in and of every folder above it, and it finds project agents in the repo it starts in. So in this window, every Claude Code session gets the P3 repo's own CLAUDE.md, which holds the Builder's rules (one change per round, never write your parts of reviews/, ask before any bench run), and claude --agent p3-guide finds the Guide in .claude/agents/.

A session started at the course repo's root gets the course assistant's instructions instead, and it sees the P3 repo's CLAUDE.md only once it happens to read a file in work/p3-tutor, which can be too late: it may already have run a command or changed a file without those rules.

Now open a terminal in the new window, with Terminal > New Terminal. Its prompt shows the folder it is in, and it should end in p3-tutor; if you are not sure, run pwd, which prints the whole path. On Windows, use Git Bash for the commands, as in P2: open the small menu next to the + in the terminal panel and choose Git Bash. PowerShell works for p3 too.

Check uv, Claude Code and Python

Three programs need to work in this terminal, each for its own reason.

  • uv runs every p3 command in this guide, which is why they all start with uv run. You installed it for lecture 12.
  • claude is Claude Code itself: the two windows on the next page run it, and so does the bench, which starts it once for every scenario.
  • Python on your PATH, because the guard that keeps the Guide read-only is a small Python script, and it looks for python3, python or py on your PATH. uv can bring its own Python for p3, so a working uv does not prove that Python is on your PATH.
Run in a plain terminal in work/p3-tutor
uv --version
claude --version
python --version
What you will see

One line from each, with a version number in it. On macOS and Linux, type python3 --version for the last one.

If you do not have uv, every command also works as python -m p3 ... (on macOS and Linux, python3 -m p3 ...), because p3 uses only Python's standard library, from Python 3.11 on, so your Python should then be 3.11 or later. Wherever this guide says uv run p3 check, you would type python -m p3 check.

The first time you use uv run in this repo, uv sets up the project's environment before it runs the command, so you may see a few lines from uv itself. It builds the project into a .venv/ folder and writes a uv.lock file, and git ignores both, so git status shows no new file afterwards; p3 has no dependencies, so there is nothing to lock.

If it fails

If claude is not found, p3 cannot start the bench either. When it breaks shows how to point P3_CLAUDE at the program. If no Python is found, the Guide will say that its tools are off; the same page has the fix.

Set your section in p3.json

Open p3.json in the editor. It says which section you are in and which stretch you chose, and as it ships it reads:

{
  "section": "498E",
  "stretch": null
}
  • If you are in 498E, it is already right. Leave stretch as null until you choose one of the five stretch options, and then set it to that option's id (Stretch options and the 598E length study lists them).
  • If you are in 598E, your stretch is the length study, which is required, so set both now:
{
  "section": "598E",
  "stretch": "length-study"
}

p3 check reads your section to know which minimums to count you against (498E needs at least four skills and five subagents across your snapshots, 598E at least six and eight), and 598E or the length-study stretch switches on the length study's checks in uv run p3 check --final. Keep the double quotes around "498E" or "598E", keep the comma at the end of the "section" line, and write null without quotes.

If it fails

A section that is not exactly 498E or 598E gives a WARN line such as p3.json: section is '498e'; set it to "498E" or "598E", and a missing quote or comma gives a FAIL line saying that p3.json does not parse. Fix the file and run the check again.

Run p3 check, and read what it says

p3 check is the command you will run more than any other. It reads your whole repo, makes no model call and costs nothing, and prints a checklist of the repo's state: whether the course's fixed files are unchanged, whether your snapshots and runs still match each other, and what is still to do for the hand-in, down to which review still holds a marker.

Run in a plain terminal in work/p3-tutor
uv run p3 check
p3 check: 498E (C:\...\work\p3-tutor)

Integrity
  OK    p3.json: section 498E, no stretch chosen yet
  OK    p3/bench.sha256 matches the 31 fixed files
  OK    tutor/FORMATS.md is identical to bench/FORMATS.md
  OK    configs/c0-baseline/ matches its SNAPSHOT.json (14 files)
  OK    bench/runs/: no runs yet
  ...
  OK    no config file copies 40 or more characters from a shared topic

Hand-in
  TODO  EVAL.md: 30 TODO markers left (lines 31, 38, 49, 55, 65, 77, 84, 90, 98, 110, ...)
  OK    config c0-baseline: the baseline
  TODO  config c1-skills: not snapshotted yet (p3 snapshot c1-skills)
  ...
  TODO  runs of c0-baseline: 0 of the 3 scored full runs needed on agent-architecture at 30 minutes (p3 bench --config c0-baseline --repeats 3)
  ...
  TODO  reviews/c1-skills.md, quick rounds: 0 of the 2 complete rounds needed
          Quick rounds > Round 1: not written yet
          Quick rounds > Round 2: not written yet
  ...

Integrity: no failures.
Hand-in: 2 of 29 items done (TODO lines are work still to do; p3 check --final fails on them).

That is the fresh template's output, trimmed where it says ...; yours starts with your own path, and the numbers can differ a little. On a fresh copy almost every Hand-in line is TODO, and that is exactly right: you have not done the work yet.

Each line starts with one of four words.

OK
The item holds.
TODO
Hand-in work you have not done yet. It is work to do, not an error, and it never makes the check fail. The text in parentheses often names the command that does it.
WARN
Worth a look, such as a file to tidy, and never a failure.
FAIL
Something is broken, and the line names the file to look at. Only a FAIL makes the check fail.

The Integrity section is what must hold at every moment of the project: the fixed files unchanged, every snapshot matching its recorded hash, every run pointing at a config that still matches it. The Hand-in section is everything you hand in, item by item. The last two lines add it up. Integrity: no failures. is the line you want to see before every push. The Hand-in count goes up as you work, and at the very end, uv run p3 check --final turns every TODO that is left into a FAIL, so that one command tells you whether the hand-in is complete (Hand in covers it).

What you will see

On a fresh copy: no FAIL line, Integrity: no failures., and a long list of TODO lines. That is a working setup.

If it fails

A FAIL line on a fresh copy usually means a file changed on the way, for example an edit under bench/ or p3/, which are the course's fixed files. Restore it with git restore <path> and run the check again, or see When it breaks.

Commit, push, and watch CI go green

Your repo comes with a GitHub Actions workflow called p3-check, which runs the same check on GitHub every time you push. Commit what you changed and push it:

Run in a plain terminal in work/p3-tutor
git status
git add -A
git commit -m "Set my section in p3.json"
git push

git status first shows you what is about to go in, so nothing surprises you. Then open your repo on GitHub, click the Actions tab, and click the newest p3-check run. When it finishes, a green check mark next to it means it passed.

If git says there is nothing to commit, which happens when you are in 498E and did not need to change p3.json, start a run by hand: on the Actions tab, choose p3-check in the list on the left, then Run workflow.

What CI checks, and why it is there

CI runs python -m p3 check on a fresh machine of GitHub's, on exactly the files you pushed, with their full git history. It never calls a model: your runs were made on your machine with your Claude plan, and CI checks them as you committed them. Like the check on your machine, only a FAIL line turns it red; TODO lines keep it green.

It is there because "it works on my machine" is not the same as "it is in the repo I handed in". When your own check passes and CI fails, a file is usually missing from a commit or different from yours, and you want to find that out now, not on the last night. A green p3-check is also part of the setup points.

If it fails

Click the red run, then the check job, then the Run p3 check step, and read its FAIL lines: each one names the file. Fix it on your machine, check that uv run p3 check shows Integrity: no failures., and push again.

From the next page on, you can also ask the Builder to commit and push for you.

Open this guide from your repo

This guide is part of your repo, in guide/, so the pages you read always match the version of the project you have. The pages open straight from disk in any browser, with no server and nothing to install. Open guide/index.html in one of these ways:

  • In VS Code's Explorer, right-click guide/index.html, choose Reveal in File Explorer (Windows) or Reveal in Finder (macOS), and double-click the file.
  • From a terminal in work/p3-tutor, run start guide/index.html on Windows (in Git Bash or PowerShell) or open guide/index.html on macOS.

Bookmark the page in your browser, so it is one click away for the next three weeks. The Guide window reads these same pages from your repo, so when it says "see guide/08-step1-skills.html, under Rounds", that is a page you can open here.
