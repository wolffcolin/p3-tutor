Part I · Getting set up

The Guide and the Builder

You work on P3 through two Claude Code windows with separate jobs: the Guide explains and tells you the one next thing, and the Builder changes your tutor. This page shows how to start each one, what to say to each, what each will not do, and where the other two terminals, a plain terminal for long runs and your tutor's own window, fit in.

About 24 minutes to read.

The short path

Why

In P2 one agent both guided you and built for you, and many of you found that confusing. Here each window has one job, so you always know which one to ask: the Guide to understand, the Builder to change something.

Do
  1. In the VS Code window of work/p3-tutor, open a terminal (Terminal > New Terminal) and start the Guide in it: claude --agent p3-guide.
  2. In that terminal, if Claude Code asks whether you trust this folder, press the down arrow to Yes, I trust this folder, then Enter; the highlighted choice is "No, exit".
  3. Open a second terminal (the split button in the terminal panel, or Terminal > New Terminal) and start the Builder in it: claude.
Done when

One window's header shows @p3-guide, and that window has told you your next step, with the reason for it. The other window runs plain claude and is waiting for you.

Then

Run the baseline and read what it made, or ask the Guide what's next.

Why two Claude Code windows and not one

In Project 2 one agent did everything: it told you what to do next, and then it did it. Many of you told me that it asked you to do a lot of things without saying why, that long lists of steps were overwhelming, and that it was hard to tell when it was teaching you and when it was building for you. So P3 splits those jobs between two sessions of Claude Code with different instructions.

  • The Guide is a Claude Code session started as a custom agent, p3-guide, whose whole instructions are in .claude/agents/p3-guide.md. Its first rule is one thing at a time: each reply gives one next action, or two that belong together, with the reason first, and then it waits for you.
  • The Builder is plain Claude Code at the repo's root, with Claude Code's own instructions plus the repo's CLAUDE.md, which holds the rules written for it: one thing per request and one change per round, never your words, ask before any run, and for "what next" questions, send you to the Guide.

The cost is one more terminal to keep open, and a habit to learn: ask the Guide when you want to understand, and the Builder when you want something changed. If after a few days this split feels wrong for how you work, tell me; I would rather adjust it than have you keep working in a way that does not suit you.

Start the Guide

  1. Open a terminal in the VS Code window of work/p3-tutor, with Terminal > New Terminal. Its prompt should show a path that ends in p3-tutor; if you are not sure, pwd prints the whole path.

  2. Start the Guide.

    Run in a new terminal in work/p3-tutor
    claude --agent p3-guide

  3. Answer the trust question, if it comes. The first time Claude Code starts in this folder it asks whether you trust it, and the highlighted choice is "No, exit"; The trust question below shows what to press.

  4. Look at the header. Claude Code's startup header shows @p3-guide, which tells you this window is the Guide and not the Builder.

  5. Watch the first message send itself. Without your typing anything, the question "Where am I in Project 3, and what is the one thing I should do next?" appears as the first message, because the Guide is set up to ask it on your behalf as soon as it starts.

  6. Read its reply. The Guide runs uv run p3 next, which you see it do in the window, and answers from what that command prints.

Its first reply says in a sentence who it is, then gives one next thing with the reason for it, and then hands that thing to the right place. Right after setup, that next thing is the baseline's first run, which is the next page of this guide. Later in the project, a first reply looks something like this.

I'm the Guide: I explain the project and point the way, and the Builder window is the one that changes your tutor.

You have finished Round 1 of c1-skills and written your thoughts for Round 2, so the next thing is for the Builder to make the one change those thoughts ask for. Keeping it to one change means your next run shows exactly what that change did.

Say to the Builder:

    Act on Round 2 of reviews/c1-skills.md.

There is more in guide/08-step1-skills.html, under Rounds.

That is an example, and the Guide's words will differ, but its shape stays the same. When it hands you something to do, it uses one of four forms, and they match the boxes in this guide:

  • "Say to the Builder:" and one sentence you can paste into the Builder's window, naming the file and the round.
  • "Run in a plain terminal in work/p3-tutor:" and the exact command.
  • For your own writing: the file, the heading to write under, and what kind of thing goes there, but never the words themselves.
  • For your tutor: "Open a terminal in work/p3-tutor/tutor and start claude there", and what to try in it.

When an idea is new, the Guide may end with one short question to check that it landed, or offer to go deeper. Answering helps it set the level of the next explanation, and saying "skip" is fine. When you have done the thing, come back to the Guide and say so; it runs uv run p3 next again before it says what follows, because the repo has changed.

The trust question, and its "No, exit" default

The first time Claude Code starts in a folder, it may ask:

What you will see

"Quick safety check: Is this a project you created or one you trust?", with the choice "No, exit" highlighted.

Press the down arrow to move to Yes, I trust this folder, then press Enter. If you press Enter straight away, which is easy to do by habit, Claude Code exits; nothing is harmed, and you start it again with the same command.

Why it asks, and why yes is right here

A project folder can hold settings, hooks and instructions that run on your machine, so Claude Code asks before it uses a folder for the first time. This is your own repo, made from the course template, so trusting it is right. It also matters for the Guide: the guard that keeps the Guide read-only is a hook, and the Guide's hooks run only once you have trusted the folder.

The Guide and the Builder both start in work/p3-tutor, so you answer once for both. You may see the question again the first time you start claude in tutor/; answer it the same way.

When the session starts, Claude Code also tells you its permission mode. Recent versions start in Auto mode by default, so most read-only commands run without asking you first. That is fine for both windows: the Guide's limits come from its guard and not from prompts, and the Builder's rule to ask you before any bench run comes from the repo's CLAUDE.md.

Start the Builder

  1. Open a second terminal. Click the split button in the terminal panel's toolbar to put it beside the Guide, or use Terminal > New Terminal for a new tab. It starts in work/p3-tutor, like the first.

  2. Start Claude Code with no agent.

    Run in a second terminal in work/p3-tutor
    claude

  3. Check the header. It has no @p3-guide in it, so this is the Builder. It waits for you; it sends no first message.

You do not need to tell the Builder anything before your first request. Because it starts at the repo's root, Claude Code reads the repo's CLAUDE.md by itself before your first message, and that file holds the Builder's rules. Every Claude Code session at the root that was not started with --agent p3-guide is a Builder, so if you close it, any new claude in this folder is a Builder again.

The Claude Code panel

If you prefer the Claude Code panel in VS Code for the Builder, it works the same way, as long as this VS Code window has work/p3-tutor open as its folder. The Guide needs a terminal, because the panel cannot start a session as an agent with --agent.

What to say to the Guide

Ask the Guide anything about what you are doing, why, or what comes next. It reads the page of this guide for the step you are on, and the README, before it explains, and it tells you which page and section it used. Here are requests that work well.

Say to the Guide
What's next?

It runs uv run p3 next and gives you one next thing, the reason for it, and the window or command that does it. Say this whenever you come back to the project or finish something.

Say to the Guide
Why does the project ask me to add only one component per round?

Any "why does the project ask for this" question. It answers from the guide and the README, in a few sentences, with the page to read for more.

Say to the Guide
What does the criterion "Wording and possible misreadings" ask me to look for?

It explains the criterion and what good evidence for it looks like, such as item ids and quotes. It does not write your feedback, and it does not rate anything.

Say to the Guide
Explain this line of p3 check: TODO  reviews/c1-skills.md, quick rounds: 0 of the 2 complete rounds needed

Paste any line from p3 check, p3 next or a bench run's summary that you do not understand. It reads the files the line names before it answers.

Say to the Guide
How much is left before I can snapshot c1-skills?

It tells you how many things are left and which one is next, and not a list of all of them, so you can keep your attention on one thing.

If you ask the Guide for the whole plan, it gives you its shape in two or three sentences, points you to the map, and comes back to the next step. If you have been stuck for a while, say so; it will make the next step smaller, and it will mention office hours.

What to say to the Builder

Ask the Builder to change something, run something, or explain a change it made. Give it one thing per message: when you ask for several, it does the first, says in a sentence what it left, and waits.

Say to the Builder
Act on Round 2 of reviews/c1-skills.md.

The request you will use most. It reads your thoughts in that round (and the round before), makes one change to the tutor in tutor/, writes the round's What changed (the Kind, the Files and the Why) under your thoughts, and for a new component fills in the inventory's factual fields. Then it tells you what it changed and suggests the cheapest run that shows it.

Say to the Builder
Run the cheapest run that shows this change.

It names the command, such as uv run p3 bench --config live --only quiz for a change to the quiz skill, says how many sessions it will start, and waits for your yes before it starts the run in the background. A full run it never starts itself: it gives you the command for a plain terminal.

Say to the Builder
Snapshot the tutor as c1-skills.

It runs uv run p3 snapshot c1-skills, which freezes the tutor's config under that name. Ask for this only when the step holds what it must, for c1-skills the four skills, and you are happy with it, because a snapshot is frozen once it has runs.

Say to the Builder
What exactly did you change in the grade skill, and why?

A question about a change it made is the Builder's to answer, with the lines it changed.

Say to the Builder
Commit configs/, bench/runs/ and reviews/, and push.

It commits and pushes for you. It commits your reviews as you wrote them; it never edits your words to do it.

What each window will not do, and why

The Guide never changes a file

The Guide has four tools: reading a file, finding files, searching in files, and a shell. The first three only read; the shell could write, so a guard checks it: a hook, a small script that Claude Code runs before each of the Guide's tool calls, which lets through only read-only commands such as uv run p3 next, uv run p3 check, uv run p3 report, git status and cat, and blocks everything else, including p3 bench, p3 score and p3 snapshot. When the Guide reaches for something outside its list, the guard blocks the call, and the Guide reads the guard's message and tells you who runs it instead, with the exact words for the Builder or the exact command for a plain terminal. You may see the guard's message in the Guide's window, for example:

p3-guide guard: the Guide only reads, so it cannot run this: p3 bench is not one of the Guide's read-only commands (next, check, report, compare --list). Tell the student who runs it instead: ...

That message means the guard is working, not that something broke.

Why read-only? So you can ask the Guide anything without worrying that it changes your tutor or your reviews. So that only one window ever changes the tutor, and only when you ask, which keeps each round's evidence clean. And because a guide that also builds is exactly what confused you in P2. The guard also keeps the Guide out of a blind comparison's key file, and its instructions keep it from making or suggesting blind picks, because those picks have to be yours.

The Builder does not plan the project

Ask the Builder what comes next in the project, or why the project asks for something, and it answers in one sentence that the Guide window is the place for that, with the words to use, such as "Ask the Guide: what do I do after this round?" It is not being unhelpful: a building agent that also hands out plans is how you got lists of ten things at once in P2. A question about the change it just made is still the Builder's to answer. Each of its replies ends with what it changed and at most one next action, usually the cheapest run that shows the change, and then it waits.

Neither one writes your reviews

Your reviews are the measurement in this project. A script can check that a fact is present or that a key agrees with two solvers, but only you can say whether a lesson worked for you, and if an agent wrote those words, the review would measure the agent instead of you. So neither window writes, drafts, rewords or tidies your parts: the Run lines, your thoughts, your live tries, every rating and its feedback, the comparisons with the previous step, what the next step should fix, your learning sessions, your test-topic reviews, and each inventory entry's Purpose, Review and Kept in final. The Builder writes only the What changed part of each round, and the inventory's Kind, Step added, and With and without, which you then check.

You can still get help. The Guide can explain what a criterion means, ask you a question that helps you notice something, and show what good evidence looks like. The Builder can offer wording in the chat when you ask for it. Either way, you type your own version into the file.

Where your own words go: the file, in the editor

This is the one rule of the windows that matters most: your reviews go in the review file, in the editor, never in a chat. The review files are Markdown files in reviews/, and each one ships with the headings already in place and a marker line, TODO, where each of your parts goes.

For the first quick round of step 1, for example, you open reviews/c1-skills.md in VS Code (Explorer, then reviews, then c1-skills.md), find ## Quick rounds, then ### Round 1, and replace the TODO after **Run:** with the folder of the run you looked at, and the TODO under **My thoughts:** with your own words. You leave **What changed:** as it is, for the Builder. A round from a student's file, with both parts written, looks like this:

### Round 2

**Run:** bench/runs/_live/20261105-141502-agent-architecture-m30-r1, a quick run

**My thoughts:**

The new quiz skill helped: the six items now mix mcq, numeric and short, where the quiz in Round 1 was six mcq items.
But q4 asks for "the best design" without saying best for what, and I could argue for two of its options.
The feedback on s1 q5 marks it partial, which is right, but it only says "You are close, think about why", and it never says that my answer gave the what and missed the why.
I want feedback that says which part of an answer was right, which part was missing, and one thing to reread.

**What changed:**

- Kind: new skill
- Files: tutor/.claude/skills/grade/SKILL.md
- Why: Grading still ran inside /teach with no rule for feedback; a grade skill of its own names what was right, what was missing and one thing to reread for every item, as these thoughts ask.

The Run line and My thoughts are the student's; What changed is the Builder's. The full example is in reviews/README.md, and Your reviews explains every part of every review.

Why the file and never the chat

A chat is not part of your repo: p3 check cannot count what you typed there, and I never see it. If you type a review into a chat and ask an agent to put it in the file, the words in the file came through an agent, which is the one thing the reviews must never do. And the Builder's job starts from the file: "Act on Round 2 of reviews/c1-skills.md" makes it read your words exactly where you wrote them.

Watch out

Keep every heading exactly as it is, because p3 check finds each part of a review by its heading. Write your text in place of the marker line, and delete the marker. Save the file as UTF-8, which VS Code does by default.

One quick round, across the windows

A quick round is how you build each step: you run the tutor as it stands, read and try what it made, write what you think, and the Builder makes one change from what you wrote. This is how one round moves across the windows.

  1. A run of the tutor as it stands. Ask the Builder for the cheapest run that shows what you are working on, or run it yourself:

    Run in the Builder, or a plain terminal
    uv run p3 bench --config live --quick

    --config live runs tutor/ as it is right now, and --quick runs five of the ten scenarios once; add --only quiz (or any list of scenario ids) instead of --quick to rerun just the part you are working on, which costs less. Live runs go to bench/runs/_live/, which git ignores.

  2. Read and try what it made, in your browser and the editor: the lesson under teach/outputs/lessons/ in the run's folder, the quiz (take it yourself before you look at the key), the feedback on the graded answers, and the tutor's replies in each probe's result.json.

  3. Write the round, in the editor. In reviews/c1-skills.md, under the round's **Run:**, the run's folder, and under **My thoughts:**, a few sentences: what worked, what did not, and what you want changed, with quotes, because live runs are not committed and your thoughts are the only record of them. From Round 2 on, begin your thoughts with whether the last change helped. The file ships with Rounds 1 and 2; from Round 3 on, add each round yourself by copying the last one with its marker lines.

  4. Hand it to the Builder.

    Say to the Builder
    Act on Round 1 of reviews/c1-skills.md.

    It makes one change and writes What changed under your thoughts. The next round's run then shows the tutor with that change, so the run before the round is the tutor without it and the run after is the tutor with it.

Step 1, under Rounds, walks through the rounds of the first step in full, and Your reviews explains why the rounds work this way.

The plain terminal, for full runs

A full run runs all ten scenarios of the bench on a snapshot once (teach, quiz, the two grade scenarios and the six tutor probes) and then scores them. In my pilot one full run took about 6 minutes for the baseline and about 17 for a config with review loops, at the default --jobs 1; the baseline's three full runs together took about 20 to 25 minutes, and three repeats of a larger config can take an hour or more. The teach scenario alone may run up to 45 minutes. A run can last longer than a Claude Code window allows: Claude Code stops a command it runs in the foreground after ten minutes at most, and a run a Claude Code window started stops when that window closes. So full runs go in a third terminal with no Claude Code in it, where nothing stops them but you.

Open it the same way as the others, with Terminal > New Terminal in the VS Code window of work/p3-tutor; on Windows, choose Git Bash, as in P2. When a full run is next, the Guide or the Builder gives you the exact command, for example:

Run in a plain terminal in work/p3-tutor
uv run p3 bench --config c1-skills

Start it, and keep working in the other windows: the reading and writing of the project goes on while a run goes, and that is how the three weeks fit. The run prints a summary table when it finishes.

Watch out

A terminal inside VS Code ends when you quit VS Code, so keep VS Code open, and your computer awake, until the run prints its summary table. If you stop a run halfway, its folder in bench/runs/ has no run.json; delete that folder rather than commit it. A run that reaches your usage limit stops by itself and sets that repeat aside; When it breaks says what to do next.

Your tutor's window

When you learn with your tutor, as a real learner would, you start Claude Code inside tutor/, where the tutor's own CLAUDE.md, skills and settings are. You do this for the live tries of each major review, for the three learning sessions in final, and in a quick round whose thoughts are about the tutor job, when you want to talk to it.

In VS Code's Explorer, right-click the tutor folder and choose Open in Integrated Terminal, or open a new terminal and type cd tutor. Then start Claude Code there:

Run in a terminal in work/p3-tutor/tutor
claude

Then ask it for what you need as a learner, in your own words, for example:

Say to your tutor
Teach me a 10-minute lesson on how an agent decides when to stop.

The files it writes as you learn, such as MISSION.md, NOTES.md and lessons/, stay in tutor/ and are never part of a config. From c2-review on, your tutor waits for subagents, and in your own sessions it can do that only once fork mode, a Claude Code setting that is on by default, is off; the last section of tutor/.claude/agents/README.md shows the one setting that turns it off, in a personal file that never reaches the bench. Close the window with /exit when you are done, and change the tutor afterwards through the Builder, in a round, never from inside the tutor's window.

Note

Claude Code also reads the CLAUDE.md of every folder above the one it starts in, so a session in tutor/ sees the repo's root CLAUDE.md too, and, inside the course repo, the course's own; the root one tells a session in tutor/ to follow tutor/CLAUDE.md instead. If a learning session ever acts more like a course assistant than your tutor, that is why, and you can learn from a copy of tutor/ outside the course repo instead. The bench never has this problem, because it runs each scenario in a fresh folder outside your repo.

Name the tabs

With three or four terminals open it is easy to type into the wrong one. Right-click each terminal's tab and choose Rename, and name them "Guide", "Builder" and "Runs" (and "Tutor" when you open one). You can also drag a terminal's tab into the editor area, to keep the Guide beside the review file you are writing.

When you close a window

Close a Claude Code window with /exit, or by closing its terminal. Nothing is lost: the state of your project lives in your repo's files, your tutor, your reviews, your snapshots and your runs, and none of it lives in a chat. To carry on, start a new window with the same command in a terminal in work/p3-tutor. A new Guide sends its first question again and runs uv run p3 next, so it knows where you are without being told. A new Builder reads your round from the file when you say "Act on Round k of ...", so it needs no history either. Closing the Guide or the Builder does not stop a run in the plain terminal.

What the windows cost

Both Claude Code windows use your own Claude plan, the same as every other Claude Code session you run. The Guide's use is light: it reads a few files and gives short replies. The Builder's use is moderate: it reads and writes a skill or a subagent per round. What really costs is the bench: every scenario is a full Claude Code session, plus the scoring after it, and a full run of the baseline was about 1.85 million tokens in my pilot. p3 next, p3 check, p3 report and p3 snapshot cost nothing, because they call no model. Type /usage in either Claude Code window to see how much of your plan is left, and check it before a big run; The bench has the cost of each kind of run.
