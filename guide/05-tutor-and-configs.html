Part II · How it works

Your tutor, configs and snapshots

Your tutor is one folder, tutor/. This page says which of its files make up the tutor and which belong to the learner, how a snapshot freezes one version of it so that a run's numbers belong to one exact tutor, what skills and subagents are and where they go, and the few fixed rules that let one script score every student's tutor.

About 29 minutes to read.

On this page

  • tutor/.claude/settings.json: the allow list, the model, and where hooks go.
  • Who owns what in your repo.

What is in tutor/

Your tutor is the folder tutor/ in your repo, and it does four jobs: it teaches (a lesson), tutors (a reply in the chat), quizzes (a quiz with its answer key) and grades (verdicts and feedback on a learner's answers). The files in that folder are of two kinds. The config decides how the tutor behaves; you write it, usually by asking the Builder for one change at a time. The learner files are what one learner's sessions leave behind; the tutor writes them as it works.

The rule is short. A config is tutor/CLAUDE.md, tutor/PREFERENCES.md and everything under tutor/.claude/ except settings.local.json. Nothing else in tutor/ is ever part of a config, whatever its name. So anything the tutor needs in order to work, such as a permission or a hook, goes in tutor/.claude/settings.json, never in settings.local.json.

Why it is this way

Every bench scenario starts from the same learner: the topic's starting workspace, copied fresh each time. If the learner files from your live tries were part of a config, one config would start with a learner who had already seen three lessons and another with a learner who had seen none, and a comparison of the two would measure the learner, not the tutor.

On a fresh copy of the template, tutor/ holds CLAUDE.md, PREFERENCES.md, FORMATS.md and a .claude/ folder with one skill, teach (its SKILL.md and nine guides in references/), the README.md of agents/, and settings.json. That is the 14 files that uv run p3 check reports for configs/c0-baseline/, because FORMATS.md is not part of a config.

Watch out

Git does not ignore the learner files, so committing tutor/ commits them, and your repo is public, history included. Keep personal details out of MISSION.md, NOTES.md and everything else your sessions leave in tutor/.

Why the tutor has a folder of its own

You develop the tutor from the root of your repo, work/p3-tutor, and you learn with it by starting Claude Code inside tutor/. That way the tutor's CLAUDE.md is never the one you develop with, and the Builder's rules are never the tutor's. Three kinds of Claude Code session touch this repo, and each has its own instructions.

Claude Code also reads the CLAUDE.md of every folder above the one it starts in. So a session in tutor/ sees the root CLAUDE.md as well, and, inside the course repo, the course's own CLAUDE.md. The root CLAUDE.md expects this: its first section tells a session started inside tutor/ that it is the tutor, and that it should ignore the root file and follow tutor/CLAUDE.md. If one of your live sessions ever acts more like a course assistant than like your tutor, that is why; the README's "Start here" suggests learning from a copy of tutor/ outside the course repo if it keeps happening.

The bench avoids all of this, because it runs each scenario in a fresh folder outside your repo, where the tutor's CLAUDE.md is the only one in the folder. On Windows the temporary folder is inside your home folder, so a CLAUDE.md in your home folder itself would still reach every scenario; p3 bench warns when it finds one, and The bench says what to do.

One more consequence: skills and subagents in the root .claude/ also load in a session you start in tutor/, but never in a bench run. So everything about how your tutor behaves belongs inside tutor/, where both your live sessions and the bench see it. The root .claude/ holds the Guide's agent, and a session in tutor/ can see it, which is why tutor/.claude/settings.json ships with a line that stops your tutor from handing work to the Guide (below).

tutor/CLAUDE.md

This file tells Claude that it is the learner's tutor in this folder: read the learner's files before answering, use the teach skill for every request, follow FORMATS.md exactly, work only inside this folder, and never edit PREFERENCES.md, FORMATS.md or anything under .claude/. It is part of your config, so you may change it like any other part, through the Builder, and every snapshot keeps it. One line in it describes the baseline: "Use the teach skill (/teach) for every request: lessons, questions, quizzes and grading." The bench names the skill in every request it sends, so that line matters less there, but your own sessions in tutor/ read it, so when your skills change, check that this file still describes your tutor.

A config

A config is one complete version of the tutor's setup: the config files above, as they are at one moment. Every config has a name, and the bench runs two kinds.

live

tutor/ exactly as it is right now, uncommitted changes and all. uv run p3 bench --config live writes its runs to bench/runs/_live/, which git ignores. You use it in quick rounds, to see what a change did before you keep it.

a snapshot, such as c1-skills

a frozen copy of the config in configs/<name>/, made with uv run p3 snapshot <name>. uv run p3 bench --config c1-skills writes its runs to bench/runs/c1-skills/, and you commit them.

A name uses lowercase letters, digits and hyphens, starts with a letter or a digit, and is at most 41 characters long; live is taken. The ladder's names (below) are fixed, because p3 check and p3 report look for them by name.

A snapshot

p3 snapshot copies the config files from tutor/ into configs/<name>/, computes a hash of them, and records it in configs/<name>/SNAPSHOT.json. It reads nothing but tutor/, it calls no model, and it costs nothing. You take one at the end of each step, when you are happy with the tutor, and the bench then runs that snapshot by name.

Run in the Builder, or a plain terminal
uv run p3 snapshot c1-skills
configs/c1-skills/: <N> config files, sha256:<64 hexadecimal digits>
Run it with: p3 bench --config c1-skills

SNAPSHOT.json holds four things: the name, the hash, the time the snapshot was taken, and the list of files. The shipped baseline's looks like this, shortened:

{
  "name": "c0-baseline",
  "hash": "sha256:<64 hexadecimal digits>",
  "created_at": "<when it was taken, in UTC>",
  "files": [
    ".claude/agents/README.md",
    ".claude/settings.json",
    ".claude/skills/teach/SKILL.md",
    ".claude/skills/teach/references/GLOSSARY-FORMAT.md",
    ...
    "CLAUDE.md",
    "PREFERENCES.md"
  ]
}

The hash is a SHA-256 fingerprint of the config's files and their contents: change one character in one file and the hash changes. p3 computes it with line endings ignored, so a Windows checkout with its own line endings does not break it. Three things check it.

  • p3 bench recomputes the hash before it runs a snapshot, and refuses one whose files no longer match: "configs/c1-skills/ no longer matches its SNAPSHOT.json ... A snapshot is a fixed record; change tutor/ instead and take a new snapshot".
  • Every run records the hash of the config it ran in its run.json, as config_hash, so each run points at one exact tutor.
  • p3 check, on your machine and in CI on every push, confirms that every snapshot still matches its SNAPSHOT.json and that every run's hash matches its snapshot.

Why snapshots, and not git tags

I use snapshots rather than git tags because git does not push tags by default, and a run must always point at a config I can read. A snapshot is plain files in a folder you commit, so the tutor that made a run sits right beside the run, in every clone of your repo, including the one I grade.

A snapshot is frozen once it has runs

As soon as a snapshot has one run, quick or full, it is the record of what made that run, and it must never change again. p3 snapshot protects you from doing it by accident: it refuses to overwrite a name that exists, and a second snapshot under the same name prints this.

Run in the Builder, or a plain terminal
uv run p3 snapshot c1-skills
p3 snapshot: configs/c1-skills/ already exists; pick a new name, or add --force to replace it (runs made with the old snapshot will no longer match it)

--force deletes the old snapshot and takes a new one in its place. That is fine, and it is what --force is for, when the snapshot has no runs yet: you snapshot c1-skills, notice a typo in a skill before you start its full run, fix it in tutor/, and snapshot again with --force. Once the snapshot has a run, --force breaks the record, and p3 check fails, in CI too, with a line like this:

FAIL  bench/runs/c1-skills/: 1 run out of 1 do not match configs/c1-skills/
        bench/runs/c1-skills/<run-id> was made with another version of c1-skills than configs/c1-skills/ holds; restore that snapshot from git, or delete this run

If that happens, restore the old snapshot from git, which works if you committed it with its run (the Builder can do it: ask it to restore configs/c1-skills/ exactly as your last commit has it), and put your change somewhere else. On the ladder, a change you want after a step's full run usually belongs to the next step. After final, snapshot the changed tutor under a new name, because final and its runs stay as they are. Do not delete a run to make the check pass: a run is evidence, and the README's ground rules ask you never to delete one because you did not like its numbers.

Watch out

Never snapshot over c0-baseline. It ships with the template, it is the baseline every step is measured against, and its three full runs point at it. tutor/ stops matching it the moment you change anything, which is expected.

Never edit a file in configs/ by hand. Change tutor/ and take a snapshot.

p3 snapshot refuses a file that is not UTF-8, and names it, because a file saved in a Windows "ANSI" encoding would stop matching its own hash in a fresh checkout. Save the file as UTF-8 (VS Code shows the encoding in its status bar) and snapshot again.

Commit configs/ together with the runs it made and your reviews, as each step's last action; the step pages (Step 1, for example) say when.

The ladder of configs

Everyone builds the same kinds of architecture, in the same order, so that the class's results can be compared; what each piece does and how you build it is yours. Each rung of the ladder is a snapshot with a fixed name.

The architecture ladder, from the README. "Full runs" counts the full bench runs each config needs on the shared topic.
ConfigWhat it addsFull runsPage
c0-baselinenothing, as shipped: one teach skill does all four jobs in one shot3The baseline
c1-skillsthe four skills teach, tutor, quiz and grade, plus any others you like; still one agent1Step 1
c2-reviewreview loops on teach, quiz and grade, with the reviewers as subagents1Step 2
c3-splitthe teach job split across subagents (a planner, a designer, a writer, a visual designer, a references finder, and so on)1Step 3

Each step is measured against the one before it, in quality (your major review and the objective checks) and in cost (tokens, turns, subagents and time). An ablation names what it removes, for example final-minus-quiz-review or final-minus-planner. Only c0-baseline and final get three runs, because those two carry the project's main comparison and a split pipeline with reviewers is expensive to repeat.

c0-baseline keeps the neutral PREFERENCES.md the template ships, and c1-skills is the first config with yours. So step 1, and the comparison of c0-baseline with final, measure your skills and your preferences together, and EVAL.md asks you to say which differences you think came from which.

The output contract

How your tutor works is yours, with one exception: the files it writes for the bench to read must match bench/FORMATS.md exactly, down to the file names, the numbering and the JSON keys. That file is the contract, with a complete example of every JSON file, and tutor/FORMATS.md is an identical copy for your tutor to follow in live sessions. Read it once before step 1, because every skill you write has to produce these files.

The outputs the bench reads, each in a sentence. bench/FORMATS.md has the full rules and examples.
OutputFileIn a sentence
Lessonlessons/NNNN-<slug>.htmla complete, self-contained HTML page with two meta tags, p3-minutes and p3-objective, its CSS and scripts inline or under assets/, no remote scripts or stylesheets, and ordinary links to outside references welcome.
Quizquizzes/NNNN.jsonthe items, each with an id, a type (mcq, numeric or short), the objective it serves, the stem, and options for mcq, and never an answer.
Keykeys/NNNN.jsonfor each item the answer, other accepted forms, a rationale, and the misconception behind each wrong option, under the quiz's own number.
Gradesgrades/NNNN-sN.jsonfor each item a verdict (correct, partial or wrong), the misconception id if one applies, and feedback that is never empty, plus a summary to the learner.
Learning recordlearning-records/NNNN-<slug>.mdone thing the learner has shown they understand, in the teach skill's format.
Tutor replythe session's last messagefor a message from the learner, the reply is the final message of the session, so it comes after every file the tutor writes.

A few rules from the contract catch people out, so here they are in one place.

  • Numbering. A new file takes the next four-digit number after the highest one in its folder, or 0001 in an empty folder; a key takes its quiz's number, and a grades file is named after the quiz and the submission. On the shared topic the starting workspace already holds quiz 0001 with its key and no lesson, so the bench's new quiz is quizzes/0002.json with keys/0002.json, the lesson is lessons/0001-<slug>.html, and the grades for submission s1 go in grades/0001-s1.json.
  • Never change an existing quiz, key or submission. A quiz that needs fixing becomes a new quiz.
  • One new lesson per teach request. The teach check expects exactly one new lesson in lessons/, so a draft saved there turns a good run into a recorded failure. Keep drafts in a folder of your own, such as drafts/.
  • Ids are shared. Objective ids (O1, O2, ...) and misconception ids (M1, ...) come from the request and the learner's files, and the tutor never invents a new id for something that already has one.
Why it is this way

The contract is what lets one script score every student's tutor. Forty tutors built forty different ways can all be checked by the same scorer, and compared on the same numbers, only because they all write the same files in the same shape. The cost is a little freedom over file names, and nothing over how the tutor gets there.

Never change bench/FORMATS.md or tutor/FORMATS.md. The first is hash-checked, and p3 check fails when the second differs from it. If you think the contract has a bug, tell me, and I will fix it for everyone.

Skills and subagents

Your tutor grows from one skill to several skills, then to skills that start subagents. You met both in lectures 15 to 19; this section is what you need of them for P3.

A skill

A skill is a folder, tutor/.claude/skills/<name>/, with a SKILL.md in it. The file opens with frontmatter between two --- lines, and the Markdown after it is the skill's instructions. The shipped teach skill's frontmatter shows the fields that matter here:

---
name: teach
description: Teach, tutor, quiz and grade the learner in this workspace - ...; use it for every request from the learner here.
argument-hint: "What would you like to learn, or what should I do?"
---

description says what the skill does and when to use it, and argument-hint is the hint shown after its name when you type /teach. A skill runs inside the conversation that invokes it. When the bench sends /quiz with a request, Claude Code loads the quiz skill's instructions into that session, which already holds the request and can read the learner's files. A skill folder may hold more files beside SKILL.md, as teach does with its guides in references/, which its instructions reach as ${CLAUDE_SKILL_DIR}/references/.

A subagent

A subagent is one Markdown file, tutor/.claude/agents/<name>.md. It is a separate Claude with its own system prompt (the file's Markdown body), its own tools and a fresh context window. The main conversation starts one with the Agent tool and a task message it writes, and gets back one report. A subagent does not see the main conversation's history, the skills it already invoked or the files it already read, so the task message has to carry what the subagent needs, or say which files to read.

This is the example from tutor/.claude/agents/README.md:

---
name: quiz-reviewer
description: Reviews a draft quiz and its key for one objective and returns numbered findings. Use after drafting a quiz, before finishing.
tools: Read, Glob, Grep
model: sonnet
maxTurns: 20
---

You review one quiz and its key against the objective it serves.
(The rest of the system prompt: what to check, how to report, when to stop.)
  • The first --- must be the file's first line, and only name and description are required.
  • Field names are case-sensitive camelCase, and Claude Code silently ignores a field it does not recognize, so a misspelled field fails without an error.
  • A file without such frontmatter is documentation. Claude Code does not load it, and p3 check notes it as documentation and does not count it as a subagent; a checklist file a reviewer reads is fine there.
  • Without a tools list, a subagent inherits every tool, the Agent tool included, so it can start subagents of its own; give a reviewer an explicit list.
  • model lets a subagent run on a model of its own, such as haiku; left out, it runs on the main conversation's model.

tutor/.claude/agents/README.md has every field, what I saw the bench do with them, and the link to the Claude Code documentation on subagents (a reference page; read the part on frontmatter fields when you write your first one).

Which one to use

The component inventory asks you this for every component you build: why it is a skill or a subagent rather than the other. These are the questions I would ask.

When a skill fits, and when a subagent fits.
A skill fits whenA subagent fits when
the work needs what the conversation already has: the request, the learner's files it read, the draft it just wrotethe work is better done without the writer's reasoning to lean on, such as a reviewer that reads a draft the way the learner will
one set of instructions carries the job from start to end, such as how to write a quiz and its keypart of the job needs instructions and tools of its own, such as a planner, a writer and a references finder in the c3-split pipeline

The cost is real. Every claude -p call carries a fixed load before it does any work, 24,000 to 49,000 input tokens in my checks, almost all of them cached reads of Claude Code's own instructions and tools. Every subagent pays a share of that again, plus whatever it reads, which is why fan-out is what drains a weekly limit (What runs cost has the numbers).

When each arrives on the ladder

  • c1-skills: skills only. The four skills, and any others you want, but no subagent. p3 check fails, even without --final, when configs/c1-skills/ holds a subagent or a round in reviews/c1-skills.md is of Kind new subagent, because step 1 is still one agent and its numbers have to show what skills alone do.
  • c2-review: reviewer subagents on teach, quiz and grade, one per quick round.
  • c3-split: the teach pipeline, its subagents one per quick round.
  • final: usually a grader subagent, because once the guard keeps keys/ from the main conversation, grading has to happen in a subagent the guard allows (The guard).
Note

In a bench run, a subagent the main conversation starts runs in the background by default, and Claude waits for it when it judges it should or when it is told to, so a skill that needs a reviewer's report should say to wait for the report before going on. In your own sessions in tutor/, Claude can wait for a subagent only once fork mode, a Claude Code setting that is on by default, is off; the last section of tutor/.claude/agents/README.md says how, in tutor/.claude/settings.local.json, which never reaches the bench.

How the bench starts each job

The bench starts every job with a slash command: /teach, /tutor, /quiz or /grade, when the config has that skill, and /teach when it does not. That is why these four skill names are fixed, and it is how c0-baseline does all four jobs with its one skill.

Which command starts each job.
JobIts scenariosStarts withWhen the config has no such skill
teachteach/teachnone: every config needs its teach skill
tutortutor-p01 to tutor-p06/tutor/teach
quizquiz/quiz/teach
gradegrade-s1, grade-s2/grade/teach

The bench looks for exactly .claude/skills/<job>/SKILL.md in the config. A skill in a folder called quizzes/ or grader/ is not found, and that job quietly goes to /teach. Every run.json records which command each job started with, under entries, so look there after the first run of a new skill.

The text after the command is the request. Its exact wording, for every scenario, is in bench/scenarios.json; these are its four templates, where {entry} is the command and the bench fills in the rest from the topic:

{entry} Teach objective {teach_objective_id}: "{teach_objective_text}" as a {minutes}-minute lesson for the learner described in MISSION.md and NOTES.md. Write the lesson as FORMATS.md describes.

{entry} Write a six-question quiz on objective {quiz_objective_id}: "{quiz_objective_text}" for this learner. Write the quiz and its key as FORMATS.md describes.

{entry} Grade the learner's submission submissions/{submission}.json for quiz {graded_quiz}, with feedback for each answer. Write the grades as FORMATS.md describes.

{entry} {probe_message}

So with a grade skill, the scenario grade-s1 on the shared topic sends this, as one message:

/grade Grade the learner's submission submissions/s1.json for quiz 0001, with feedback for each answer. Write the grades as FORMATS.md describes.

Everything after the skill's name reaches the skill as its arguments. In the shipped teach skill, $ARGUMENTS under its heading "The request" is where that text lands, which is how one skill can tell a request for a lesson from a request to grade. Your own skills can use it the same way.

Two facts about the bench shape how you write these skills.

  • A tutor probe is one message, and the final message is scored. The request is the probe's message alone, after /tutor, and nothing comes after it. The reply that gets scored is the session's final message, so your tutor skill must answer in the chat, not in a file, and write any file it wants to (a note in NOTES.md, a learning record) before its reply, never after it.
  • No one is there to answer a question. Each request runs headless and ends when the session ends, so a skill that stops to ask the learner something has ended its job. The shipped teach skill says what to do: a request that says what to do gets done now, and any question for the learner goes at the end of the final message.

tutor/.claude/settings.json

This is the tutor's settings file, and it is part of your config. The template ships it like this:

{
  "permissions": {
    "allow": ["WebSearch", "WebFetch"],
    "deny": ["Agent(p3-guide)"]
  }
}
permissions.allow: the only tools a bench run may use without asking

The bench passes this list to Claude Code as --allowedTools, and always adds Glob and Grep to it, because on macOS, Linux and WSL Claude Code leaves those two out unless they are named, and every config should be able to search its workspace the same way on every system. A fresh folder ignores a project's own allow rules, and in a bench run there is no one to approve anything, so any other tool call that would need a permission prompt is denied, and run.json lists it, scenario by scenario, under permission_denials. The bench runs with --permission-mode acceptEdits, so writing and editing files inside the scenario folder needs no rule. The Agent tool, which starts a subagent, needs no rule either, and the allow list covers your subagents' tool calls too.

In my pilot, the baseline's teach session tried to count its lesson's words with a shell command, which the baseline does not allow, so it had no way to check its own length. If your tutor needs a command, allow the narrow one it needs, in the same form as the rules in the root .claude/settings.json (such as "Bash(git status*)"), or tell the skill how to finish without it, and try it with --config live before you snapshot.

permissions.deny: keep this line

Claude Code finds project agents by walking up to the root of the repository, so a session you start in tutor/ can see the Guide's agent at the root. Agent(p3-guide) in the deny list keeps your tutor from ever handing work to the Guide. Leave it in, and keep it when you add rules of your own.

model: the tutor's model

The key "model" sets the model the tutor's main conversation runs on; without it, which is how the template ships, the bench uses sonnet. A subagent can name its own model in its frontmatter, which is one road to the cheaper-tutor stretch (A cheaper tutor).

hooks: here, never in a subagent's frontmatter

The bench runs every scenario with claude -p in a fresh folder that was never trusted. A hook in a subagent's frontmatter runs only once a folder's trust question has been answered yes, so in the bench it silently does nothing, while a hook in this file does fire there. Put every hook here, and keep any script a hook runs under tutor/.claude/ too (for example in tutor/.claude/hooks/), so it is part of the config and is copied into every scenario folder. You add your first hook in final; The guard explains it.

Watch out

A tool you approve in your own session is not approved in the bench. When you approve a tool at a permission prompt in a session in tutor/, Claude Code writes the rule to tutor/.claude/settings.local.json, which is never part of a config and never reaches the bench. So a live session that works is no proof that a bench run will; a --config live run is.

Two different guards. The root .claude/ holds the Guide's guard, which keeps the Guide read-only and belongs to the course. Your tutor's guard, which you build in final, lives in tutor/.claude/settings.json and is yours.

Who owns what

The rule behind the layout is simple: I own everything that runs the measurement, and you own everything that decides how the tutor behaves.

If something goes wrong, and where to go next

A snapshot that will not take, a run that will not start, a p3 check line you do not understand: When it breaks has the symptoms and the fixes, and every p3 message names the file to look at. Next, The bench follows one of these configs through a run: what each scenario does, what every number means, and what it costs.
