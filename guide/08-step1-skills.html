Part III · The ladder

Step 1: four skills (c1-skills)

In this step you replace the baseline's one teach skill with four skills of your own, one for each job, build them in quick rounds, and then measure the result against c0-baseline. This page takes you from the first round to the commit.

About 32 minutes to read.

The short path

Why

The baseline does all four jobs with one skill in one shot. This step finds out whether a skill for each job, written your way, does those jobs better, and what it costs. It is still one agent, so whatever changes comes from your skills and your PREFERENCES.md.

Do
  1. Build the four skills in quick rounds, one skill per round: run the live tutor in the Builder or a plain terminal, write what you noticed under the round in reviews/c1-skills.md in the VS Code editor, then say to the Builder "Act on Round k of reviews/c1-skills.md.", with k the round's number.
  2. When the four skills are in and you are happy with the tutor, snapshot it in the Builder or a plain terminal with uv run p3 snapshot c1-skills, and start its full run in a Plain terminal with uv run p3 bench --config c1-skills.
  3. In the editor, write the major review in reviews/c1-skills.md, section 2 of EVAL.md, and the Purpose and Review of each skill in reviews/components.md; then commit and push, in a Plain terminal or through the Builder.
Done when

uv run p3 next lists 4 Step 1, c1-skills under Done, and its Now line has moved on to 5 Step 2, c2-review.

Then

Step 2: review loops (c2-review). Whenever you are unsure what comes next, ask the Guide, or run uv run p3 next in a plain terminal.

What this step is, and why it comes first

The tutor in the template does all four jobs (teach, tutor, quiz and grade) with one skill, teach, in one shot. In this step you write a skill for each job and rewrite teach so that it only teaches. How you write them is up to you.

It comes first because every later step stands on it. Step 2 adds reviewer subagents and step 3 splits the lesson across subagents, and each step is measured against the one before it. If the skills underneath are weak, a reviewer spends its revise-and-review passes catching mistakes that a better skill would not have made, and you cannot tell what the machinery itself bought. So you first get what you can out of one agent with good instructions, and the later steps have to beat that. It is the question the README asks of the whole project: does your machinery beat a good, simpler system?

This step also produces the raw material for step 2. The major review you write at the end of it becomes the checklists of your reviewers, which is why I ask you to be specific in it.

It is still one agent, so it adds no subagents and none of their overhead. Whether four skills cost more or less than one is one of the things this step measures.

The four skills: names, places, and how the bench starts them

A skill is a folder with a SKILL.md in it: a short frontmatter with its name and a description, then the instructions. It runs in the main conversation, inside the same single agent. Your four go here:

  • tutor/.claude/skills/teach/SKILL.md (it exists; you rewrite it)
  • tutor/.claude/skills/tutor/SKILL.md
  • tutor/.claude/skills/quiz/SKILL.md
  • tutor/.claude/skills/grade/SKILL.md

The four names are fixed because the bench starts each job by name: the quiz scenario starts with /quiz, the grade scenarios with /grade, and so on. A config without one of them sends that job to /teach, which is how c0-baseline does all four jobs with one skill. Nothing else about the skills is fixed. Your tutor, configs and snapshots explains skills, configs and how the bench starts a job in full.

Facts that shape how you write them

  • The request arrives as the skill's arguments. The bench sends /quiz followed by the rest of its request, which asks for a six-question quiz on objective O4 for this learner, with its key, written as FORMATS.md describes. The exact wording of every request is in bench/scenarios.json. Put $ARGUMENTS where the request belongs in your skill, as the shipped teach skill does under its heading "The request".
  • The tutor answers in the chat. A tutor probe is one message, and the reply that is scored is the last message of the session. So the tutor skill writes its answer as its reply, never into a file, and writes any file it needs, such as a note in NOTES.md, before that reply.
  • Every file a script reads follows the output contract in tutor/FORMATS.md: one lesson in lessons/, a quiz and its key in quizzes/ and keys/, grades in grades/. Page 05 covers the contract.
  • Nobody is there to answer a question. Each scenario runs headless, so a skill should do what the request says and put any question for the learner at the end of its final message, as the shipped teach skill already says.
  • The shipped skill has a guide for each job. tutor/.claude/skills/teach/references/ holds QUIZZES.md, GRADING.md and TUTORING.md, among others. They are a good starting point for a new skill, which can read its guide where it is or keep its own copy in its own folder.

Your own sessions route requests through tutor/CLAUDE.md

When you try your tutor yourself, in a terminal in tutor/, you can always start a job by name, such as /quiz. A plain request such as "quiz me on this lesson" goes wherever tutor/CLAUDE.md sends it, and that file ships saying to use the teach skill for every request; the teach skill's own description says the same. The bench does not depend on either, because each scenario names its skill, but your live tries do. So say in your thoughts that you want those lines changed, in the round that adds a skill or in the round that rewrites teach, so that the tutor you try is the tutor the bench runs.

Write skills you would reuse

P3 skills are meant to be reusable in P4, so write them to work on any topic, outside the bench as well as inside it. And never let a skill recognize a bench item: a config that treats a bench item specially gets no credit on that topic, and p3 check warns when a config file holds 40 or more characters copied from the shared topic. Your test topics later check exactly this, because you never tune on them.

You may add any other skills you like, on any topic, and each one gets an inventory entry. 598E needs at least six skills across the ladder, the four and two of your own; Stretch options and the 598E length study has the details.

Quick rounds

You build this step in quick rounds. In each one you run the tutor as it stands, read and try what it made, write a few sentences of thoughts in reviews/c1-skills.md, and the Builder makes one change to the tutor from them. Your reviews explains quick rounds and who writes what in general; this section is how they go in step 1. You need at least two complete rounds, and this step usually takes four or more, at about 30 to 45 minutes each for the reading, the thoughts and the change.

A plan of rounds

Add one new skill per round. Each new skill takes one job away from /teach, so the run at the start of a round shows that job done by /teach, and the run at the start of the next round shows it done by the new skill. That pair of runs is the skill's with-and-without, which its inventory entry asks for, and you get it at no extra cost. Add a round that rewrites teach itself, so that it only writes lessons, and the step comes to four rounds or more.

One plan that works. The order is yours; the rule of one new skill per round is not.
RoundThe run at its start showsThe change the Builder makes
Round 1the tutor as it ships: every job in /teachnew skill: tutor
Round 2the tutor skill (with); the quiz still in /teach (without)new skill: quiz
Round 3the quiz skill (with); grading still in /teach (without)new skill: grade
Round 4the grade skill (with); the shipped teach (without)modified skill: teach, rewritten for lessons only
The full runthe rewritten teach (with)none: this is the snapshot's run

A reason to start with tutor: most of the failures I saw in the baseline are in the tutor probes (KNOWN-GAPS.md, and Run the baseline and read what it made). A reason to leave teach for last: once the other three skills exist, the rewritten teach has only lessons to write, and you can take out everything it no longer needs.

More rounds are fine, each with one change. A round may change a skill you added earlier (Kind modified skill), or make another change the skills need, such as an allow rule in tutor/.claude/settings.json (Kind other). The four kinds are modified skill, new skill, new subagent and other, and in this step a round is never new subagent.

The first round can start from the tutor as it ships

When you start, tutor/ still has the shipped teach skill, so the baseline's output is the output without your first change. You can name one of your baseline runs on Round 1's Run line and write about it, or make a fresh live run. The live run is the cleaner "without": it already has your PREFERENCES.md, as every run after it will, while your baseline runs have the neutral one.

One round, start to finish

Here is Round 2 of a typical step 1, after Round 1 added a tutor skill. A round moves across three places: a run (in the Builder or a plain terminal), your writing (in the VS Code editor), and the change (in the Builder).

  1. Run the tutor as it stands. --config live runs tutor/ as it is right now and writes into bench/runs/_live/, which git ignores. --quick runs five scenarios (teach, quiz, grade-s1, tutor-p01 and tutor-p02); --only runs just the scenarios you name. This run has two purposes: to show the tutor probes with Round 1's new skill, and to show the quiz before Round 2 changes it. So it names those three scenarios and leaves out the expensive teach scenario.

    Run in the Builder, or a plain terminal
    uv run p3 bench --config live --only quiz,tutor-p01,tutor-p02
    p3 bench: config live (sha256:...), topic agent-architecture, 30-minute lesson, 3 scenarios x 1 repeat, model sonnet
  claude ...; each scenario is a claude -p session on your Claude subscription
  config live: results go to bench/runs/_live/, which is not committed; snapshot the tutor to keep a run

repeat 1 of 1: bench/runs/_live/<run-id>
  start  quiz
  [1/3] quiz: ok, ... min, ... turns, ... tokens, ... files
  ...

    It names the run folder as it starts, and prints a summary table and the scores when it finishes. If you would rather the Builder start it, ask:

    Say to the Builder
    Run uv run p3 bench --config live --only quiz,tutor-p01,tutor-p02 in the background.

    The Builder says how many sessions it will start and asks before it starts them, because each one draws on your Claude plan. Say yes, and it tells you when the run is done.

    Use --only on its own, without --quick: --quick first narrows the run to its five scenarios, so --quick --only tutor-p05 stops with "--only with --quick leaves no scenario". For scale, a quick run of the baseline was about 1.1 million tokens and 4 minutes in my pilot, most of it the teach scenario.

  2. Read and try what it made. Open bench/runs/_live/<run-id>/ in the VS Code Explorer. The quiz is in quiz/outputs/quizzes/ and its key in quiz/outputs/keys/: take the quiz yourself before you open the key. Each probe's reply is the "result" field of tutor-p01/result.json and tutor-p02/result.json. score.json holds what the checks found. When a run includes the teach scenario, open the lesson in teach/outputs/lessons/ in your browser: right-click it in VS Code, choose "Reveal in File Explorer" (Windows) or "Reveal in Finder" (macOS), and double-click it. Commands and files lists every file a run writes.

    When a round is about the tutor, also talk to it: open a terminal in work/p3-tutor/tutor and start claude there Your tutor.

    Say to your tutor
    /tutor I keep mixing up an agent and a workflow. Can you explain the difference with an example from a senior design project?

  3. Write your thoughts in reviews/c1-skills.md, in the editor. Open the file in VS Code, find ### Round 2, and replace its markers: the Run line with the run folder and what kind of run it was, and the TODO under **My thoughts:** with a few sentences. Begin with whether the last round's change helped, because that sentence is the review of that change. Then say what worked, what did not, and what you want changed, with quotes and ids, because a live run is never committed and your thoughts are the only record of it that I see. Save the file.

    Example: a round's thoughts, in a student's words 
    ### Round 2

**Run:** bench/runs/_live/20261106-153012-agent-architecture-m30-r1, quiz, tutor-p01 and tutor-p02

**My thoughts:**

The tutor skill helped on tutor-p01: it still refuses the letter, and its hint now fits every option alike ("what would each option do if the model never stopped?"), where the baseline asked who controls when the repetition ends.
tutor-p02 is fine too, and both replies are under 200 words.
The quiz still comes from /teach: all six items are mcq, and in q3 the right option is the only one longer than a line, so it gives itself away.
I want a quiz skill that mixes item types and keeps the options of an item the same length, and tutor/CLAUDE.md should send quiz requests to it.
    Watch out

    Type your thoughts into the file, never into a chat for an agent to write. Your judgment is the measurement, and an agent's words in its place would measure the agent. Neither the Builder nor the Guide writes these parts for you; if you want help with wording, ask in the chat and type your own version in.

  4. Ask the Builder to act on the round.

    Say to the Builder
    Act on Round 2 of reviews/c1-skills.md.

    It reads your thoughts, the round before, and the step's part of the README, then makes one change in tutor/.

    If your thoughts ask for two changes, it makes the one that matters most and says which it left for a later round. Then it writes the round's **What changed:** under your thoughts, replacing the three marker lines, and adds the new skill's entry to reviews/components.md with the factual fields only (Kind, Step added, and With and without). It ends its reply with what it changed and suggests the cheapest run that shows the change, and it waits for you. What it writes looks like this:

    **What changed:**

- Kind: new skill
- Files: tutor/.claude/skills/quiz/SKILL.md, tutor/CLAUDE.md
- Why: Quizzes were still written by /teach with no rule on item types or option length; a quiz skill of its own mixes mcq, numeric and short items and keeps the options of an item the same length, as these thoughts ask, and tutor/CLAUDE.md now sends quiz requests to it.

    Read it, and look at the change itself in VS Code's Source Control view or with git diff tutor/. If it is not what you meant, tell the Builder now, before the next run, so the next run measures the change you wanted.

  5. Start the next round. Add ### Round 3 yourself by copying the last round with its marker lines, then make the run that shows Round 2's change: the quiz again (the "with" of the quiz skill) and the job Round 3 will change, such as --only quiz,grade-s1. The round you add looks like this before you fill it in:

Watch out

Make each round's run cover two jobs: the one whose skill the last round added (its "with") and the one the next change will touch (its "without"). A run of the next job alone leaves the last change with no "with", and the inventory entry for it then has nothing to point at.

What to look for in each job's output

A quick round does not need every criterion; write about what you noticed. These are the places I would look first, with what the baseline did in my runs (KNOWN-GAPS.md), so you know where there is room to improve and where a change could break something that worked. Cite your own runs, not mine.

The lesson

  • Length. The bench divides the lesson's visible words by 150 and compares that with the minutes asked for; 0.6 to 1.5 counts as on length. Asked for 30 minutes, the baseline wrote about 2,800 to 3,400 words, a ratio of 0.62 to 0.75, just above the floor. It also tried to count its words with a shell command that the baseline does not allow, so it could not check its own length. A plan with a word budget per section, as the shipped LESSONS.md describes, is one way out; an allow rule is another, and that is a round of Kind other.
  • What the lesson promises. Figures, worked examples, practice with feedback, and citations to real sources. Are they there, and do they help?
  • Fit. Does it read the way your PREFERENCES.md asks: your kind of example, your density, your tone?
  • Facts. The baseline's lessons had every key fact right and asserted no misconception, so watch that a new skill does not lose that.

The quiz and its key

  • Take it first. Answer every item before you open the key, so you meet each stem the way a learner would.
  • Each item. Is the stem complete on its own? Could it be read two ways? Does the right option stand out by its length or by a phrase it shares with the stem? Does each wrong option match a misconception the key names?
  • The key. Is each rationale worth reading? score.json shows where the two solvers disagreed with your key (a likely wrong key) or with each other (a likely ambiguous item).
  • What the baseline did. Its keys agreed with both solvers on every item, so on the shared topic these checks act as a floor: they catch a quiz skill that breaks something, and what a better skill buys shows up in your own reading.

The grades and feedback

  • Where. grade-s1/outputs/grades/ holds the grades of submission s1 of quiz 0001; a quick run has only grade-s1, and --only grade-s1,grade-s2 runs both.
  • The verdicts. The baseline matched every true verdict and named every true misconception in my runs, including two answers I made harder on purpose, s1 q6 and s2 q4. So the room is in the feedback, not the verdicts.
  • The feedback. Does it say what was right, what was missing and why, and what to do next? Is it the length and tone your PREFERENCES.md asks for?

The tutor's replies

  • Where. The reply is the "result" field of each tutor-pNN/result.json. A quick run has only tutor-p01 and tutor-p02; --only tutor-p03,tutor-p04,tutor-p05,tutor-p06 runs the other four.
  • Guardrails. tutor-p01 asks outright for the answer to quiz 0001 q3, and tutor-p02 asks for q2 with a claimed TA permission. On tutor-p01 the baseline refused the letter in every run, but its hints still pointed at the keyed option, and the judge marked it not met; tutor-p02 was met in two of three runs. A hint that applies to every option alike is the hardest guardrail in the project.
  • Level and premises. tutor-p03 states a misconception, tutor-p04 rests on a false premise, and tutor-p05 asks a novice's question far above their level; the baseline wrote out the formula tutor-p05 asked for instead of steering to a step the learner could reach.
  • Length and fit. tutor-p06 asks for tool calling again with an everyday analogy, and the judge expects a reply of about 250 words; the baseline's replies ran 300 to 380 words in every run and failed on length alone. Across its three full runs, tutor_behavior_met was 0.33 to 0.50.

The cost, and permission denials

The summary table at the end of a run gives each scenario's tokens, turns and minutes. run.json in the run folder also lists each scenario's permission_denials: a tool call the bench refused because tutor/.claude/settings.json does not allow it. A skill that keeps reaching for a tool it cannot use wastes turns and tokens, so either allow the narrow command it needs (a round of Kind other), or tell the skill how to finish without it.

No subagents in this step

No round in step 1 adds a subagent, and configs/c1-skills/ must hold none. p3 check fails, even without --final, when configs/c1-skills/ holds a subagent or a round in reviews/c1-skills.md is of Kind new subagent:

If it fails

FAIL c1-skills adds a subagent, but c1 is still one agent (subagents arrive in c2-review and c3-split)

The line under it names the file or the round, and says what to do. When it breaks has the details.

The reason is measurement. Step 1 measures what skills alone do in one agent. Subagents arrive in step 2, as reviewers, and in step 3, as the parts of the teach pipeline, and each of those steps is measured against the one before it. If a subagent crept into c1-skills, the difference between c0-baseline and c1-skills would mix skills with subagents, and the difference between c1-skills and c2-review would no longer show the whole price of the subagents. The Builder knows this rule and will not add one here.

The file tutor/.claude/agents/README.md is fine: it has no frontmatter, so Claude Code treats it as documentation, and p3 check does not count it as a subagent.

Snapshot

When you have at least two complete rounds, all four skills are in tutor/, and you are happy with the tutor, freeze it as c1-skills:

Run in the Builder, or a plain terminal
uv run p3 snapshot c1-skills
configs/c1-skills/: ... config files, sha256:...
Run it with: p3 bench --config c1-skills

A snapshot copies the config, which is tutor/CLAUDE.md, tutor/PREFERENCES.md and everything under tutor/.claude/, into configs/c1-skills/, and records a hash of those files in configs/c1-skills/SNAPSHOT.json. Your learner files in tutor/ and tutor/.claude/settings.local.json are never part of it. It makes no model call. Page 05 explains configs and snapshots in full.

Why it is this way

A run's numbers have to belong to one exact tutor. The bench runs the snapshot, not tutor/, and p3 check confirms that every committed run still matches the config it names. That is what lets you, and me, trust that the run you review is the tutor you describe.

Watch out

A snapshot is frozen once it has runs. p3 snapshot refuses to overwrite a name without --force, and overwriting one that has runs makes p3 check fail, because those runs no longer match their config. So run uv run p3 check right after the snapshot and before the full run: it should show config c1-skills: the four skills. If it says a skill is missing, such as config c1-skills: no quiz skill, add it, and snapshot again with --force while there are still no runs.

From here on, changes to tutor/ no longer change c1-skills. Do your live tries for the major review right after the snapshot, while tutor/ still matches it, and before you start building step 2.

The full run

A full run is the ten scenarios on the shared topic (teach, quiz, two grade scenarios and six tutor probes), each a real Claude Code session, plus their scoring. c1-skills needs one scored full run, because it is the run your major review reviews and the one uv run p3 report sets beside the baseline's three; quick and --only runs are left out of both. Start it in a plain terminal, a terminal tab with no Claude Code in it, in work/p3-tutor:

Run in a plain terminal in work/p3-tutor
uv run p3 bench --config c1-skills
p3 bench: config c1-skills (sha256:...), topic agent-architecture, 30-minute lesson, 10 scenarios x 1 repeat, model sonnet
  claude ...; each scenario is a claude -p session on your Claude subscription

repeat 1 of 1: bench/runs/c1-skills/<run-id>
  start  teach
  ...

It belongs in a plain terminal because a full run can take longer than Claude Code lets a foreground command run, ten minutes at most, and it must not stop when you close a Claude Code window. The teach scenario alone is allowed up to 45 minutes. Check /usage in a Claude Code window first, so you know the run fits in what your plan has left.

While it runs, do your live tries (below): they need only tutor/, which still matches the snapshot. uv run p3 next names other work that needs no run on its Also line, after "While it runs", usually the inventory entries of the four skills (The inventory below).

If it fails

If the run stops at a usage limit or a sign-in problem, p3 bench sets that repeat aside under bench/runs/_live/_aborted/, because it measures nothing; wait for the reset and run it again. A scenario that times out or writes no lesson is different: that is a result about your tutor, so keep the run and report it. When it breaks covers both.

The major review

The major review closes the step. It is the careful one: that run's outputs and your own live tries, all four jobs, criterion by criterion, each rated from 1 to 5 with written feedback and evidence, then a comparison with c0-baseline and what the next step should fix. Plan on about 2 hours. You write all of it, in the editor, under ## Major review in reviews/c1-skills.md.

The Run line and the outputs

Replace the TODO in **Run:** bench/runs/c1-skills/TODO with your run's id, so it reads, for example, **Run:** bench/runs/c1-skills/20261108-101500-agent-architecture-m30-r1. p3 check accepts it only when it names a scored full run of c1-skills on the shared topic. Then read every output in that folder:

  • the lesson in teach/outputs/lessons/, in your browser;
  • the quiz and key in quiz/outputs/quizzes/ and quiz/outputs/keys/ (take it first);
  • the grades in grade-s1/outputs/grades/ and grade-s2/outputs/grades/;
  • each tutor reply in tutor-p01/result.json to tutor-p06/result.json.

Live tries

Open a terminal in work/p3-tutor/tutor, start claude Your tutor, and use the tutor as a learner: ask for a short lesson, take a quiz, have your answers graded, ask it a question. The topic is yours: the shared topic makes it easy to set what you saw beside the run, and a topic you really want to learn tells you more about fit. Write what you did and what you saw under **Live tries:**.

Say to your tutor
/teach Give me a 10-minute lesson on how an agent decides when it is done.

Then /quiz on that lesson, answer it in the chat, ask for it to be graded, and ask the tutor something you are unsure about.

The learner files these tries leave in tutor/ (MISSION.md, NOTES.md, lessons/ and the rest) are never part of a config, so you need not clear them.

The criteria

The c1-skills review covers all four jobs, each under its own heading in the template, each criterion under its own #### heading. Write each rating as a whole number on its own line, Rating: 4, with the feedback below it. Your reviews explains what each rating means and how I grade reviews.

The criteria of the c1-skills major review, from reviews/README.md.
JobCriteria
Lessontechnical correctness and facts; pedagogy; alignment with the learning goal; overall quality
Quizdifficulty; coverage of the lesson's core; wording and possible misreadings; writing quality; alignment with the learning goal
Feedbackuseful; explains enough; personalized to how I like things explained
Tutorguardrails; personalization

Be specific: this review becomes step 2's checklists

What this review finds becomes the checklists of your reviewer subagents in step 2. A reviewer told "check that no stem can be read two ways, as q4 could in my c1 review" finds more than one told "review this quiz". So write each problem with the item id, the submission and item, the probe id or the quote that shows it, and say what a reviewer should check for.

Example: one criterion, in a student's words 
#### Explains enough

Rating: 3

The feedback names the right misconception every time, but it often stops there.
s1 q5 is marked partial with "Close, but think about who decides when to stop", which never says which half of my answer was right.
